# 活动中心

独立扩展服务，默认端口 9878。当前活动只有「充值抽奖」，以后按活动注册表增加 Tab；管理员奖励账本是独立入口。用户页提供转盘、单抽 / 10 / 20 / 50 连抽和个人奖励分页，不展示规则说明、概率或充值门槛。用户界面使用主站 SSO，只有实时核验过的管理员可以读取奖励账本、入账回执及执行恢复入账。

## 接入

1. 将 `.env.example` 配置为 `.env`，填写活动 HTTPS 地址、主站内部 / 公开地址和管理员 API Key。
2. 配置 SELECT-only PostgreSQL 连接 `SUB2API_DATABASE_URL`，读取主站 `redeem_codes`，`ACTIVITY_CENTER_RECHARGE_SOURCES` 默认为 `redemptions`。使用与运营中心成本分析相同的余额兑换入账口径，不再合并支付订单或调用充值中心实付接口；数据库不可用时暂停新抽奖，不回退到不完整合计。
3. 首次部署启动时自动将当前时间永久记入 SQLite，只统计该时刻起实际使用的余额兑换记录，部署前已使用的兑换不产生抽奖次数，也不计入高额奖品门槛。兑换码提前生成、活动开始后才使用的，按使用时间计入。起点不支持手动指定或回溯；非空的旧 `ACTIVITY_CENTER_START_AT` 配置会被拒绝，须移除。更新、重启保留原起点和已用次数，不能更换数据卷重开额度；程序会拒绝时区、主站 / 数据库变化。密钥轮换不改变活动范围。
4. 主站自定义菜单配置活动中心 HTTPS 根地址，开启 Token 传递，沿用其他 extra 模块的 `token` / `access_token` 参数。页面立即清除地址栏 Token，换取短时活动会话；前端不持久保存主站 Token。跨站 iframe 支持 Partitioned Cookie 和内存 / sessionStorage 中的独立短时 Session，主站 Token 仅保留在服务端内存。
5. TLS 反向代理转发到 `127.0.0.1:9878`，保留 Host / X-Forwarded-Proto，关闭含参数的访问日志，使用 `no-referrer`；只在可信的一层代理后开启 `ACTIVITY_CENTER_TRUST_PROXY`。多主站域名填 `SUB2API_PUBLIC_URLS`，不支持通配符。推荐独立域名根路径，不能直接把服务挂在去不掉前缀的子路径下。

根 Compose 已登记 `activity-center` profile；源码构建入口：

```bash
docker compose --env-file compose.services.env --profile activity-center up -d --build activity-center
```

部署前须确认对应提交的 CI 和 `activity-center-latest` 镜像已成功发布。先升级配套主站，再更新活动中心：主站固定码 `create-and-redeem` 契约须支持 `affiliate_balance`，并包含将兑换码字段扩大为 128 位的迁移，以容纳现有 51 位活动码。运营中心需包含旧活动赠送识别，避免历史奖励虚增自动收入。已上线环境和验证记录见[生产部署](docs/production-deployment.md)，其中首次上线使用的是旧实付口径，不能视为本次概率或返利类型入账已上线的证明。

旧版 `official` / `recharge_center` / 两者混用的配置会统一读取兑换记录，必须提供只读数据库连接。首次迁移保留原主站 / 数据库 / 时区与旧 `ACTIVITY_CENTER_RECHARGE_URL`（如有），供原活动身份核验；验证通过后，只更新来源标识，保留原起点、已用次数、批次和奖励账本。之后可移除旧充值中心 URL / Token；不再需要充值中心在线或提供集成令牌。来源身份不匹配时拒绝启动，不创建新活动替代旧数据。

## 内部结算口径

机会按余额兑换净入账金额计算，每累计 5,000 分产生一次机会，零头保留。PostgreSQL 先精确合计原始金额，再向下取整到分，不把未满 50 元的金额四舍五入为一次机会。新奖品由工作器自动以「余额（返利转入）」`affiliate_balance` 类型计入主站余额，不走支付回调、不产生充值机会或二次推荐返利，不扣减用户原有可转返利额度。转盘为等角度视觉显示，开奖结果完全由服务端加密随机数决定，前端只能让转盘停在返回的奖项。

下表仅是维护文档与服务端配置，不进入静态资源或用户 API：

| 奖品（元） | 概率 | 活动期累计兑换净入账（元） |
| --- | --- | --- |
| 0.5 | 52% | 无限制 |
| 1 | 20% | 无限制 |
| 2 | 10% | 无限制 |
| 3 | 5% | 无限制 |
| 5 | 2% | 无限制 |
| 10 | 5% | ≥ 1,000 |
| 20 | 4% | ≥ 2,000 |
| 50 | 2% | ≥ 5,000 |

不满足条件的奖项权重全部并入 0.5 元，其他已解锁奖项概率不变。0.5 元在累计充值不足 1,000 / 满 1,000 / 满 2,000 / 满 5,000 元时的实际概率分别为 63% / 58% / 54% / 52%。全解锁每抽期望 3.21 元。各次独立，连抽与单抽使用完全相同的采样函数。

- `redemptions`：只读当前用户 `status='used'`、`used_at` 在活动起点至当前时间内、类型为 `balance` / `admin_balance` 的记录，排除用户 ID 1。直接按 `value` 原数值作为人民币入账金额，正数增加、负数冲减，与成本分析的兑换入账口径一致；不按渠道实付、币种或汇率折算。
- 「余额（返利转入）」的类型为 `affiliate_balance`，不在充值类型白名单内；原生返利从 `user_affiliate_ledger` 合并展示，新活动奖励则持久化为同类型的兑换回执。两者都不计充值金额、不产生抽奖次数或高额奖品资格，无须备注标记；主站余额和累计充值字段的变化不参与活动计算。
- 普通余额兑换、充值中心入账、Sub2API 内置余额充值产生的兑换记录、管理员余额调整都经过同一读取路径，每条兑换只计一次；支付订单与充值中心实付不再相加。订阅、并发、邀请等非余额兑换，以及只有付款但尚未产生已使用余额兑换的订单不产生机会。成本分析的手工收入和无关联兑换的支付补充收入也不纳入活动。
- 新活动奖励通过 `affiliate_balance` 类型直接排除；历史 `balance` 奖励保留固定 `AC-...` 码和完整活动备注同时匹配的排除，与运营中心活动赠送识别一致，避免奖励循环产生机会。其他普通兑换及管理员入账按记录金额计算，不能用此口径证明渠道现金实收；支付退款不会单独改变兑换金额，须以主站实际兑换 / 调整记录为准。记录减少或负数调整后，可用次数最低为 0，未来净入账先抵扣已抽次数，不扣回奖励余额、不重置已用次数。
- 补贴单独生成兑换记录，备注只要任意位置包含连续的“补贴”二字即可，例如 `补贴说明`、`故障补贴到账`、`余额补贴` 或 `[补贴] 故障补偿`。`balance` / `admin_balance` 的此类记录正常到账并保留主站明细，但不计充值金额、抽奖次数或高额奖品门槛；运营中心也排除充值额度与自动收入。不要求方括号或固定前缀，仅按字面包含判断，`不含补贴` 也会排除；空备注与不含该词的正常充值照常统计。正常充值与额外补贴分别入账，不能给合并后的整笔充值备注写“补贴”。
- 原始余额仍由主站维护。奖励账本存入账回执、状态、原始抽奖结果和管理员恢复操作；运营中心仍负责现有资金核对，将带完整活动标识的余额兑换识别为赠送，不增加现金收入。

## 可靠性与账本

SQLite WAL 在一个事务里写入整批奖品及已消费次数，唯一 `(user_id,request_id)` 防止重复提交。请求 UUID 在浏览器获得结果前保留；断网后恢复同一次结果，不重抽。每笔奖励都有独立随机固定兑换码，单笔对应一次主站原生入账。重试只复用这一码和同一金额 / 用户，服务端逐项核对兑换码、金额、类型、状态、用户、时间与活动备注；不直接改主站余额。

SQLite schema 2 自动增加每笔奖励的 `credit_type`。升级前已存在的待入账、异常和成功记录都保留 `balance`，继续原码原金额重试，避免主站已到账但响应丢失后变更类型或重复发钱；升级后新抽奖固定使用 `affiliate_balance`。保留原数据卷、活动起点和已用次数，不能通过清库切换类型。主站尚未支持新类型时，新奖励仍保存原结果并显示待入账 / 异常，自动重试达到上限后由管理员恢复；不会降级为普通余额充值。

后台工作器每 15 秒检查队列，使用 60 秒租约和尝试序号隔离迟到结果。网络 / 主站异常指数退避最多 8 次，回执不一致直接标记异常；管理员可恢复同笔入账并留下审计。崩溃后租约到期自动恢复，已成功但本地未收到的入账通过主站固定码契约再次核验。不会退还已抽机会重新选奖，也不因超时补发第二笔。

账本累计 / 今日已发放只计算通过核验的 `paid` 记录，今日按主站回执实际使用时间及配置时区计算；待入账和异常另列。明细支持用户 / 邮箱 / 奖励流水 / 批次 / 回执搜索、抽奖日期区间、状态筛选、分页及原生回执详情；汇总独立于列表筛选。用户 API 只返回自己的必要结果，不返回回执、其他用户或内部充值快照。

管理员账本增加「门槛审计」：按每笔奖励关联批次保存的抽奖时充值金额，核验 10 / 20 / 50 元奖品对应的 1,000 / 2,000 / 5,000 元门槛。未达门槛时显示异常用户数、奖励笔数 / 总额及其中已入账金额，可一键筛选并查看所需充值、当时充值与差额。快照缺失、金额无效或用户不匹配单独显示待核查，不能当作正常；无需门槛的奖品不报异常。汇总覆盖全历史的已入账 / 待入账 / 异常奖励，独立于搜索、日期、状态和分页；打开账本、手动刷新及页面可见时的定时刷新均重新核验。明细读取失败时仍保留成功取得的全局审计结果，审计本身读取失败则明确提示暂不可用。

此审计只读核对抽奖资格与保存快照的一致性，当前充值、后续充值 / 退款或余额调整不改变历史核验依据；充值来源及现金实收核对仍归运营中心。门槛、快照、审计结果与管理页面都仅管理员可见，普通用户页及奖励 API 继续隐藏这些条件。

使用一个活动服务实例和持久数据卷；虽然 SQLite 事务及租约可以保护共享文件的并发写入，登录会话仍为本机内存。不要多副本配多个数据卷，更不要删卷重试。备份请停服务后复制整个数据目录，或通过 SQLite backup API 取得一致快照；不能只复制运行中的主文件而漏掉 WAL。暂停新抽奖设置 `ACTIVITY_CENTER_ENABLED=false`，已产生奖励仍继续完成。`healthz` / `readyz` 分别检查进程与本地 SQLite，不代表外部充值 / 主站一定可用。

## 本地验证

```bash
npm ci
npm run check
npm test
npm run preview
```

预览仅监听本机 19927，使用临时 SQLite 和虚构身份 / 充值 / 原生回执，绝不加载生产 `.env`。用户：`http://127.0.0.1:19927/?token=preview-user`，管理员：`http://127.0.0.1:19927/?token=preview-admin`。正式镜像不包含这些脚本，没有模拟角色切换或付款接口。

仅在隔离预览中设置 `ACTIVITY_PREVIEW_AUDIT=1`，可加入三笔未达门槛和一笔无效充值快照的虚构奖励，用于检查管理员提醒；默认预览使用正常样本。这些异常样本不通过正式接口生成，也不会连接真实主站或发放真实金额。

`npm run test:browser` 启动另一套临时服务，使用 Playwright + Chrome 验证实际页面、转盘像素及落点、单抽 / 连抽 / 丢失响应恢复、权限和账本、手机 / 窄屏 / 深色 / 减少动画。可通过 `PLAYWRIGHT_MODULE` 指定已有 Playwright 安装。单元 / HTTP / PGlite SQL 测试覆盖精确概率全集、兑换净入账 / 起点 / 负数调整 / 奖励排除、旧来源迁移、并发、幂等、回执、重启、CSRF 和角色撤销，不操作真实资金。
