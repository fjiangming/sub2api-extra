# 活动中心

独立扩展服务，默认端口 9878。当前活动只有「充值抽奖」，以后按活动注册表增加 Tab；管理员奖励账本是独立入口。用户页提供转盘、单抽 / 10 / 20 / 50 连抽和个人奖励分页，不展示规则说明、概率或充值门槛。用户界面使用主站 SSO，只有实时核验过的管理员可以读取奖励账本、入账回执及执行恢复入账。

## 接入

1. 将 `.env.example` 配置为 `.env`，填写活动 HTTPS 地址、主站内部 / 公开地址和管理员 API Key。
2. 选择充值来源。充值中心模式需在 `recharge-center/.env` 设置独立随机令牌 `RECHARGE_CENTER_ACTIVITY_INTEGRATION_TOKEN`，与本模块 `ACTIVITY_CENTER_RECHARGE_TOKEN` 相同；令牌至少 32 字符，服务内部传递，不能给浏览器。主站官方支付模式另需 SELECT-only PostgreSQL 连接。混用填写 `official,recharge_center`；配置后任何一个来源故障都暂停发起新抽奖，不使用不完整合计。
3. 首次部署启动时自动将当前时间永久记入 SQLite，只统计该时刻起的实际付款，部署前的充值不产生抽奖次数，也不计入高额奖品门槛。起点不支持手动指定或回溯；非空的旧 `ACTIVITY_CENTER_START_AT` 配置会被拒绝，须移除。更新、重启保留原起点和已用次数，不能更换数据卷重开额度；程序会拒绝时区、主站 / 充值来源变化。密钥轮换不改变活动范围。
4. 主站自定义菜单配置活动中心 HTTPS 根地址，开启 Token 传递，沿用其他 extra 模块的 `token` / `access_token` 参数。页面立即清除地址栏 Token，换取短时活动会话；前端不持久保存主站 Token。跨站 iframe 支持 Partitioned Cookie 和内存 / sessionStorage 中的独立短时 Session，主站 Token 仅保留在服务端内存。
5. TLS 反向代理转发到 `127.0.0.1:9878`，保留 Host / X-Forwarded-Proto，关闭含参数的访问日志，使用 `no-referrer`；只在可信的一层代理后开启 `ACTIVITY_CENTER_TRUST_PROXY`。多主站域名填 `SUB2API_PUBLIC_URLS`，不支持通配符。推荐独立域名根路径，不能直接把服务挂在去不掉前缀的子路径下。

根 Compose 已登记 `activity-center` profile；源码构建入口：

```bash
docker compose --env-file compose.services.env --profile activity-center up -d --build activity-center
```

部署前须确认对应提交的 CI 和 `activity-center-latest` 镜像已成功发布。使用充值中心来源需一并更新充值中心的只读集成接口；运营中心需更新活动赠送识别，避免奖励虚增自动收入。主站不需要改库或改源码，但必须支持固定兑换码的 `create-and-redeem` 原生入账契约。已上线环境和验证记录见[生产部署](docs/production-deployment.md)。

## 内部结算口径

金额以整数分保存，每累计实付 5,000 分产生一次机会，零头保留。奖品直接计入主站余额，不走支付回调、不产生充值机会。转盘为等角度视觉显示，开奖结果完全由服务端加密随机数决定，前端只能让转盘停在返回的奖项。

下表仅是维护文档与服务端配置，不进入静态资源或用户 API：

| 奖品（元） | 概率 | 活动期累计实付（元） |
| --- | --- | --- |
| 0.5 | 40% | 无限制 |
| 1 | 24% | 无限制 |
| 2 | 11% | 无限制 |
| 3 | 8% | 无限制 |
| 5 | 6% | 无限制 |
| 10 | 5% | ≥ 1,000 |
| 20 | 4% | ≥ 2,000 |
| 50 | 2% | ≥ 5,000 |

不满足条件的奖项权重全部并入 0.5 元，其他已解锁奖项概率不变。全解锁每抽期望 3.50 元。各次独立，连抽与单抽使用完全相同的采样函数。

- `recharge_center`：只认充值中心人民币、已验证付款证据且原生入账完成的三种个人收款订单，以 `payable_amount_minor` 和 `alipay_paid_at` 为准。排除未付、待核验、入账异常、纯余额兑换和赠送。充值中心官方模式使用主站支付表计数，在此来源中排除，混用也不重复。
- `official`：只读主站已付款、已完成入账的人民币余额订单，使用 `pay_amount`，排除订阅、赠送、非当前用户及起点前付款。部分成功退款按 `refund_amount / amount` 比例折算人民币实收并四舍五入到分；全退和退款处理中不产生机会。官方订单缺币种按主站契约回退 CNY；明确非 CNY 的已完成订单会阻止抽奖并提示核验，不擅自换汇。
- 普通兑换码、管理员调整、旧线下赠送无法证明实际付款，不自动计入。现有充值中心未提供退款写入流程；若线下另行退款，应在正式退款系统 / 来源契约扩展后同步调整，不能直接篡改奖励或重置活动数据库。官方退款导致历史机会减少时，可用次数最低为 0，未来充值先抵扣已抽次数，不直接扣回已发余额。
- 原始余额仍由主站维护。奖励账本存入账回执、状态、原始抽奖结果和管理员恢复操作；运营中心仍负责现有资金核对，将带完整活动标识的余额兑换识别为赠送，不增加现金收入。

## 可靠性与账本

SQLite WAL 在一个事务里写入整批奖品及已消费次数，唯一 `(user_id,request_id)` 防止重复提交。请求 UUID 在浏览器获得结果前保留；断网后恢复同一次结果，不重抽。每笔奖励都有独立随机固定兑换码，单笔对应一次主站原生入账。重试只复用这一码和同一金额 / 用户，服务端逐项核对兑换码、金额、类型、状态、用户、时间与活动备注；不直接改主站余额。

后台工作器每 15 秒检查队列，使用 60 秒租约和尝试序号隔离迟到结果。网络 / 主站异常指数退避最多 8 次，回执不一致直接标记异常；管理员可恢复同笔入账并留下审计。崩溃后租约到期自动恢复，已成功但本地未收到的入账通过主站固定码契约再次核验。不会退还已抽机会重新选奖，也不因超时补发第二笔。

账本累计 / 今日已发放只计算通过核验的 `paid` 记录，今日按主站回执实际使用时间及配置时区计算；待入账和异常另列。明细支持用户 / 邮箱 / 奖励流水 / 批次 / 回执搜索、抽奖日期区间、状态筛选、分页及原生回执详情；汇总独立于列表筛选。用户 API 只返回自己的必要结果，不返回回执、其他用户或内部充值快照。

使用一个活动服务实例和持久数据卷；虽然 SQLite 事务及租约可以保护共享文件的并发写入，登录会话仍为本机内存。不要多副本配多个数据卷，更不要删卷重试。备份请停服务后复制整个数据目录，或通过 SQLite backup API 取得一致快照；不能只复制运行中的主文件而漏掉 WAL。暂停新抽奖设置 `ACTIVITY_CENTER_ENABLED=false`，已产生奖励仍继续完成。`healthz` / `readyz` 分别检查进程与本地 SQLite，不代表外部充值 / 主站一定可用。

## 本地验证

```bash
npm ci
npm run check
npm test
npm run preview
```

预览仅监听本机 19927，使用临时 SQLite 和虚构身份 / 充值 / 原生回执，绝不加载生产 `.env`。用户：`http://127.0.0.1:19927/?token=preview-user`，管理员：`http://127.0.0.1:19927/?token=preview-admin`。正式镜像不包含这些脚本，没有模拟角色切换或付款接口。

`npm run test:browser` 启动另一套临时服务，使用 Playwright + Chrome 验证实际页面、转盘像素及落点、单抽 / 连抽 / 丢失响应恢复、权限和账本、手机 / 窄屏 / 深色 / 减少动画。可通过 `PLAYWRIGHT_MODULE` 指定已有 Playwright 安装。单元 / HTTP / PGlite SQL 测试覆盖精确概率全集、充值 / 退款口径、并发、幂等、回执、重启、CSRF 和角色撤销，不操作真实资金。
