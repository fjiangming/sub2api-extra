# 统计指标与实现口径

## 1. 数据边界

统计对象是 Sub2API 终端用户和站点业务。运营指标按需读取 Sub2API PostgreSQL 业务表和原生聚合表；成本分析另有运营中心本地手工台账，不复制供应商资产或凭据。

所有用户业务指标统一排除 `users.id = 1`、`usage_logs.user_id = 1`、`usage_dashboard_daily_users.user_id = 1`、`payment_orders.user_id = 1` 和 `redeem_codes.used_by = 1`，包括人数、请求、四类 Token、费用、耗时、收入、退款、入账、排名、占比及激活/留存的分子与分母。普通用户的 `admin_balance` 调整仍统计；身份缺失的资金记录保留，不能因为用户关联缺失而抹掉金额。本地手工收支没有 Sub2API 用户归属，继续按发生日期统计。数据库容量、真实行数、保留覆盖和清理完整性核验按全部实际源数据计算，避免破坏维护检查。

用量自然日使用 `SUB2API_TIMEZONE`，该值必须与 Sub2API 全局时区一致，默认 `Asia/Shanghai`。最新版 Sub2API 聚合代码按全局时区生成小时和日桶；早期迁移注释中的“UTC bucket”已不再能代表当前运行口径。

资金自然日使用 `FINANCE_TIMEZONE`，默认同为 `Asia/Shanghai`。API 响应和页面会分别显示用量、资金时区，避免跨口径误比较。

“活跃用户”指当天出现在 `usage_dashboard_daily_users` 的去重用户。它是用量活跃，不等同登录活跃或完整成功请求；免费、订阅、零倍率和部分完成的正常用量都可能计入。

## 2. 已实现指标

### 2.1 运营概览

| 指标 | 口径 |
| --- | --- |
| 今日 DAU | 当前用量自然日的去重 `user_id` |
| 本月 MAU | 当前自然月所有日活集合的用户并集；31 天月份不会漏掉月初 |
| 近 7/30 日活跃 | 对相应自然日范围内用户集合去重 |
| 今日/本月新增 | `users.created_at` 落入用量自然日/自然月 |
| 总用户、保留用户、可用用户 | 全部用户、`deleted_at IS NULL`、未删除且 `status='active'` 分开展示 |
| 今日/本月请求 | 保留的 `usage_logs` 请求记录数，排除 `user_id = 1` |
| 今日/本月用户消费 | 对应自然日/自然月保留的 `usage_logs.actual_cost` 求和，排除 `user_id = 1` |
| 今日/本月支付实收 | `payment_orders.pay_amount` 按 `paid_at`、币种汇总，排除 `user_id = 1` |

概览复用用量接口的非管理员汇总，避免今日、本月和趋势采用不同口径。接口逐日比较全部 `usage_logs` 明细请求数与包含管理员的原生日汇总请求数，只用于核验完整性，不作为业务指标返回；明细数不少于日桶请求数才通过该日核验。缺少日桶也标记不完整，不让某一天新增请求抵消其他日期的明细缺失。若逐请求明细已被清理，页面仍保证不包含 ID 1，但请求与消费仅统计保留明细，可能少计。要在 31 天月份始终保留完整的当月用量，Sub2API 和运营中心的请求明细保留期应至少设为 32 天。

### 2.1.1 与成本分析自动收入的关系

本月用户消费是非管理员用户在用量时区内实际产生的 `actual_cost`，属于消费确认；成本分析自动收入是资金时区内已使用的 `balance`、`admin_balance` 记录的带符号 `value`，属于余额入账。两者通常不相等。

一个直观的充分条件是：比较范围均为本月且两个时区一致；逐请求明细完整；自动收入中的余额入账全部属于非管理员用户；每笔 `actual_cost` 都真实从这些用户余额扣减；币种、金额单位和舍入精度一致；除自动收入外没有初始余额、首次绑定赠送、邀请返利、退款、直接改库等其他余额净变动；并且非管理员用户月初与当前的余额合计相同。满足这些条件时两者才会相等。更一般地，设自动收入为 `R`、其他未纳入自动收入的余额净变动为 `O`、月初余额为 `B0`、当前余额为 `B1`，则用户消费 `C = R + O + B0 - B1`；所以 `C = R` 的严格条件是 `O = B1 - B0`。订阅额度或免费额度产生的 `actual_cost` 若不扣余额，也会破坏这个等式，不能把数值相等当成固定业务规则。

### 2.2 任意日期范围用量

`GET /api/metrics/usage?start=YYYY-MM-DD&end=YYYY-MM-DD` 支持 1 至 `RETENTION_USAGE_DAILY_DAYS` 天，起止日期均包含在内。当前默认上限为 730 天。

返回以下排除 ID 1 的用户指标：

- 请求记录数
- 输入 Token
- 输出 Token
- 总 Token（输入与输出之和，不含缓存创建与缓存读取）；页面达到百万用 `M`、十亿用 `B`，最多保留两位小数，小于百万保留整数
- 缓存创建 Token
- 缓存读取 Token
- 标准计价 `total_cost`
- 用户实际消费 `actual_cost`（从所选用量自然日内的 `usage_logs` 汇总，排除 `user_id = 1` 管理员）
- 账号成本 `account_cost`
- 总耗时与 `总耗时 / 总请求` 的加权平均耗时
- 每日活跃人数
- 所选范围内去重活跃用户
- 每日趋势、汇总覆盖起止日期和最新计算时间

查询可以覆盖单日、自然月或任意日期范围。请求、四类 Token、标准计价、实际消费、账号成本和耗时均从非管理员保留明细按自然日汇总；账号成本沿用原生公式 `COALESCE(account_stats_cost, total_cost) * COALESCE(account_rate_multiplier, 1)`，平均耗时使用该范围非管理员总耗时除以请求数。活跃人数继续读取长期日活用户集合并排除 ID 1，对用户去重，不能把 DAU 相加。接口逐日比较未过滤的明细请求数与未过滤的站点日桶请求数，以 `metrics_complete` 标记用量完整性，同时保留兼容字段 `actual_cost_complete`。明细缺失时汇总只包含保留明细，页面提示可能少计，请求、Token、消费趋势对应日期全部留空，不回退到包含管理员的站点总量。

源表缺少某个日桶时，趋势返回 `available=false`，页面显示空缺，不把“数据不存在”伪装成业务零值。

### 2.3 最近 30 天维度统计

`GET /api/metrics/usage/dimensions` 直接读取 `usage_logs`，支持：

- 模型：优先 `requested_model`，回退 `model`
- 用户 `user_id`
- API Key `api_key_id`
- 上游账号 `account_id`
- 分组 `group_id`
- 计费类型 `billing_type`

可以叠加用户、Key、账号、分组和模型过滤，返回请求数、Token、费用、图片/视频数量和平均耗时。聚合前统一过滤 `user_id <> 1`，管理员专属模型、Key、账号、分组和计费类型不会形成结果行；显式查询 `userId=1` 也返回空结果。维度表的输入、输出与总 Token 沿用上述计量展示，总 Token 为输入与输出之和。结果限制 Top 100，日期范围不能超过请求明细保留期。

### 2.4 用户分析

| 指标 | 口径 |
| --- | --- |
| 区间活跃 | 日期范围内日活集合的去重用户 |
| 活跃/新增趋势 | 每日活跃集合和 `users.created_at` |
| 首次观测活跃 | 当前可见日活历史中的最早出现日；不声称是终身首次使用 |
| 7 日激活 | 已成熟注册用户在注册日起 7 个自然日内出现用量活跃 |
| D1/D7/D30 注册留存 | 注册 cohort 在第 1/7/30 自然日再次用量活跃 |
| 当前保留/可用用户 | 当前用户状态，不回写历史 cohort |

Cohort 页面只列最近 90 天注册日。注册人数、首次观测活跃、激活与留存人数及其分母统一排除 ID 1；只有管理员活跃的已知日期显示 0 位用户。尚未到达观察日的单元格标为“未成熟”，不会按 0% 展示。

### 2.5 支付、退款和余额入账

现金与额度必须分账：

支付、退款、付款人数、订单均额和异常订单计数均排除 `payment_orders.user_id = 1`；入账事件、金额和人数排除 `redeem_codes.used_by = 1`。

| 业务事实 | 来源 | 展示方式 |
| --- | --- | --- |
| 支付实收 | `payment_orders.pay_amount` / `paid_at` | 按币种、订单类型、支付日汇总 |
| 退款估算 | `amount`、`pay_amount`、`refund_amount` / `refund_at` | 按订单额度退款比例折算现金，单独标明估算 |
| 净收款 | 当期实收减当期退款估算 | 按币种和订单类型计算 |
| 在线充值入账 | 已使用 `redeem_codes` 且关联支付订单 | 作为额度事件，不再加到现金收入 |
| 独立兑换码 | 已使用余额兑换码且无支付订单 | 作为额度，不默认视为现金 |
| 管理员调整 | `type='admin_balance'` | 正负额度调整，不默认视为现金 |
| 异常订单 | 状态/付款时间矛盾、缺失币种快照、付款后未入账 | 单独计数，要求人工核对 |

币种优先取订单 `provider_snapshot.currency` 或 `provider_snapshot.config.currency`。当前源数据缺失快照时暂归 `CNY`，并计入 `inferred_currency_orders`；这不是支付渠道结算结论。

退款字段不保证等于支付渠道实际现金退款，页面明确显示“退款估算”。跨月退款按 `refund_at` 进入退款发生月，原支付仍保留在 `paid_at` 所在月份。

### 2.6 成本与利润

| 指标 | 口径 |
| --- | --- |
| 自动收入 | 已使用的 `balance`、`admin_balance` 记录汇总带符号的 `value`，排除 `used_by = 1`，以 `used_at` 归属自然日，统一归入 `CNY` |
| 手工收入 | 本地台账中所选币种的收入，以录入的发生日期归集 |
| 总收入 | 自动收入加手工收入 |
| 供应商成本 | 手工台账中绑定 Provider Monitor 供应商的支出 |
| 自定义支出 | 手工台账中自定义名称的支出 |
| 利润 | 总收入减手工支出 |
| 利润率 | 利润除以总收入；总收入为零时不计算 |
| 用户总余额 | 当前未删除用户的 `users.balance` 合计，排除 ID 1 |
| 实际利润 | 利润减用户总余额，仅在 `CNY` 报表计算 |
| 实际利润率 | 实际利润除以总收入；总收入为零或非 `CNY` 时不计算 |
| 平均金额 | 自动收入除以已使用余额记录数；不包含手工收入 |
| 趋势图主站消费 | 与每日列表相同：资金日全部 `usage_logs.actual_cost`，排除 ID 1，包含订阅等计费类型 |
| 趋势图供应商消费 | 仅启用定时检查供应商的账号日实际汇总，按历史充值倍率及汇率折算 |
| 趋势图真实收入 | 主站消费减供应商消费，与日列表使用同一归档 / 实时结果；不扣手工支出或当前余额 |

真实收入趋势仅适用于 `CNY`，保留最多 8 位小数；顶部实际利润卡片仍按余额快照公式计算。趋势从同一逐日报告归并日、周、月、年，利润率按周期合计计算；有未知日期则保留空缺。主站消费按资金时区归属日期，以原生日桶核验全部明细覆盖，保留已删除用户消费；已归档日期使用保存时的完整性，不再读取历史明细。

“每日真实收入”按资金日倒序展示。主站消费排除 ID 1、包含全部计费类型；供应商只统计勾选“启用定时检查”（`enabled=1`）的账号日汇总，Sub2API 取 `total_actual_cost`，New API 读取消费额度 `quota / quota_per_unit`，再按历史充值倍率和汇率折算 CNY。停用供应商即使有旧日志或汇总也不参与新统计；纳入账号包含全部 Key，不与原明细账本叠加。利润为主站消费减供应商消费，不扣手工支出、充值或当前余额。字段 / 倍率 / 汇率缺失、接口失败、重复账号或主站不完整均保留待核验，缺失不当零。

按 `FINANCE_TIMEZONE` 每日 01:00 统计前一日至运营中心 `daily-profit.sqlite`，历史列表及趋势只读此归档，当天在查询 / 刷新时实时读取。首次历史缺口后台补算，页面显示待统计并轮询结果；零点至一点前一日等待归档，未来日期不请求。后台调度补跑、失败退避与任务租约均持久保存，重复统计覆盖同一天。刷新历史范围会后台重算，归档记录的供应商范围、倍率 / 汇率和核验口径在重算前不随配置修改；已保存日报不因主站明细清理而消失，但重算不能恢复已丢失明细。需要两服务配套更新（响应新增 `providerFilter=scheduled_enabled`），无新环境变量，推荐配置已有集成 Token 保证无人值守归档，保留运营中心数据卷。

日、周、月、年只是同一自然日明细的不同汇总粒度。周从周一开始；首尾周期会按查询范围截断。自动收入直接从 `redeem_codes` 单表读取 `status='used'`、`type IN ('balance', 'admin_balance')` 且 `used_at` 非空的记录，也不叠加支付订单，所以每条余额记录只统计一次；正数增加收入，负数冲减收入。并发、管理员并发调整、订阅和邀请记录不具有可靠货币含义，全部排除。兑换表和用户余额都没有币种字段，统一按 `CNY` 处理；用户总余额是查询时的当前快照，不随日期范围回溯。币种之间不自动换算，供应商列表只用于成本归类。该余额入账口径不等同现金实收，`admin_balance` 还可能包含赠送或纠错；在线订阅支付、新用户初始余额、首次绑定赠送余额和邀请返利转余额不在 `redeem_codes` 中，退款估算、税费和未录入成本也不进入利润。手工收入不会和兑换记录自动去重，同一笔线下充值不应同时存在手工收入与 `admin_balance`；源兑换记录被硬删除后历史自动收入也会减少，页面会持续展示这些口径提示。

## 3. 数据来源和保留范围

| 能力 | 来源 | 默认可用范围 |
| --- | --- | --- |
| 请求与维度明细 | `usage_logs` | 最近 30 天 |
| 小时用量/小时活跃 | `usage_dashboard_hourly*` | 最近 30 天 |
| 排除管理员的日用量趋势 | `usage_logs`，原生 `usage_dashboard_daily` 仅核验覆盖 | 默认最近 30 天；已清理明细的日期无法恢复精确用量 |
| DAU、MAU、区间活跃 | `usage_dashboard_daily_users` | 最长 730 天，按 Sub2API 全局时区 |
| 注册和当前用户状态 | `users` | 原业务记录覆盖范围 |
| 支付与退款 | `payment_orders` | 长期业务记录覆盖范围 |
| 余额入账 | `redeem_codes` 及支付订单关联 | 长期业务记录覆盖范围 |
| 手工收支 | 运营中心 `cost-ledger.json` | 数据卷保留范围 |

原生站点级用量仍保留 730 天，日活集合也保留 730 天，可以按 ID 排除管理员并计算历史 DAU/MAU。站点汇总没有用户请求、Token、费用或耗时分项；这些非管理员指标以及模型、Key、账号、分组和计费维度依赖默认保留 30 天的明细，清理后无法重建。接口仍支持最长 730 天范围，但明细缺失时返回不完整标记和提示，不将站点总量冒充非管理员用量。这不影响当前余额和永久资金订单。

## 4. 缓存与负载控制

- 只读连接池最多 4 个连接，查询有超时。
- 常规聚合结果默认缓存 60 秒，最多 100 项，进程重启即消失。
- 维度查询最长 30 天、最多 100 行。
- 日级查询最长 730 天，业务总量只扫描所选日期范围内仍保留的请求明细；活跃使用长期用户集合。
- 容量样本使用有固定上限的内存数组，不创建历史表。

## 5. 已知限制

- 原生日活集合没有保存当时的角色、探针或测试账号标记，清理后不能按新规则重算历史 DAU/MAU。
- `users.last_login_at` 只是最后状态，不能还原历史登录 DAU；当前实现不把它包装成登录活跃。
- 首次观测活跃受最长 730 天集合覆盖限制。
- 资金报表不是会计总账，退款是估算，历史币种快照可能缺失。
- 余额变化还可能来自消费、赠送、推广、冻结和人工操作，不能用余额差倒推充值。
- 站点日聚合没有用户、Key、模型和分组维度，30 天后无法由现有数据恢复这些历史分项。
- 不同币种不会相加为一个“总收入”。

## 6. 验收要点

- 同一用户同日多次请求只计一个 DAU，跨日/月按集合正确去重。
- 31 天月份的 MAU包含第 1 日。
- 任意日期范围顶部用量汇总等于非管理员每日保留明细之和，平均耗时使用非管理员总耗时除以总请求。
- 四类 Token 不重复相加，缓存创建细分不额外叠加到缓存创建总数。
- 缺失日显示空缺而不是零。
- 一笔在线充值只产生一份现金实收和一份额度入账展示，两者不相加。
- 跨月退款进入退款发生期，状态矛盾和缺币种快照可见。
- 管理员专属维度不会形成结果行，ID 1 不参与占比或留存分母；普通用户的管理员余额调整仍参与资金统计。
- 清理 `usage_logs` 后，30 天外维度查询明确不可用，非管理员用量标记不完整并显示趋势空缺；730 天内排除 ID 1 的活跃集合仍可查询。
