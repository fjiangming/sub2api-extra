# Sub2API 数据清理范围与影响报告

报告日期：2026-09-22
实现目录：`sub2api-extra/operations-center`
源码核对基线：Sub2API `d2e319b2a17006122cd2d53d828c44a0bf21bd9b`（`0.2.7` 之后）

## 1. 结论摘要

本次实现采用“短期明细、长期紧凑汇总、资产永久保护”的方案，并遵守不扩展业务数据存储的约束：

- 不修改 Sub2API 源码。
- 不复制 `usage_logs`，不建立冷归档库或永久逐请求扣费账本。
- 请求和请求级扣费明细保留 30 天。
- 小时用量和小时活跃集合保留 30 天。
- 站点日用量、四类 Token、费用、耗时和日活用户集合保留 730 天。
- 普通系统日志保留 7 天；错误详情、拒绝聚合、已结束告警和运维指标保留 30 天。
- 用户、余额、API Key、订单、充值、退款、订阅、资产账本和扣费防重数据不进入清理白名单。
- 不再额外永久保留“历史总消费”。站点消费日汇总最多保留 730 天，超过后不承诺恢复；当前余额和资金订单仍长期保留。

清理服务默认只能预览。只有同时配置 `OPERATIONS_CENTER_ENABLE_CLEANUP=true` 和独立维护连接后才允许执行，而且执行前必须通过聚合检查和预览后备份检查。

## 2. 可执行清理白名单

清理目标写死在服务端，前端只能提交目标 ID，不能提交表名、字段名、SQL 或文件路径。所有条件均为严格小于截止点，即保留截止点及其后的数据。

### 2.1 单次请求及请求级扣费明细

| 项目 | 内容 |
| --- | --- |
| 目标 ID | `usage_logs` |
| 表 | `usage_logs`，包括通过父表访问的现有分区 |
| 时间列 | `created_at` |
| 默认期限 | 30 天 |
| 删除条件 | `created_at < 预览创建时间 - 30 天` |
| 附加条件 | 无 |
| 风险等级 | 高 |

这张表同时承载单次请求与请求级扣费事实，包括用户、API Key、账号、分组、模型、请求号、Token、缓存 Token、图片/视频数量、计费类型、标准费用、实际扣费、账号成本快照、耗时及其他请求元数据。

删除后的直接影响：

- Sub2API 用户和管理员页面无法再查询超期逐条请求。
- 超期数据不能再按用户、API Key、模型、账号、分组、计费类型或请求号筛选、统计和导出。
- `actual_cost` 随请求记录一起删除，因此不能再恢复超期逐笔扣费。
- 依赖请求号、模型、Token、耗时或路由证据的旧投诉只能依靠当时已保存的其他证据处理。
- 当前余额不会被反向修改；支付订单、充值、退款和订阅也不会被删除。
- 站点级日用量和日活集合在 730 天窗口内继续可查，但它们不能恢复逐用户或逐请求维度。

清理前的强制覆盖检查会按 `SUB2API_TIMEZONE` 的完整自然日比较：

- 请求数 `total_requests`
- 输入 Token `input_tokens`
- 输出 Token `output_tokens`
- 缓存创建 Token `cache_creation_tokens`
- 缓存读取 Token `cache_read_tokens`
- 标准费用 `total_cost`
- 用户实际消费 `actual_cost`
- 账号成本 `account_cost`
- 总耗时 `total_duration_ms`
- 去重活跃用户数和日活用户集合

检查区间从 730 天保留边界到 30 天明细截止日。730 天以前的原始明细没有长期汇总承诺，删除后可能完全不可恢复。

### 2.2 小时用量汇总

| 表 | 时间列 | 默认期限 | 附加条件 |
| --- | --- | ---: | --- |
| `usage_dashboard_hourly` | `bucket_start` | 30 天 | 无 |
| `usage_dashboard_hourly_users` | `bucket_start` | 30 天 | 无 |

删除后的影响：

- 超期小时请求、Token、费用、耗时和小时活跃人数曲线消失。
- 不能在 30 天后重新生成小时峰谷、小时并发替代指标或小时活跃集合。
- 日、自然月和任意日期范围的站点级统计继续读取日汇总，不受这两张表清理影响。

### 2.3 站点日汇总与日活集合

| 表 | 时间列 | 默认期限 | 附加条件 |
| --- | --- | ---: | --- |
| `usage_dashboard_daily` | `bucket_date` | 730 天 | 无 |
| `usage_dashboard_daily_users` | `bucket_date` | 730 天 | 无 |

`bucket_date` 按 `SUB2API_TIMEZONE` 解释。删除条件是本地自然日早于“预览时间减 730 天”对应日期，不依赖 PostgreSQL 服务器默认时区。

删除后的影响：

- 730 天以前的站点请求、Token、标准费用、用户消费、账号成本和耗时趋势消失。
- 730 天以前的 DAU、MAU、区间活跃、首次观测活跃和注册 cohort 计算失去依据。
- 当前用户、余额、订单和订阅不受影响。
- 不存在本服务维护的第二份日汇总，因此删除后不能从运营中心恢复。

### 2.4 普通系统日志

| 表 | 时间列 | 默认期限 | 附加条件 |
| --- | --- | ---: | --- |
| `ops_system_logs` | `created_at` | 7 天 | 无 |

删除后的影响：管理员无法再搜索超期普通运行日志、组件消息、请求链路、用户/账号关联和日志全文。它不影响网关请求处理、余额或计费。

`ops_system_log_cleanup_audits` 不在本服务白名单中。它是清理操作审计且增长通常远小于日志正文；Sub2API 原生运维清理仍可能按自身配置处理它。

### 2.5 错误详情及短期运维事件

| 表 | 时间列 | 默认期限 | 附加条件 |
| --- | --- | ---: | --- |
| `ops_error_logs` | `created_at` | 30 天 | 无 |
| `ops_ingress_reject_aggregates` | `bucket_start` | 30 天 | 无 |
| `ops_alert_events` | `created_at` | 30 天 | `status <> 'firing'` |

删除后的影响：

- 用户、客服和管理员无法查看超期错误详情。
- 超期入口拒绝原因、协议、路由族、IP 和用户/API Key 聚合不能复盘。
- 已结束告警的历史复盘范围缩短。
- 仍为 `firing` 的告警即使创建时间很早也不会删除。
- 请求处理和计费主流程不依赖这些历史记录。

### 2.6 运维指标

| 表 | 时间列 | 默认期限 | 附加条件 |
| --- | --- | ---: | --- |
| `ops_system_metrics` | `created_at` | 30 天 | 无 |
| `ops_metrics_hourly` | `bucket_start` | 30 天 | 无 |
| `ops_metrics_daily` | `bucket_date` | 30 天 | 无 |

删除后的影响：超期吞吐、错误率、延迟分位数、Token 消耗和系统性能曲线不能回放。它不修改业务请求、用户余额、费用或订单。

## 3. 用量统计保留情况

### 3.1 仍然保留

在 730 天日汇总窗口内，运营中心支持按单日、自然月或任意起止日期查询：

- 请求记录数
- 输入 Token
- 输出 Token
- 缓存创建 Token
- 缓存读取 Token
- 标准计价 `total_cost`
- 用户实际消费 `actual_cost`
- 账号成本 `account_cost`
- 总耗时与正确加权的平均耗时
- 每日活跃用户
- 所选区间去重活跃用户
- 自然月 MAU、近 7 日和近 30 日活跃用户
- 日趋势和按所选日期范围求和的顶部统计

MAU 和任意区间活跃人数是对 `usage_dashboard_daily_users.user_id` 去重，不是把每天 DAU 相加。31 天月份会包含月初第一天。

资金统计直接读取长期保护的订单、兑换和退款字段，可按任意日期范围查询实际覆盖内的日/月实收、退款估算、净额和余额入账来源。

### 3.2 只保留最近 30 天

以下用量维度依赖 `usage_logs`，因此只保证最近 30 天：

- 用户
- API Key
- 模型
- 分组
- 上游账号
- 计费类型
- 请求号和逐条请求
- 单次请求实际扣费
- 图片/视频用量细分

### 3.3 不再永久保留

- 不永久保存逐笔扣费记录。
- 不新增历史总消费永久账本。
- 站点级消费日汇总保留 730 天，而不是永久。
- 订单永久保留只能证明充值/订阅等资金事件，不能反推出每次 API 消费。
- `usage_billing_dedup` 及归档只用于防止重复扣费，不含可替代 `actual_cost` 的完整金额账本。

## 4. 永久保护范围

以下对象不在任何固定清理目标中。

| 数据类别 | 代表表/对象 | 保护原因 |
| --- | --- | --- |
| 用户、余额、认证 | `users`、认证身份、passkey | 登录、资产、账号恢复和安全状态 |
| API Key 与权限 | `api_keys`、用户允许分组 | 鉴权和服务可用性 |
| 订阅与权益 | `user_subscriptions`、订阅计划/购买关系 | 已购权益和到期判断 |
| 支付订单 | `payment_orders` | 实收、退款、履约和资金争议证据 |
| 支付审计 | `payment_audit_logs` | 支付状态变更和幂等审计 |
| 充值/兑换/人工调整 | `redeem_codes` | 余额入账和管理员调整凭证 |
| 推广和资产账本 | `user_affiliate_ledger` 等 | 奖励、分成和资产对账 |
| 扣费防重 | `usage_billing_dedup`、`usage_billing_dedup_archive` | 防止同一请求再次扣费 |
| 管理与风控审计 | `audit_logs`、内容审核、prompt 审计 | 安全调查、申诉和合规证据 |
| 配置与路由 | 分组、账号、渠道、价格、路由、系统设置 | 在线请求与计费配置 |
| 进行中任务和未消费事件 | outbox、异步任务、幂等状态 | 防止重复执行、丢任务或破坏重试 |

“保护”表示本服务不删除，不代表 Sub2API 其他原生生命周期任务已经关闭。上线时必须同时审查原生配置。

## 5. 间接影响

### 5.1 分组日汇总

最新 Sub2API 在 `usage_logs` 上有删除触发器。删除带 `group_id` 的历史请求时，触发器会更新 `usage_group_rollup_state`，使已发布分组汇总水位后退。后续 Sub2API 同步会以当前仍在线的最早请求为起点重建，并可能移除更早的 `usage_group_daily_rollups`。

因此：

- 本服务不直接删除分组日汇总，但清理原始请求会间接缩短它的可重建范围。
- 超过 30 天的按分组历史消费不能作为稳定承诺。
- 维护角色需要对 `usage_group_rollup_state` 有 `SELECT, UPDATE` 权限，否则首批 `usage_logs` 删除会失败并回滚。
- 维护连接会显式设置为 `SUB2API_TIMEZONE`，避免触发器按错误数据库会话时区后退水位。

### 5.2 原生人工用量删除

Sub2API 的人工用量清理任务完成后会触发指定范围重算。如果原始日志已经删除，对旧范围再次重算可能把已有日/小时聚合缩小或归零。因此：

- 运营中心发现 `usage_cleanup_tasks` 存在 `pending`/`running` 时会阻断执行。
- 30 天滚动保留应使用原生保留参数，不应再创建覆盖旧历史的人工范围清理任务。

### 5.3 下游消费者

`provider-monitor`、外部报表、人工导出和其他消费者若依赖 30 天以前的 `usage_logs`，清理后将无法补采。运营中心要求操作者确认下游同步安全，但不会假装知道所有外部系统的水位。首次执行前必须人工列出下游并确认其回补窗口。

## 6. 明确不处理的对象

本服务不执行以下操作：

- 不删除 PostgreSQL 数据目录、WAL 文件、归档 WAL 或表空间文件。
- 不执行 `VACUUM FULL`、`CLUSTER`、`REINDEX`、`TRUNCATE`、`DROP TABLE` 或 `DROP PARTITION`。
- 不执行 Redis `FLUSHDB`/`FLUSHALL`，不删除 AOF/RDB。
- 不删除 Docker 卷、容器、当前镜像或唯一回滚镜像。
- 不删除 Sub2API 备份集。
- 不删除图片、视频、异步任务输入输出或对象存储文件。
- 不直接清理 channel monitor V2 分层聚合；继续使用 Sub2API 原生 1 分钟/5 分钟/1 小时/12 小时/1 日生命周期。
- 不直接清理通用幂等表、scheduler outbox、会话或缓存键。
- 不自动清理内容审核、prompt 审计或管理审计。
- 不删除 `usage_group_daily_rollups`、`usage_group_rollup_state`、`usage_cleanup_tasks` 或运维 heartbeat。
- 不根据表名通配未知的新表；未知对象默认保护。

这些对象仍会显示在数据库关系大小排行中，便于发现真实增长来源，但不会因为占用大就自动获得删除权限。

## 7. 备份与恢复

Sub2API 原生备份已包含：

- PostgreSQL `pg_dump` 后 gzip 压缩为 `.sql.gz`
- S3 兼容对象存储，可使用单文件或分卷
- 手工和定时备份记录
- 下载链接
- 从原生备份记录执行覆盖恢复
- 密码和可选 step-up 2FA 保护的敏感操作

运营中心不重复保存备份文件，也不实现新的上传/恢复接口。每次执行要求有一份**完成时间不早于当前预览创建时间**的原生成功备份。仅有 24 小时内旧备份不足以放行当前预览。

注意：当前 `/admin/backups` 能恢复 Sub2API 自己记录并位于配置 S3 中的对象；源码没有提供任意本地 `.sql.gz` 文件上传导入接口。跨服务器迁移时应保留 S3 对象、配置和备份记录，或由数据库管理员使用标准 `psql` 流程恢复已下载文件。恢复能力必须在非生产环境定期演练，不能只验证“备份状态 completed”。

若原生 step-up 2FA 拒绝运营中心后台触发备份，应在 Sub2API 原生备份页完成 TOTP 和创建操作；运营中心只需看到后续成功记录即可继续。

## 8. 删除执行保护

一次执行依次经过：

1. 本地管理员登录、会话 Cookie、CSRF 和登录限流。
2. 固定目标白名单与服务端配置的保留期限。
3. schema 重新探测；缺少关键表时失败关闭。
4. 对每张目标表做精确符合行数、最早/最晚时间和逻辑体积估算。
5. 对 `usage_logs` 做完整自然日聚合一致性和 24 小时水位新鲜度检查。
6. 检查没有正在等待或执行的 Sub2API 人工用量清理任务。
7. 预览有效期默认 15 分钟，过期必须重建。
8. 预览后原生成功备份硬闸门。
9. 不可逆影响与下游水位两个确认框。
10. 每个预览随机生成专属中文确认短语。
11. 执行前再次检查 schema、聚合、任务冲突和备份。
12. 数据库 advisory lock 防止多个运营中心实例同时执行。
13. 单连接、每批默认 5,000 行、每批独立事务、5 秒锁等待上限和批间延迟。
14. 分区表使用 `tableoid + ctid` 定位真实分区行，并使用 `FOR UPDATE SKIP LOCKED`。
15. 单次默认最多 5,000,000 行，达到上限后标记部分完成，必须重新预览。
16. 取消只在批次之间生效；已提交批次不会回滚，当前批失败会回滚该批。
17. 结果记录每个目标、表、批次、删除行数、备份与覆盖检查，输出 stdout 并可下载 JSON。

运行报告仅保存在有上限的进程内存中，服务重启后消失。这样不新增一张无限增长的清理审计业务表；生产环境应让 Docker/日志平台按既定期限保存 stdout。

## 9. 磁盘空间效果

### 9.1 能确定的效果

- 超期行不再参与查询。
- PostgreSQL 可以在后续写入中复用这些行原来占用的页。
- 索引中的无效项会由 vacuum 逐步处理。
- 稳态在线明细规模会从无限增长收敛到近 30 天附近。

### 9.2 不能直接承诺的效果

- `DELETE 100 GB` 不等于操作系统立刻多出 `100 GB`。
- 删除会先产生死元组和 WAL，执行期间短时空间压力可能上升。
- 长事务、复制槽和落后副本会延迟 vacuum 与 WAL 回收。
- 普通 `VACUUM` 主要让空间在库内复用，通常不收缩数据文件。
- `VACUUM FULL` 会重写并强锁表，还需要额外临时空间；满盘时贸然执行风险更高。

已分区的 `usage_logs` 有两种行为：

- 运营中心按行批量删除，截止点精确，但空分区文件仍需 PostgreSQL 后续维护，物理回收较慢。
- Sub2API 原生持续保留会删除完整超期月分区，物理回收更快，但 30 天配置可能实际保留约 30 至 61 天，因为与截止点相交的整月分区不能提前删除。

页面中的“逻辑体积估算”按目标行数和整表/分区总占用估算，只用于量级判断；“可归还文件系统空间”保持未知，不与该估算画等号。

## 10. 推荐上线步骤

1. 先以 `OPERATIONS_CENTER_ENABLE_CLEANUP=false` 部署，只开放统计和诊断。
2. 核对线上 Sub2API 版本、迁移、全局时区、表覆盖和当前原生保留配置。
3. 连续采样至少一天；大库建议 7 至 14 天，确认主要增长表和高峰时段。
4. 用相同口径抽样对账日汇总与 `usage_logs`，并确认运营中心覆盖检查通过。
5. 盘点 `provider-monitor`、报表、导出和其他下游的最近同步时间。
6. 在独立环境完成一次 Sub2API 原生备份恢复演练。
7. 创建受限维护角色，启用清理；不要使用数据库 owner 或超级用户。
8. 第一次只选择普通系统日志，验证预览、备份、执行、取消和报告链路。
9. 请求明细从当前 90 天等较长窗口分阶段收缩，例如 `90 -> 75 -> 60 -> 45 -> 30`，每阶段重新预览和备份。
10. 每阶段观察请求延迟、数据库 CPU/IO、WAL、复制延迟、死元组、autovacuum 和文件系统余量。
11. 最后把 Sub2API 原生滚动保留参数设置为 30/30/730，避免仅靠人工运行维持窗口。
12. 验证用户页面明确标注近 30 天维度范围，长期页面只展示日级站点汇总。

## 11. 验收标准

- 30 天内逐条用量和各维度统计完整。
- 730 天内任意日期范围的请求、Token、费用和日活统计可查询，空缺日不伪装成零。
- MAU 和区间活跃用户正确去重。
- 清理前后的当前余额、用户、Key、订单、充值、退款和订阅逐项一致。
- 清理前后的保留窗口内日汇总与日活集合一致。
- `firing` 告警未被删除，保护表没有出现在任何运行报告中。
- 没有新建业务统计表、归档库或永久消费字段。
- 没有调用 `VACUUM FULL`、`TRUNCATE`、`DROP` 或文件删除。
- 备份必须晚于预览，旧备份无法绕过硬闸门。
- 失败批次回滚；连接失败后任务不会永久占用运行锁。
- 分区子表体积被计入容量和清理估算。

## 12. 剩余风险与边界

- 当前尚未连接用户的真实 PostgreSQL，实际数据规模、索引选择、锁竞争和每批耗时必须在线上只读预览及维护窗口中验证。
- 运营中心 advisory lock 只协调自身实例，不能与 Sub2API 的 Redis/数据库原生运维锁形成同一把锁。应避开原生清理时段；行锁能避免重复删除，但不能消除叠加负载。
- 精确 `COUNT(*)` 在超大历史表上可能超过只读查询超时；这会让预览失败，而不是退化成不准确执行。
- 退款现金额是根据 `amount`、`pay_amount` 与 `refund_amount` 的比例估算，不是支付渠道结算单。
- 缺失 `provider_snapshot.currency` 的历史订单按当前实现标记并暂归 CNY，需人工核对。
- 活跃集合没有保存历史角色、探针或测试用户快照；长期 DAU/MAU 不能在清理后按新排除规则重算。
- 服务自身容量样本在内存中，重启后重新积累；要跨重启长期容量趋势必须接入现有监控，不能在“不新增存储”约束下伪造。

最终判断：该方案保留了用户最常用的近 30 天明细、最长 730 天的站点用量与活跃统计，以及全部关键资产和资金记录；主要牺牲是超期逐请求、逐扣费和维度历史。这个取舍能显著限制 `usage_logs` 与运维日志的持续增长，同时不会通过新增副本把空间问题转移到另一套存储。
