# 对话 JSONL 推送接入

只修改、升级运营中心，不需要修改或重新发行 sub2api 采集器。目标是按日志日期和模型汇总 JSONL，以默认 **10,000,000,000 字节（10 GB）** 为对象上限，通过 S3 Multipart Upload 上传到指定 Bucket。目录为 `桶 / 可选前缀 / 日志日期 / 模型 / 带时间戳的文件.jsonl`；要直接在桶下放日期目录，前缀须留空。推送开关仍默认关闭。

## 接收方提供的信息

- S3 兼容平台、HTTPS Endpoint、Region、Bucket、目录前缀，以及是否使用 Path Style。
- 专用访问凭据；临时凭据还需 Session Token、有效期与更新方式。当前不自动取得或刷新外部 STS 凭据。
- 目标前缀的 `s3:PutObject` 和 `s3:AbortMultipartUpload` 权限，服务支持 Create / UploadPart / Complete / Abort Multipart Upload。不要求列举、读取或删除正式对象。
- 新 JSONL 单行仅包含 `request_id`、`request`、`response`，接收方还需兼容升级前仍在重试 / 续传的 v1 Base64、v2 带编码字段格式或 v3 两字段正文；确认请求 ID、原文 / 脱敏、特殊字节表示、日期时区、实际模型名的约定。

当前每行表示一次已归档的上游请求尝试或一段 WebSocket 消息，不把若干请求拼造成一条完整多轮会话。新格式仅有 `request_id`、`request`、`response`。请求 ID 直接取已保存的网关 `request_id`，不是归档行 ID、投递 ID 或厂商响应 ID；同一请求的多次上游尝试可共用此值，每条仍分别保留，接收方不能仅按它去重。两侧直接输出有效 UTF-8 正文字符串，保留原有 JSON 字段、大整数、数值写法、空白、BOM 和 SSE。外层 JSON 的引号与换行按标准转义，读取一行 JSON 后即得到原文本；不把正文 JSON 转成对象或重新排列。WS 有帧时，两侧分别为按各自方向排序的消息字符串数组，保留空帧，非空初始正文作为对应首项；帧时间、交错顺序与 binary 元数据留在内部。不因格式转换删除消息或再次脱敏。

gzip / br / deflate / zstd 在独立输出后台按内存预算解压，严格检查 UTF-8，不改变正文文本。真正二进制与非法文本用 `data:application/octet-stream;base64,<完整原字节的Base64>` 保留；无法解压、未知压缩或解压后仍为非法文本时，用 `data:application/octet-stream;content-encoding=gzip;base64,<完整原压缩字节的Base64>`（gzip 随实际编码变化）。内存不足明确失败 / 重试，不截断、不因预算改变输出表示。正文内图片编码、模型加密字段或签名仍原样保留，不递归解码或尝试解密。原字节校验仍在内部进行，新 JSON 不包含编码、摘要、schema 或元数据字段；示例和消费规则见 [接收格式](conversation-logs.md#接收格式)。

页面批量下载也采用相同 JSONL 行格式，支持当前筛选下最近 1–10,000 条（默认 1,000），按时间从新到旧，不受分页影响；下载为一个文件，不按日期 / 模型切卷。默认脱敏优先，不可用时使用保留原文，回退原因与完整性留本地跟踪，原始单侧字节下载仍可用。采用独立、单并发、2 MiB/s 的只读下载进程，避让采集和交互读取，无明文暂存或整文件页面 Blob；详见 [JSONL 下载与中断边界](conversation-logs.md#jsonl-下载)。仓库 Compose 内存默认 4 GiB，CPU 仍 1 核；镜像本身不能改变既有容器限额，推送堆扩容也不自动提高导出进程的堆上限。

## 页面配置

在“对话日志 → 推送策略 → 推送平台”添加或编辑 S3，文件格式选择“JSONL · 按日期和模型汇总”。单文件上限默认 10 GB；归档日期时区默认 `Asia/Shanghai`，可填写有效 IANA 时区，例如 `UTC`。日期取日志自身的内部 `metadata.at`，不是上传日期；迟到记录仍进入原日志日期下的新卷，不向正文添加日期字段。原文与脱敏沿用已有选择；脱敏异常、过期规则、排除用户和模型名单依然在推送前复核。历史批次、文件进度及重试位于“推送任务”，价格明细与合计位于“存储计费”。

历史批量推送每批最多匹配 10,000 条，超过时按日期、模型等缩小筛选后重新预览，不会只取前 10,000 条而遗漏其余记录。预览和推送记录只查询轻量索引，不在主 HTTP 进程扫描正文。旧库升级后可能显示“历史推送准备中”，由独立低优先级读取进程分批补齐原内容指纹，新采集记录直接同步索引；准备期不自动重发历史、不改变投递 ID 或正文。所选历史未就绪时会及时显示重试提示，已就绪的筛选子集可继续预览。原日志列表 / 导出索引的就绪状态不因这次推送准备而被重置。

“推送范围”默认“仅传输完整”，与旧策略一致。显式选择“包含传输未确认”后，可推送已保存但 `read_error` / 提前关闭等传输状态未确认的内容；本地仍保留 `complete=false`、原 `reason`、上游完成证据和 `transport_diagnostics`，不会伪造完整或恢复未收到的字节，新正文不包含这些字段。该选项对 Webhook、逐条 S3 和 JSONL 一致生效，不绕过用户 / 模型排除，脱敏不可用时按下述规则回退原文。修改范围不重发已有同一任务；自动扫描此前跳过的历史需要重新预览安排。

副本策略默认“脱敏优先（不可用则原文）”：处理失败、待处理、脱敏副本缺失、含 `inspection_warnings` 或规则 / 引擎过期时，有保留原文就使用原文；脱敏密文读取失败也可回退。自动扫描仍先等待待处理阶段完成，手动批次可使用现存原文。内部保存实际副本 `source`、请求副本 `requested_source` 与 `fallback_reason`，不删除原处理异常、检查警告或传输诊断，不把这些字段加入新正文。原文含未替换敏感信息，页面、批次预览与下载状态明确展示，不将其冒充脱敏。原文也不存在、被排除或超出显式传输范围时不能恢复该轮，不伪造完整上下文。升级不自动重处理历史。

JSONL 成员持久保存实际副本与回退原因，写入分片后不重新选择另一种正文；重启、校验前缀和续传使用同一选择，防止文件中途切换。旧成员的空来源按原文件策略解释。格式版本也持久固定：旧 v1 / v2 / v3 任务与文件保持原完整行字节、摘要、上传 ID 及已确认分片；新任务使用三字段数据，内部版本为 4，不在 JSON 中出现，v3 续传仍保留两字段。同日同模型的旧开放卷遇新格式时先封卷，再建立独立新卷，单卷不混版本。历史重新下载会带请求 ID，旧推送若需补带，应重新预览安排新任务；新任务 ID 包含内部格式版本，可能再次推送先前旧格式已送达的同一归档。接收方不能从新正文读取归档 ID，应按 Webhook 幂等头或 JSONL 对象 key / 行位置识别尝试，不能仅按 request_id 去重。自动游标不重置，不自动重发历史。规则或正文改变使已汇总文件失效时，先取消旧文件，再按当前规则重新汇总仍合格的成员；不能拼接两个版本的分片。

Webhook 和逐条 S3 JSON 在首次发送前也持久固定实际副本、回退原因与加密元数据快照。同一投递 ID 的超时 / 重启重试不会从原文换回脱敏副本，也不会改写处理状态；只增加小型加密快照，不额外复制正文。已尝试的脱敏副本后来过期时取消该旧任务，不能用同一投递 ID 换成原文；管理员重新预览安排当前版本。发送和重试仍核对排除、保留期与传输范围，已发出的数据无法撤回。

例如接收方给出：

```text
s3://incoming-04-20260624/2026-06-25/Opus5.5/Opus5.5-2026-06-25.jsonl
```

Bucket 填 `incoming-04-20260624`，对象前缀留空，模型从归档实际值取得。实际文件名加 UTC 时间戳和稳定文件 ID，避免同日滚动覆盖：

```text
s3://incoming-04-20260624/2026-06-25/Opus5.5/Opus5.5-2026-06-25-20260625T080000000Z-0123456789abcdef.jsonl
```

安全模型名（如 `Opus5.5`、`gpt-6.1-sol`）直接用作模型目录，并用于文件名，不自动把 `Opus5.5` 改成 `Opus5`。模型中的路径分隔符等非安全字符仅在路径中替换为 `_`，过长名称截短；发生替换、Unicode 规范化或截短时，目录另加原模型名的稳定摘要后缀，避免不同原始模型混入同一目录，也不允许 `.` / `..` 路径段。正文自带的模型字段不变，不额外添加模型字段。不同原始模型值独立汇总，不通过文件名推断或合并模型别名。

升级前已经生成的旧路径文件保留原 key、成员、上传 ID 和分片进度，继续原路径投递，不搬移或重新发送已送达对象；旧开放卷接收下一条同模型日志前先封卷，新日志转入带模型目录的新卷。仅路径变化，不更改目标身份、格式版本或自动扫描游标。日期仍取日志发生日，迟到 / 历史补推不会改放到上传当天的目录。

同一日期、模型和推送目标累计到上限前会切换新卷，绝不把一条日志切成两行或截断正文。每行末尾为 LF，按实际 UTF-8 输出字节计算大小，包含 request_id、文本转义、必要的 data URI 和换行。单条本身超过配置文件上限时显示 `JSONL_RECORD_TOO_LARGE` 并停止该任务；管理员提高上限后可重试，归档正文保留。请求 ID 异常时明确显示 `EXPORT_REQUEST_ID`，停止该任务、不自动网络重试、不伪造或省略字段，禁止完成不完整文件并安排清理已知的未完成上传；正常归档的请求 ID 已由采集入口验证。

默认定时上传间隔为 0：当日尾卷跨日后自动上传。非 0 时按所填分钟提前上传，适合低流量且需要较快送达的情况。“立即上传待汇总日志”把当前已排队日志汇总后提前上传；历史批量推送也会在该批已排队成员汇总后上传，不要求再等一天。归档距保留期不足六小时也会提前封卷。已汇总成员不占等待处理队列上限，因此大量小日志不会因队列条数被提前切卷；也没有固定行数截断。磁盘低于归档预留空间时停止增加汇总元数据，并提前安排已有文件上传；上传完成后，只有显式启用送达后清理且所有目标均满足条件才删除本地正文。10 GB 是上限，不要求每卷恰好等于 10 GB；跨日、手动、定时、到期保护等情况下同日同模型会有多个文件。

### 多平台与存储计费

原 S3 / Webhook 保留原标识，最多可再添加 18 个 S3 或 Webhook 平台。每个平台独立配置名称、启用状态、地址、凭据和模型价格；S3 的格式、文件上限、归档时区、定时间隔和限速也独立保存。即使两个平台使用相同 Endpoint / Bucket，也会产生各自的任务、JSONL 文件、上传 ID、分片进度及费用凭证，不合并成功状态。后台仍串行上传并避让采集，新增平台会增加总发送量和完成时间，不提高容器配额或并发。

自动推送向当前启用平台分别入队；历史预览可勾选多个平台。隔日日界仍统一沿用原 S3 配置的时区，各平台时区独立决定本平台文件的日期分组。新加平台不会自动补发已有历史，须手动选择日期预览安排。停用只影响后续入队，已有任务仍须继续送达；未完成或已取消但未成功的任务会阻止删除平台。全局关闭推送仍暂停所有平台。所有实际安排的兄弟任务成功后才允许清理，手动批次须整批成功；失败、取消、超时、分片回执或未知 Complete 均不能授权删除。新增平台不会追溯加入以前的额外平台批次；原 S3 / Webhook 保留启用目标与当前正文版本的历史安全复核。

各平台的“模型存储定价”可添加 / 删除模型，精确匹配归档中的模型名，区分大小写，不自动合并别名。每个平台最多 200 个模型；人民币单价以元 / TB 输入，可到 4 位小数，0 表示免费，不接受负数或同名重复配置。预设如下：

| 模型 | 元 / TB |
| --- | ---: |
| gpt-6-astra、gpt-6.1-sol、gpt-6.2-astra、gpt-6.2-sol | 40,000 |
| claude-opus-5-5 | 80,000 |
| claude-opus-5 | 50,000 |
| fable-5 | 60,000 |
| fable-5-1 | 80,000 |
| fable-5-2 | 100,000 |

金额 = 成功完整文件的输出字节 / 1,000,000,000,000 × 该平台该模型单价。JSONL 包含文本转义、data URI 及 LF；JSON / Webhook 使用完整序列化请求体长度，不计 HTTP 头、分片重传流量、归档密文大小或存储商内部开销。同一数据推送至两个平台会分别计量，平台合计是两份容量之和。不是 Token 计费或按月存储租金，也不直接修改主站余额 / 使用账单。使用整数计算，每份文件四舍五入到 0.000001 元再合计。

只在 Webhook 完整发送后的 2xx、S3 PutObject 成功或 JSONL Complete 成功且已确认字节等于完整文件大小后写入费用凭证；连接测试不计费。分片成功、失败、取消和不明送达均不预计费。每个平台的文件 / 投递 ID 唯一，状态与费用同事务提交，重试不会重复入账。成功时冻结当时有效的单价和价格版本，之后改价只影响后续确认成功的文件；修改价格不改变原任务 ID、对象 key 或分片进度。

旧平台升级默认关闭计费，新页面添加的平台默认启用并载入上述预设。已确认的旧 JSONL 文件平时按后台每轮最多 16 份补入容量凭证，不猜测历史价格；旧逐条 JSON / Webhook 没有可信长度凭证的记录不反推费用。缺少单价标为“待定价”，关闭计费的送达记录单列。

“自动补记全部未计费记录”提交一个持久后台任务，按提交时的平台 / 精确模型 / 日志日期筛选及已启用计费的平台价表，自动补完全部符合条件的未定价记录，无需反复点击。不设筛选即处理全部平台 / 模型 / 日期；已计费记录和原金额保持不变。任务先分批核对提交前已有的历史 JSONL 文件，把可信成功容量纳入凭证，再按冻结单价补记；中途改价不改变本任务的单价与版本。新成功投递沿用正常送达时定价；本次范围外、新增价目或重新启用计费后的历史记录可再次提交。未配置单价或提交时未启用计费的记录保留待处理，不阻塞其他模型。保存或启用定价本身不会自动启动历史补记。

任务运行在现有低优先级推送子进程，至少间隔 1 秒，每批最多检查 100 条，循环时间预算约 8 ms，写锁等待最多 1 ms；预算不包含不可中断的单次磁盘操作和提交耗时。只读容量元数据，不读正文、不重新推送；利用已有未定价平台 / 模型索引按游标推进，稀疏日期条件也不会导致单批全量扫描 / 排序。采集、正文读取、导出、修复及正在上传的文件优先，忙时暂停、空闲继续；与送达后本地清理交替执行，避免长期推迟清理。进度、容量、金额和游标与价格更新同事务保存，关闭页面或重启服务后继续；单实例持久节流也防止重复后台进程加速执行。同筛选的重复提交复用进行中的任务，同时最多一个任务；其他筛选须等待或停止当前任务。停止保留已完成的费用，之后重新提交只补剩余。共享 SQLite / CPU / 磁盘仍有少量开销，不保证严格零影响。

每批不触发自动 WAL 检查点；批次事务结束后，在空闲准入仍有效时每 5 秒及任务完成时尝试一次 `PASSIVE` 检查点，已提交页面可以复用，不等待现有读事务退出。长期持有读事务仍可能保留 WAL，日常采集 / 读取优先让行继续生效。页面显示本次筛选、提交时间、补记进度 / 金额、等待原因及停止操作。运行中每 5 秒仅查询单条任务状态，金额汇总最多每 30 秒自动更新一次并在完成后刷新，避免每批重做整表汇总。

“存储计费”支持平台、精确模型名及日志日期筛选，展示按模型 / 价格版本汇总和送达明细，包括模型、成功容量、字节、单价、费用、条数及送达时间。明细每页 20 项，模型汇总最多展示 1,000 行并提示缩小筛选，合计和各平台金额仍包含全部匹配项。平台名称在费用凭证中保留成功时快照。费用凭证不含正文和凭据，独立于正文与临时送达回执；删除本地正文或删除已完成的平台后仍可查询。继续使用原归档数据卷备份方式。

旧 S3 策略升级后继续逐条 JSON 推送，需在页面显式选择 JSONL。Webhook / S3 的新日志任务统一使用包含网关请求 ID 的三字段数据，旧 v1 / v2 / v3 任务继续原格式，传输鉴权和幂等机制保持。Webhook 幂等 ID 留在 `Idempotency-Key` 请求头，S3 单条 ID 留在 key / 对象元数据；连接诊断仍使用独立的测试格式。更改文件格式、目标、副本或时区会取消旧目标下尚未完成的任务，历史可重新预览并批量安排。凭据、定时间隔、限速、推送范围和大小设置更新不改变目标身份；调整大小不重写已汇总或已经上传的文件，新汇总按当前上限切卷。

### 自动推送方式

勾选“自动推送新日志”后，可选择“实时推送”或“推送前一天”，保存后生效；Webhook、逐条 S3 JSON 和 S3 JSONL 均遵循该选择。旧策略默认实时，旧客户端未传 `automaticMode` 时保留已选方式，非法显式值拒绝。页面显示已保存的方式、时区，以及待自动核对 / 已到日期的数量；数量是待调度引用，不等于剩余未送达条数，已经手动送达的同版本记录会在后台核对后去重移除。

- **实时推送**（`realtime`）：新归档处理完成后及时安排；JSONL 沿用满卷、定时间隔、跨日或手动封卷规则，不表示每条都立刻完成一个 S3 文件。
- **推送前一天**（`previous_day`）：按 S3“归档日期时区”（默认 `Asia/Shanghai`）的日历零点安排此前日期的日志。例如 11 月 20 日的日志从 11 月 21 日 00:00 起后台推送，具体送达还取决于采集让行、积压、限速和网络；不是固定 24 小时倒计时，夏令时日期也按当地日历划分。迟到的更早日期仍补推到日志自身日期目录，当天日志继续等待，不阻挡迟到旧日期记录。Webhook 或逐条 JSON 也沿用该时区，默认北京时间。

两种方式都只自动覆盖开启自动推送之后收到的新归档；升级、切换方式不会把此前未入自动范围的全库历史全部发出。存量历史仍需手动预览安排，手动批次与“立即上传待汇总日志”不受未到日期的记录阻挡，后者不会把当天尚待日期的自动记录提前加入队列。关闭期间收到的新记录仍不自动补发；关闭前已经等待日期的引用会保留，重新开启后继续核对。日期 / 排队进度跨重启持久保存，恢复时复核当前排除用户、模型、副本、处理状态和传输范围。

调度每轮最多核对 50 条，只读轻量元数据并保存引用，不读取 / 缓存全天正文。实时及隔日方式的跨日自然封卷只等待相同目标、模型及日志日期的待汇总任务和待自动安排数据，包含尚未扫描到的迟到记录、处理等待及延迟重试；当天或其他模型 / 目标的积压不阻挡昨天的尾卷。日期范围按配置时区的两个日历零点计算，兼容夏令时 23 / 25 小时；未知旧元数据先等待补齐，未来日期的文件不提前自然封卷。这样避免同一天每轮扫描都生成一个小文件，同时允许已齐备的旧日期尾卷及时上传；此后才收到的迟到记录仍另卷补推到原日期。10 GB 滚动、定时、手动和到期保护仍生效。切换方式不改变目标、任务 ID、原文件 key、已确认分片或实际副本；保存策略沿用既有策略变更保护，在途发送可能短暂中止后续传，不重新发送已确认分片。手动和自动处理同一版本时沿用原去重规则。

隔日方式适合按日汇总，但应让本地容量覆盖**至少一天新增日志 + 已有积压 + 上传 / 重试余量**，保留时间覆盖跨日等待和实际上传耗时；仅保留 1 天可能在上传前到期，不推荐。页面的满盘停止、保留期清理和发送失败上限继续有效，调度不能保证故障时全部采集或永不丢失。当前容器 4 GiB / 推送堆 2 GiB 无需因隔日调度增加；日总量与本地空间是主要容量约束。本功能只更新运营中心，数据库自动增加轻量待日期表和索引，无需主站、定时任务或必填环境变量变更，不自动修改服务器和删除开关。

## 后台、恢复与完整性

### 确认送达后清理本地

“推送策略 → 本地保留”可勾选“确认送达后清理本地对话日志”，保存后生效。新旧策略默认关闭，旧客户端未传该字段时保留现有值。开启后，后台分批核对已送达历史和后续新记录；关闭推送或取消勾选会暂停后续删除，已经清理的正文不能从本地恢复。

同一条日志的全部已有任务与当前启用目标均须确认 2xx，当前正文版本和实际副本仍与已推送版本一致；JSONL 必须收到整卷 CompleteMultipartUpload 的成功回执，且文件摘要、累计上传字节正确。分片成功、超时、Complete 回包丢失、失败 / 取消 / 待发送任务、正文更新或新目标尚未送达都不会触发删除；不会因为某一个目标成功就丢失其他目标的发送源。恢复推送时沿用原卷与分片进度。

删除包括本地原文、脱敏副本、正文索引、处理队列和对应的 JSONL 成员引用；远端对象及其分片不删除。现有实现没有落盘的多 GB 明文 JSONL 或导出文件，不需要额外查找 / 删除临时大文件。保留的轻量凭证只包含请求 / 任务 ID、模型、送达时间、HTTP 状态，以及 JSONL key / 摘要等核对信息，不保留用户资料、完整加密元数据或正文；推送记录显示“送达成功，本地已清理”，批次统计仍能核对。凭证和采集幂等指纹保留最多 30 天、各约 100,000 条，后台有界修剪可短时超过计数阈值；过期后不承诺继续识别极旧的采集重放。存量被删除的旧日志不能再次本地导出或重新脱敏，后续导出只包含仍保留的日志。

清理复用独立低优先级推送进程，每 200ms 最多安排一个短批次，单批最多检查 64 条、删除约 4 MiB 正文，循环时间预算 10ms，SQLite 写锁最多等待 1ms。首条超过字节预算时仍允许单条删除，完成后按体积延长下一轮间隔（例如 20 MiB 至少等待 1 秒），避免连续大条绕过 IO 预算；已开始的单次删除、磁盘操作和提交不能中途抢占，不保证严格耗时上限。复用到期队列索引，校验读取精简元数据，批次共用一次提交，避免读取正文尾部字段及逐条同步提交。元数据尚未就绪、内容改变或回执不完整时保留正文，异常回滚整个当前小批次，稍后仅重试本地清理，不重新发送已确认成功的数据。

另一文件正在上传时，可以穿插清理此前已完整送达的文件；当前上传文件及未完成的兄弟目标 / 手动批次不能授权清理。每条间重新核对采集优先，采集、处理、交互读取、下载和历史维护繁忙时让行；下载 / 正文读取持有跨进程租约，直到结束 / 取消或异常租约到期才允许自动清理。后台补计费仍保持至少 1 秒间隔，不随清理调度加速。

SQLite 先释放页面供新归档复用，已释放的可复用页面从归档计入容量中扣除，不必等待磁盘文件缩小。物理缩库让位于待汇总 / 上传 / 重试任务、未封卷文件和已到调度日期的自动积压；采集、处理、读取租约、下载及后台补计费繁忙时也暂停。后台观察到连续空闲 30 秒后，最多每 30 秒执行一次 128 页（512 KiB，按默认 4 KiB 页）增量回收及零等待 checkpoint，不执行全量 VACUUM、不重启主站、不提高内存配额。持续有推送积压或当日未满的开放文件时，物理文件可能较长时间保持原大小，空闲页面仍可复用；物理占用与可复用容量不必同时下降。单次 SQL / 磁盘操作仍不能抢占，共享磁盘 IO / SQLite 写锁仍有成本，不能承诺严格零影响或固定缩库速度；不会让主站推理等待本地删除。无新增主站配置、服务器环境变量、数据库迁移或必填依赖，升级运营中心后沿用既有“送达后清理”开关、原卷与分片进度。

### 后台上传与恢复

- 主 API 只处理管理与队列元数据；正式组装、归档解密与上传都在独立低优先级子进程。子进程默认 2048 MiB old-space，可用容器环境变量 `OPERATIONS_CENTER_PUSH_HEAP_MIB` 设置 128–8192 MiB 的整数，未配置或非法值回退到 2048；不接受附加 Node 参数。只作用于推送子进程，采集、脱敏和导出仍用各自限制。按堆及宿主 / cgroup 空闲内存决定是否允许处理当前记录；堆上限不是 RSS 限额、不预分配，也不保证空闲时立刻归还全部内存。繁忙或内存不足不会转回主线程执行，也不会让 sub2api 等待。
- 不在磁盘创建多 GB 明文 JSONL，不把 10 GB 放入内存。SQLite 保存成员引用和加密元数据快照；后台逐条、按小块序列化，顺序使用一个 8 MiB 上传缓冲区。v3 / v4 输出直接从已认证的副本生成三字段 / 两字段正文，省去不外发的摘要和重复正文转换，v1 / v2 保持原格式。Webhook / 逐条 S3 也使用有界 JSON 分块，先计算长度 / SHA-256 再背压发送，不再生成完整 JSON 字符串和发送 Buffer；内容仍是单个完整 JSON，无额外换行或字段。单条与 JSONL 正文任务互相避让。
- 总内存与堆分别保护，按可能副本的最大单份长度预留，而非叠加原文 / 脱敏大小。推送另外保留 16 MiB 发送开销，只在独立推送进程允许一次 GC 恢复；提高堆上限不会绕过总内存保护。仅独立推送进程在原半数干净非活跃文件缓存之外，计入四分之一干净活跃文件缓存，避免大批量顺序读盘把可回收缓存误认为不可用内存；共享 / 脏页 / 回写不计入，合计不超过真实干净缓存，仍受宿主、容器、堆及 32 MiB 预留限制。其他采集、脱敏、读取和导出预算不变。解压使用同次推送的准入预算。
- JSONL 单条临时 `EXPORT_MEMORY` 先在当前上传位置等待最多 30 秒，逐步延长重试间隔，并持续核对取消、租约和采集优先；页面显示当前内存等待。短暂恢复无需重读已确认前缀。持续内存不足、本地 SQLite 忙锁（`ARCHIVE_BUSY`）、后台卡住恢复（`UPLOAD_STALLED`）及管理取消等待（`ABORTED`）不消耗网络尝试次数，保留 pending / buffered、UploadId 和分片，按当前退避重试；进程退出 / 过期租约恢复也退回当前未结算的本地尝试，成员次数同步更新。恢复新一轮上传会清除文件和成员的上次错误，后续新错误仍明确显示。本地读取 / 分片回执写入忙锁不会再笼统显示“发送条件已变化”或“连接失败”；真正的条件变更仍复核并取消。网络错误 / 超时遵守原上限，不能由远端错误正文伪造成资源等待。升级前已经 failed 的任务仍需管理员核对后点击重试，不自动重发历史。
- 使用分片上传，非尾分片为 8 MiB；SDK 执行 SigV4 签名，每个分片携带 SHA-256。JSONL 上传默认限速 **2 MiB/s**，页面可设置 0.25–64 MiB/s，使用 64 KiB 小块节奏控制，单并发。每个网络操作独立超时；分片额外计入该速率下的发送时间，整个 10 GB 文件不受一个短总超时截断。等待 SDK 也有独立截止，SDK 不响应取消时仍结束等待；响应正文使用可取消、限长的管道，取消时销毁连接并消费迟到结果。完成前复核行数、总字节、当前策略及所有成员，收到完整 Complete 成功回执后再次核对活动租约和取消，才将文件和成员标为已送达并记录 SHA-256。超时或被取消后迟到的成功不能授权计费和清理；远端是否已经完成仍可能未知，沿用相同 key 的至少一次投递边界。
- 汇总文件、成员顺序、对象 key、元数据快照、上传 ID 和每个已确认分片的 ETag、大小、摘要持久化。每 30 秒检查活动租约及检查点：租约失效或超过 120 秒未通过检查点时取消失活上传，再恢复过期 `running` 文件；有效的采集优先等待及前缀校验持续更新检查点，不按整个文件总耗时判断卡住。取消后仍占用超过 5 秒，由主进程重建推送子进程；推送子进程超过 60 秒未报告状态也会被重建。等待旧进程退出后再按现有 5 秒退避启动替代进程，主站和运营中心主 API 不重启，UploadId 和已确认分片保留。重试重新读取 / 解密并序列化已确认前缀来校验分片和整卷 SHA-256，但不再次网络上传已确认分片。未确认分片沿用原 PartNumber 覆盖重试，ACK 丢失也不追加重复行。该恢复节省网络传输，仍有前缀读取和校验成本。
- 整卷有效性检查在轻量元数据索引完整时只查索引，避免为读取指纹 / 处理状态额外遍历正文溢出页；索引未完整时保留原源表检查。实际前缀摘要校验仍读取正文，不以元数据代替字节校验。
- 远端上传 ID 失效返回 404 时，清除旧进度并按退避沿用同 key 重建；Complete 回执丢失也按未知处理，不能仅凭 404 假定已送达。本地分片进度异常会中止旧上传并在尝试上限内重建，字节校验不一致则明确失败，禁止 Complete。旧版本未记录分片的遗留上传先中止，再从头重建。
- 归档接收和待处理优先；推送不再要求归档处理队列完全归零，后台可以在持续采集 / 脱敏时低优先级上传。普通单条交付和计费仍等待归档处理队列清空；已封卷 JSONL 只使用独立的低优先级网络门控，因此不会因为持续的 `cl_processing` 队列把可续传分卷永久挡住。所有任务仍会在当前记录尚未完成、历史读取 / 导出 / 修复或人工清理占用前让行。每条记录、约 256 KiB 序列化和每个分片间检查优先级，繁忙时显示暂停并保留租约和进度；已经发送中的单个分片不会因新采集反复取消，让行不能抢占已开始的 SQLite 读取、单条解密或系统 IO。送达后本地清理仍额外等待归档处理和交互任务空闲，避免删除与采集写入竞争。
- 取消批次、用户 / 模型排除、脱敏规则或内容变化、原记录过期，会中止受影响文件；旧卷不再完成，仍合格的其他成员重新汇总。既有保留期不会为了推送而隐式延长。旧归档被删除的正文不能恢复。
- 接收方需要允许 AbortMultipartUpload。创建上传的回包丢失、强杀或凭据失效仍可能留下无法确认的分片，建议 Bucket 配置未完成 multipart 的过期回收。程序不能撤回已经上传的字节或已完成对象；启用版本控制时同 key 重试可能生成版本，因此仍为至少一次投递。
- 共享 CPU、数据库、磁盘和带宽仍有成本，独立后台不等于严格零性能影响。本功能不改主站推理路径、不调用付费模型、不因推送失败重放用户请求。

管理页展示最近 30 个 JSONL 文件的平台、模型、日期、对象 key、日志数、已确认字节 / 分片进度、暂停状态和错误；失败文件可继续重试。汇总积压包含未完成与失败文件，显示最早归档的保留期到期时间和六小时风险；预览及当前策略的自动扫描显示各类跳过原因。统计不保证队列能赶在保留期前传完，默认不删除原归档。成员进入汇总后显示“待上传”，不提前显示“已送达”。

每条仍需完整读取并解密原归档，并非任意大小都只占 8 MiB 内存。持续资源不足会保持积压；归档到期、被删除或规则排除时仍可能无法继续，等待不等于已送达。下载遇临时内存不足最多等待 30 秒，超时保留明确中断，不能在浏览器断开后自动续接旧文件；需重新导出并核对最终条数和摘要。当前扩容只调整运营中心，不改变主站配置。

## 服务器配置待确认

代码改造不需要主站升级或新增主站环境变量。以下只作为部署清单，需用户确认后执行：

1. 仅更新运营中心，保留现有数据卷与 `archive.key`。SQLite 启动增加分片状态及格式版本小列 / 小表，不扫描回写历史正文。精简正文及后台解压沿用现有内存、限速和采集优先保护，无需因本轮格式变更新增环境变量或提高配额；解压预算不足明确失败，不能改为另一份数据续传。
2. 运营中心容器配额由主 API、采集、脱敏、读取和推送进程共享。仓库 `operations-center/compose.yaml` 的回退值为 `${OPERATIONS_CENTER_MEMORY_LIMIT:-4g}`，`.env.example` 同步 `OPERATIONS_CENTER_MEMORY_LIMIT=4g`，CPU 保持 **1 核**。已有 Compose 插值文件若显式设置 `512m` / `1g`，须单独改成 `4g`；不能假定服务 `env_file` 的变量会自动参与根 Compose 插值。可先备份该配置，再用 `docker update --memory 4g --memory-swap 8g sub2api-operations-center` 在线提高当前容器限额，原进程 / 上传继续运行；宿主无 Swap 时不会产生真实 Swap 后备。随后仅更新运营中心镜像并用原数据卷重建，使默认 2 GiB 推送堆生效；可在 `operations-center/.env` 显式配置 `OPERATIONS_CENTER_PUSH_HEAP_MIB=2048`。重启期间页面 / 采集接收短暂不可用；推送保留原上传 ID 和分片，恢复时重新读盘校验已确认前缀，不重复网络发送已确认分片。无需重新预览、取消或清空批次；既有 failed 任务仍须人工核对重试。仅拉取镜像不能提高当前容器限额，不需要修改主站。
3. 在页面填写 Endpoint、Region、Bucket、前缀、凭据及 Path Style；采用 JSONL、10 GB、Asia/Shanghai。默认限速仍为 2 MiB/s；若服务器出口为 1Gbps 且主站与运营中心共享网卡，建议先从 32 MiB/s 观察，再按主站延迟和出口利用率提高到 48–64 MiB/s，不建议直接把限速设为链路标称的 125 MB/s。推送范围 / 原文选择需按实际需求保存，升级不会默默切换旧策略。原 30 GiB 归档容量、10 GiB 磁盘预留和 7 天保留期不自动修改；接收方故障长于保留期时仍可能丢失未推送历史。
4. 接收方授予指定 Bucket / 前缀的 PutObject 和 AbortMultipartUpload，配置未完成 multipart 的生命周期回收。现有恢复不需要 ListParts、ListBucket、GetObject 或删除正式对象权限；接收方按三字段约定处理网关请求 ID、文本、WS 数组及特殊字节 data URI，并兼容旧在途任务的 v1 / v2 / v3。

不需要调整主站、Nginx、PostgreSQL 或 Redis。容器限额不是内存预留，也不是主机容量承诺；4 GiB 容器与 2 GiB 推送堆仍需在宿主有余量时使用，不保证任意大小的单条都能处理。共享宿主资源有有限成本，不能承诺严格零延迟影响。

## 管理接口与验证

沿用管理员会话、CSRF、限流与禁止公网目标访问私网的默认约束。`POST /api/conversation-logs/push/jsonl/flush` 和 `POST /api/conversation-logs/push/jsonl/:id/retry`；现有 jobs 查询额外返回 `jsonl.files` / `jsonl.counts` / `jsonl.backlog` 和当前推送策略的 `skipped`。测试连接按当前格式发送虚构诊断，并实际执行 multipart 流程。

多平台沿用原策略接口，原 `s3` / `webhook` 字段及 ID 兼容，附加平台存于 `platforms` 数组；旧客户端省略此数组会保留已有附加平台。名称 / 计费配置不改变目标身份，秘密字段仍加密且只返回“已设置”。策略写入经管理员与 CSRF 验证后，采用独立的 4 MiB 请求体上限以容纳多平台模型价表，其余默认接口仍为 64 KiB。`GET /api/conversation-logs/push/billing` 支持 `platform`、`model`、`start`、`end`、`page`，附带补记状态；`POST /api/conversation-logs/push/billing/price` 接受相同筛选，页码不限制任务范围，返回 `202 {job}`。`GET /api/conversation-logs/push/billing/price` 仅查轻量进度；`POST /api/conversation-logs/push/billing/price/:id/cancel` 停止该任务。全部要求管理员会话，写入另需 CSRF / 限流；主进程只创建 / 停止任务，忙锁快速返回 503，不等待批次完成。

`npm run check:conversation-multi-push` 定向覆盖多 S3 失败隔离、续传、清理等待、旧策略兼容、价格快照 / 补价与 API 权限。`npm run preview:multi-push` 启动正式页面的隔离预览，默认 `http://127.0.0.1:20023/preview`，端口占用则顺延；两套 S3 和 Webhook 接收器都只监听本机，使用虚构凭据和正文，预置实际成功送达的费用记录。本地清理与自动推送默认关闭，停止后删除临时数据；不连接生产或真实 Bucket。

本地 `npm test` 覆盖真实 SQLite / HTTP / SDK 签名、JSONL 字节一致、日期与模型分组、10 GB 计数边界、真实多分片与数据库重开续传、分片 / Complete 回包丢失、SDK 忽略取消 / 超时、响应正文不结束、取消后迟到成功、SQLite 分片回执忙锁、404 重建、进度异常和内容变更、采集优先等待 / 排除、低速超时预算、旧策略 / schema 迁移、推送范围和脱敏门禁、内存准入及真实子进程崩溃 / 心跳失效恢复。10 GB 边界采用计数测试，不声称实际向外部平台传输了 10 GB。`npm run check:conversation-push-ui` 覆盖正式页面和本地 S3 接收器；不使用真实上游正文、外部凭据或生产 Bucket。
