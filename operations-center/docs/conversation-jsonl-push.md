# 对话 JSONL 推送接入

只修改、升级运营中心，不需要修改或重新发行 sub2api 采集器。目标是按日志日期和模型汇总 JSONL，以默认 **10,000,000,000 字节（10 GB）** 为对象上限，通过 S3 Multipart Upload 上传到指定 Bucket。推送开关仍默认关闭。

## 接收方提供的信息

- S3 兼容平台、HTTPS Endpoint、Region、Bucket、目录前缀，以及是否使用 Path Style。
- 专用访问凭据；临时凭据还需 Session Token、有效期与更新方式。当前不自动取得或刷新外部 STS 凭据。
- 目标前缀的 `s3:PutObject` 和 `s3:AbortMultipartUpload` 权限，服务支持 Create / UploadPart / Complete / Abort Multipart Upload。不要求列举、读取或删除正式对象。
- JSONL 单行格式是否接受既有 `sub2api.conversation.v1` envelope，以及原文 / 脱敏、日期时区、实际模型名的约定。

当前每行表示一次已归档的上游请求尝试或一段 WebSocket 消息，不把若干请求拼造成一条完整多轮会话。Request、Response 与帧 body 保持完整 base64 字节及 SHA-256；解码后保留原有 JSON 字段、数值写法、空白、SSE 或二进制。不在 JSONL 中解析重排原正文，不删除任何轮次，不因格式转换再次脱敏。

## 页面配置

在“对话日志 → 推送策略”配置 S3，文件格式选择“JSONL · 按日期和模型汇总”。单文件上限默认 10 GB；归档日期时区默认 `Asia/Shanghai`，可填写有效 IANA 时区，例如 `UTC`。日期取日志自身的 `metadata.at`，不是上传日期。原文与脱敏沿用已有选择；脱敏异常、过期规则、排除用户和模型名单依然在推送前复核。

脱敏引擎 v3 兼容协议签名，但含 `inspection_warnings` 的副本仍不具备默认脱敏推送资格；预览 / 自动队列跳过，旧队列和 JSONL 文件再次复核时显示 `INSPECTION_INCOMPLETE`，不会退回发送原文。明确选择原文时，元数据中的 `inspection_warnings` 数组说明此前处理的检查范围，原始字节不变；原文仍可能含完整敏感信息。引擎升级不会自动重处理所有历史，旧脱敏副本需要有原文才能更新。

例如接收方给出：

```text
s3://incoming-04-20260624/2026-06-25/Opus5-2026-06-25.jsonl
```

Bucket 填 `incoming-04-20260624`，对象前缀留空，模型从归档实际值取得。实际文件名加 UTC 时间戳和稳定文件 ID，避免同日滚动覆盖：

```text
s3://incoming-04-20260624/2026-06-25/Opus5-2026-06-25-20260625T080000000Z-0123456789abcdef.jsonl
```

模型中的路径分隔符等非安全字符仅在文件名替换为 `_`，每行原始模型字段不变。不同原始模型值独立汇总，不通过文件名推断或合并模型别名。

同一日期、模型和推送目标累计到上限前会切换新卷，绝不把一条日志切成两行或截断正文。每行末尾为 LF，按实际 UTF-8 输出字节计算大小，包含 base64、元数据和换行。单条本身超过配置文件上限时显示 `JSONL_RECORD_TOO_LARGE` 并停止该任务；管理员提高上限后可重试，归档正文保留。

默认定时上传间隔为 0：当日尾卷跨日后自动上传。非 0 时按所填分钟提前上传，适合低流量且需要较快送达的情况。“立即上传待汇总日志”把当前已排队日志汇总后提前上传；历史批量推送也会在该批已排队成员汇总后上传，不要求再等一天。已汇总成员不占等待处理队列上限，因此大量小日志不会因队列条数被提前切卷；也没有固定行数截断。磁盘低于归档预留空间时停止增加汇总元数据，并提前安排已有文件释放空间。10 GB 是上限，不要求每卷恰好等于 10 GB；跨日、手动、定时、空间保护等情况下同日同模型会有多个文件。

旧 S3 策略升级后继续逐条 JSON 推送，旧 Webhook 协议不变。需在页面显式选择 JSONL；更改格式、目标、副本或时区会取消旧目标下尚未完成的任务，历史可重新预览并批量安排。凭据、定时间隔和大小设置更新不改变目标身份；调整大小不重写已汇总或已经上传的文件，新汇总按当前上限切卷。

## 后台、恢复与完整性

- 主 API 只处理管理与队列元数据；正式组装、归档解密与上传都在独立低优先级子进程。子进程 256 MiB old-space，按堆及宿主 / cgroup 空闲内存决定是否允许处理当前记录。繁忙或内存不足不会转回主线程执行，也不会让 sub2api 等待。
- 不在磁盘创建多 GB 明文 JSONL，不把 10 GB 放入内存。SQLite 保存成员引用和加密元数据快照；后台逐条、按小块序列化，顺序使用一个 8 MiB 上传缓冲区。大型单条仍需读取、解密其已有归档，内存不足会可见失败 / 重试。
- 使用分片上传，非尾分片为 8 MiB；SDK 执行 SigV4 签名，每个分片携带 SHA-256。每个网络操作独立使用所配超时，整个 10 GB 文件不受一个短总超时截断。完成前复核行数、总字节、当前策略及所有成员，只有 Complete 成功才将文件和成员标为已送达，并记录文件 SHA-256。
- 汇总文件、成员顺序、对象 key、元数据快照、上传 ID 和状态持久化。子进程退出后自动重启；未确认上传先尝试中止残留 multipart，再沿用同一 key 从头重试。重试重新上传整个文件，不追加记录，也不宣称逐分片断点续传。
- 取消批次、用户 / 模型排除、脱敏规则或内容变化、原记录过期，会中止受影响文件；旧卷不再完成，仍合格的其他成员重新汇总。既有保留期不会为了推送而隐式延长。旧归档被删除的正文不能恢复。
- 接收方需要允许 AbortMultipartUpload。创建上传的回包丢失、强杀或凭据失效仍可能留下无法确认的分片，建议 Bucket 配置未完成 multipart 的过期回收。程序不能撤回已经上传的字节或已完成对象；启用版本控制时同 key 重试可能生成版本，因此仍为至少一次投递。
- 共享 CPU、数据库、磁盘和带宽仍有成本，独立后台不等于严格零性能影响。本功能不改主站推理路径、不调用付费模型、不因推送失败重放用户请求。

管理页展示最近 30 个 JSONL 文件的模型、日期、对象 key、日志数、字节数、状态和错误，并可重试整个失败文件。成员进入汇总后显示“待上传”，不提前显示“已送达”。

## 管理接口与验证

沿用管理员会话、CSRF、限流与禁止公网目标访问私网的默认约束。新增 `POST /api/conversation-logs/push/jsonl/flush` 和 `POST /api/conversation-logs/push/jsonl/:id/retry`；现有 jobs 查询额外返回 `jsonl.files` / `jsonl.counts`。测试连接按当前格式发送虚构诊断，并实际执行 multipart 流程。

本地 `npm test` 覆盖真实 SQLite / HTTP / SDK 签名、JSONL 字节一致、日期与模型分组、10 GB 计数边界、真实多分片、回包丢失同 key 同内容重试、取消 / 排除 / 过期、脱敏门禁、内存准入及真实子进程崩溃恢复。10 GB 边界采用计数测试，不声称实际向外部平台传输了 10 GB。`npm run check:conversation-push-ui` 覆盖正式页面和本地 S3 接收器；不使用真实上游正文、外部凭据或生产 Bucket。
