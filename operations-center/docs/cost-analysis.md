# 成本分析设计与口径

## 目标

成本分析把 Sub2API 兑换页面中已使用的余额金额、运营人员维护的手工收入和支出台账放在同一时间轴中，提供日、周、月、年汇总。它不修改 Sub2API 源码或业务表，也不把供应商凭据复制到运营中心。

## 数据流

1. 自动收入从 Sub2API PostgreSQL `redeem_codes` 按需读取，只统计已使用的 `balance` 与 `admin_balance` 记录。
2. 手工收入以及供应商成本、自定义支出由管理员录入本地台账。
3. 供应商目录从 Provider Monitor 同步，只保留脱敏字段和最近同步状态。
4. 查询时先按资金时区生成自然日数据，再在应用层归并为日、周、月或年周期。
5. 每日真实收入从主站使用记录和 Provider Monitor 实际采购账本按资金日只读聚合，替代周期明细，独立于手工台账与上方趋势图。

周以周一为起点。查询范围首尾不足完整周期时，周期标签按实际查询边界截断。

## 计算公式

| 指标 | 公式 |
| --- | --- |
| 自动收入 | `status='used'`、`type IN ('balance', 'admin_balance')` 且 `used_at` 非空的记录按 `used_at` 汇总 `SUM(value)` |
| 手工收入 | 所选币种手工收入台账金额之和 |
| 总收入 | 自动收入 + 手工收入 |
| 支出 | 所选币种手工支出金额之和 |
| 利润 | 总收入 - 支出 |
| 利润率 | 利润 / 总收入；总收入为 0 时返回空值 |
| 用户总余额 | 当前 `users.balance` 合计；仅含 `deleted_at IS NULL` 且 `id <> 1` 的用户 |
| 实际利润 | 利润 - 用户总余额 |
| 实际利润率 | 实际利润 / 总收入；总收入为 0 时返回空值 |
| 平均金额 | 自动收入 / 已使用余额记录数；手工收入不参与计算 |

### 消费与实际利润趋势

趋势图展示余额消费、支出和按消费计算的实际利润。余额消费为 `usage_logs.actual_cost` 按 `created_at` 汇总，仅含 `billing_type = 0` 且 `user_id <> 1` 的余额计费请求；订阅计费及未知计费类型不计入。查询不关联用户表，因此已删除或缺失用户的历史消费仍保留。按消费计算的实际利润等于当期余额消费减当期所选币种手工支出，不叠加充值与手工收入，也不再次扣除当前余额；顶部收支与余额快照卡片继续使用上表的原有公式。

消费按 `FINANCE_TIMEZONE` 归入日期，再汇总为所选日、周、月、年周期，金额保留最多 8 位小数。仅在 `CNY` 计算，不把余额额度与外币成本混算。

完整性核验使用 `SUB2API_TIMEZONE` 下全部保留请求的逐日计数，与 `usage_dashboard_daily.total_requests` 对比，包括管理员和订阅请求以保持分子分母一致。两个时区不同的资金日可能跨越多个用量日，查询会读取完整的相交用量日核验覆盖，消费本身仍严格使用资金日期边界。日桶缺失或明细数少于日桶时，相应周期的 `balanceConsumption`、`consumptionProfit` 返回 `null`，`consumptionComplete` 为 `false`，图表留空，不把缺失明细当作零消费或亏损。确认完整的零消费日仍展示零消费及负支出利润。缺少用量表或非 `CNY` 时也返回不可用值，收支与支出台账继续展示。

### 每日真实收入

原周期明细已替换为固定按日、日期倒序的列表，列为日期、主站消费、供应商消费、利润、利润率、主站请求数、数据状态、可展开供应商明细。查询粒度切换为周、月、年时，这个列表仍按日展示，使用 `FINANCE_TIMEZONE` 的自然日边界，金额保留最多 8 位小数。

| 字段 | 计算与核验 |
| --- | --- |
| 主站消费 | 当日 `SUM(usage_logs.actual_cost) WHERE user_id <> 1`，包含余额、订阅及其他计费类型，不关联用户表、不因删除用户抹除消费 |
| 供应商消费 | 上游账号每日消费汇总；Sub2API 取 `total_actual_cost`，New API 使用消费额度 `quota / quota_per_unit`，再按当日已确认历史充值倍率和汇率折算；包含该账号全部 Key，与原采购明细账本分开 |
| 利润 | 主站消费 - 供应商消费，不扣手工支出台账，不叠加充值 / 手工收入，不扣当前余额 |
| 利润率 | 利润 / 主站消费 × 100%；主站消费为 0 时为空 |
| 合计 | 只在各天对应金额均可核验时显示，任一天未知则不把该项缺失当零求和；合计利润率使用合计金额计算 |

此报表目前仅用于 `CNY`，沿用主站使用记录的额度金额约定；供应商费用按覆盖资金日的已确认历史充值倍率和“设置与备份 → 运行设置”汇率换算，不把充值、标价、余额减少估算或手工成本作为逐日消费，不默认外币与 CNY 等值。账号范围包含未勾选监控的 Key，如有其他用途也会计入；应使用专供主站的上游账号。日报不再累加原 Key 采购台账或计数器，不重复计算汇总与明细。

Sub2API 使用账号或用户 Token 调用 `/api/v1/usage/stats?start_date=日期&end_date=日期&timezone=资金时区`，严格要求 `total_actual_cost` 和请求总数；仅模型 API Key 不支持账号汇总。New API 使用系统访问令牌和用户 ID 调用 `/api/log/self/stat`，使用类型 2 的消费额度并验证 `/api/status` 的 `quota_per_unit`，不把 RPM 当全天请求总数。New API 时间戳结束边界为次日零点前一秒，兼容夏令时，不与下一日重叠。

无需先补齐逐条日志即可读取日报。日汇总接口不支持、验证码 / 认证 / 限流 / 超时、无有效金额、倍率历史缺口或日内变动、缺汇率、同一上游账号重复配置时，相关费用及利润为 `null`，供应商展开项列出原因。上游有效返回零可确认为零；上游已清理的历史数据无法靠此接口恢复。主站仍按原生日汇总核验明细，未接入的上游不在覆盖范围内。

需要配套更新运营中心与 Provider Monitor，复用现有地址、集成 Token 或管理员 SSO，不增加环境变量。监控 v34 自动增加独立日汇总快照表，按供应商 / 日期 / 时区覆盖写入，不修改原账本。当天缓存 60 秒、历史日缓存 1 小时，跨午夜重取上一日完整汇总；页面刷新按钮 / `refresh=1` 跳过成功缓存，上游失败短暂冷却 30 秒。查询只读上游汇总并保存监控快照，不触发模型、扣余额或补记账单。运营中心每次 `from=to`、报表内仅一次 SSO；单家或单日失败保留其他成功项，连续 3 次消费接口失败或全局错误会暂停后续请求，未知不作为零计算完整合计。

#### 目录、消费与汇率排查

供应商目录通过 `GET /api/integrations/providers` 获取，成本通过独立的 `GET /api/integrations/daily-costs` 获取；管理员 SSO 使用同契约的 `GET /api/daily-costs`。目录正常不代表上游汇总接口可用。每日成本参数为 `from`、`to`、`currency`、`timezone` 及可选 `refresh=1`，日期为闭区间自然日，响应必须为 `source=upstream_daily_summary`、`scope=account`；旧版监控返回账本来源会提示版本不兼容。页面“同步供应商”只刷新目录；每日消费按需读取上游账号汇总，Key 日志的截断状态不再决定该日报是否可用。

监控默认显示币种 `USD`、汇率仅 `{ "USD": 1 }`，向其请求 `CNY` 成本会返回 HTTP 400 / `CURRENCY_RATE_MISSING`。到供应商监控“设置与备份 → 运行设置 → 汇率（JSON）”补齐并“保存设置”；该项存储在监控数据库，不是运营中心环境变量。每项汇率表示“1 单位该币种等于多少显示币种”，转换为 `金额 × 源币种汇率 ÷ 目标币种汇率`。仅以 `1 USD = 5 CNY` 演示：保留 USD 显示币种时为 `{ "USD": 1, "CNY": 0.2 }`，CNY 显示币种时为 `{ "CNY": 1, "USD": 5 }`；生产应使用实际确认汇率并保留其他所需币种，充值倍率另外维护。

若所有标注 USD 的上游余额实际是人民币 1:1 购买的站内额度，应按该业务关系明确配置 `{ "USD": 1, "CNY": 1 }`，不使用市场美元汇率；供应商充值折扣 / 赠送依靠各自充值倍率另算，不能重复折算。

消费请求失败时，页面按错误码和 HTTP 状态提示具体原因：404 / 405 检查监控版本与代理路径，401 / 403 检查集成 Token 或管理员 SSO，格式不兼容检查是否收到 HTML 或旧版账本响应，连接失败 / 超时 / 5xx 检查网络与日志。不展示上游原始错误中的地址或凭据。单家上游失败、历史倍率缺口或汇率未核验在供应商明细说明，与整个监控接口不可用不同，均不以零成本计算利润。完整排查表见 [运营中心 README](../README.md#每日供应商消费不可用的排查)。

### 收支与余额口径

自动收入直接从 `redeem_codes` 单表读取，一条记录只会进入一个 `used_at` 日期桶，不与其关联的 `payment_orders` 再次相加，因此在线充值不会重复统计。只纳入具有金额含义的余额和管理员余额调整记录；并发、管理员并发调整、订阅和邀请记录的 `value` 不是可靠货币金额，全部排除。正数余额记录增加收入，负数余额记录冲减收入；未使用、禁用或过期记录没有实际使用行为，也不计入。`redeem_codes` 没有币种字段，自动收入统一归入 `CNY`；其他币种报表只汇总对应币种的手工收支，不自动换汇。该口径是余额入账代理口径，并不等同支付渠道现金实收；现金、退款和异常订单仍在“收款与入账”页单独审计。

### 自动收入复核

点击自动收入卡片后进入两级只读下钻：

1. 用户列表沿用成本分析当前的开始日期、结束日期和币种，按 `used_by` 汇总相同口径的记录，支持按邮箱、用户名或用户 ID 模糊搜索，并支持 20、50、100 条分页。
2. 用户详情按 `used_at DESC, id DESC` 稳定排序并分页，展示记录 ID、完整兑换码、`balance`/`admin_balance` 类型、备注、生成时间、使用时间和原始 `value`。

列表、详情和自动收入卡片共用 `status='used'`、`type IN ('balance', 'admin_balance')`、`used_at` 日期边界及 `CNY` 限制。用户和记录金额保留最多 8 位小数，时间按 `FINANCE_TIMEZONE` 显示，用户 ID 以字符串传输以避免 PostgreSQL `BIGINT` 在浏览器中丢失精度。软删除用户仍显示原身份并标记状态；`used_by IS NULL` 的记录归入“关联用户缺失”，可继续下钻，因此未搜索时不会因用户关联缺失而少计自动收入。搜索后的页头合计仅代表当前搜索结果。

以下余额变化不在管理员兑换页面的 `redeem_codes` 中，因此不会进入自动收入：创建用户时直接设置的初始余额、第三方账号首次绑定赠送余额、邀请返利转入余额。在线订阅支付也不生成兑换记录。若其中某项应按实际收款计入成本分析，需要在手工收入台账补录；邀请返利或赠送余额通常不是现金收入，无需补录，并会通过当前用户总余额影响实际利润。

`admin_balance` 只能证明管理员调整了余额，无法区分线下实收、赠送和纠错。当前按产品约定把它纳入自动收入，因此非实收调整需要结合备注人工核对。手工收入不会和兑换记录自动匹配；若同一笔线下充值此前已经手工录入，管理员加余额产生 `admin_balance` 记录后必须删除对应手工收入，否则总收入会重复。自动收入也不建立历史副本：Sub2API 对兑换记录采用硬删除，源记录被删除后，相同日期范围的历史自动收入会相应减少；管理员余额已变更但兑换记录写入失败时也无法自动识别，应根据 Sub2API 日志和余额记录人工核对。

用户总余额是查询时刻的当前快照，不按所选开始和结束日期回溯。余额表没有币种字段，因此用户总余额、实际利润和实际利润率只在 `CNY` 报表中计算；其他币种返回空值，避免跨币种误扣。软删除用户与 ID 1 管理员均不计入余额。

## 本地台账

`OPERATIONS_CENTER_DATA_DIR/cost-ledger.json` 是版本化、原子替换的 JSON 文件，权限为 `0600`。单进程写入通过队列串行化，收入和支出合计最多保存 50,000 条。部署时必须持久化 `/app/data`，并把该数据卷纳入运营备份。

手工收入记录包含名称、发生日期、金额、币种、备注以及创建/更新管理员和时间。新建收入和支出在页面上都默认使用 `CNY`，编辑时保留原记录币种。

支出记录包含：

- `kind`：`provider` 或 `custom`
- `providerId`：供应商支出使用的 Provider Monitor ID
- `name`：供应商名称快照或自定义支出项名称
- `date`：资金时区下的发生日期
- `amountMinor`：以百分之一币种单位保存的整数金额
- `currency`、`note`
- 创建/更新管理员和时间

供应商改名或删除不会改写历史支出的名称快照。相同自定义名称在成本构成中归为同一项。

台账版本从 v1 升级到 v2 时会在启动阶段自动添加空的手工收入列表，原支出、供应商快照和同步状态保持不变。升级无需新增环境变量或手工转换文件。

## 供应商同步

优先使用 `PROVIDER_MONITOR_INTEGRATION_TOKEN` 调用只读接口 `GET /api/integrations/providers`。未配置服务间 Token 时，运营中心可使用当前或持久化的 Sub2API 管理员 Token，通过 Provider Monitor SSO 换取短期本地会话后调用原有供应商接口。

同步失败会记录错误并继续返回上次成功快照。供应商支出只能绑定当前快照中存在的供应商；自定义支出不依赖 Provider Monitor。

## API

| 方法 | 路径 | 用途 |
| --- | --- | --- |
| `GET` | `/api/cost-analysis` | 返回区间汇总、周期序列和成本构成 |
| `GET` | `/api/cost-analysis/daily-profit` | 返回所选 start/end、currency 下的逐日真实收入、供应商拆分、核验状态和合计 |
| `GET` | `/api/cost-analysis/providers` | 返回供应商快照；`refresh=true` 强制同步 |
| `GET` | `/api/cost-analysis/incomes` | 返回日期范围内的手工收入台账 |
| `POST` | `/api/cost-analysis/incomes` | 新增手工收入 |
| `PUT` | `/api/cost-analysis/incomes/:id` | 更新手工收入 |
| `DELETE` | `/api/cost-analysis/incomes/:id` | 删除手工收入 |
| `GET` | `/api/cost-analysis/expenses` | 返回日期范围内的支出台账 |
| `POST` | `/api/cost-analysis/expenses` | 新增支出 |
| `PUT` | `/api/cost-analysis/expenses/:id` | 更新支出 |
| `DELETE` | `/api/cost-analysis/expenses/:id` | 删除支出 |

所有接口要求运营中心管理员会话；写接口额外要求 CSRF Token。金额必须大于零且最多两位小数，日期必须是真实的 `YYYY-MM-DD` 日期。

## 故障边界

- Sub2API 数据库不可用：报表查询失败，但已保存的本地台账不丢失。
- Provider Monitor 不可用：保留上次供应商快照，手工收入和自定义支出可继续维护。
- 本地数据卷不可写或台账文件损坏：拒绝启动或拒绝写入，不用空台账覆盖原文件。
- 供应商被删除：历史记录继续参与统计，新记录不能再绑定该供应商。
