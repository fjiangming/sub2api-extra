## 原因与修复

`ConversationPushStore.selection()` 在主 HTTP 进程同步查询 `cl_records` 的 fingerprint、处理版本、警告等字段，读取至 10,001 条后才检查单批 10,000 条限制。这些字段位于大型 original / masked BLOB 之后；即使不返回 BLOB 本身，SQLite 仍需遍历 overflow 页面。生产阻塞状态、源库 fd、持续大量读盘和超限数量与此路径吻合。事件循环被占用时，推送状态和健康接口同时等候，浏览器可能报网络失败；旧按钮只禁用，没有就近进度或错误，容易表现为无反应。

本地改造仅涉及运营中心：

1. 预览 / 入队只读轻量表，超过 10,000 条立即拒绝；用户仍需按日期、模型等缩小单批范围，不悄悄截取或遗漏数据。
2. 轻量表增补 fingerprint，保留原内容版本、预览 HMAC、投递 ID、格式及去重契约。启动只迁移结构，不扫描大型正文；新记录由现有触发器同步维护。
3. 旧 fingerprint 在原独立读取进程后台补齐，每轮最多 32 条 / 50ms 循环预算，按现有调度每秒续办，避让采集及交互读取。单条已开始的磁盘读取不能依靠循环预算立即打断，仍受独立进程超时与父进程抢占保护。源读取完成后才做条件更新，不在长写事务中读取 BLOB overflow；并发更新 / 删除 / 同 ID 替换优先。
4. 自动扫描遇到未准备数据暂停游标，已有任务暂停而不误取消；准备好的筛选子集可预览。任务列表改为轻量索引关联，准备期也保留既有任务。
5. 预览按钮下显示等待、准备、超限及错误；推送区显示历史准备进度，连接故障使用中文提示，轮询恢复后清除对应错误。

这不是对全部网络故障的零超时保证；共享磁盘和 SQLite 短写仍有成本。未修改主站或让推理等待预览，未提高内存 / CPU / 代理超时。旧历史的后台准备会发生一次有界、可让步的读盘。生效只需后续更新运营中心镜像，无新增服务器环境变量或 S3 配置。排查和实现阶段未提交 / 推送或部署；用户随后授权提交 GitHub，发布情况以对应工作流为准，服务器未更新。
