# 成本分析操作与统计口径

成本分析包含“消费毛利”“现金收支”和“供应商分组消费”，无需核验期初、分类旧账或设置核算起点。前两个视图默认资金时区当月一日至今天，趋势按日；可选上月、本年、自定义日期和日 / 周 / 月 / 年粒度。每日明细固定按日分页，长说明默认折叠。新增分组视图独立选择一天，按供应商的上游分组汇总同 Key 的多个主站账号及跨组消费，完整规则见[供应商分组每日消费](supplier-group-costs.md)。

## 消费毛利

| 指标 | 来源 |
| --- | --- |
| 主站消费 | `usage_logs.actual_cost`，排除 `user_id=1`，包含余额、赠送和订阅使用，保留已删除用户历史 |
| 供应商实际消费 | 启用定时检查的供应商账号日汇总，包含账号全部 Key，按该日历史倍率及有效汇率折 CNY |
| 当日抽奖所得 | 已使用的活动中心充值抽奖奖励，按 `used_at` 的资金日归集，排除 ID 1、未使用记录和普通充值 |
| 消费毛利 | 主站消费减供应商实际消费再减当日抽奖所得 |
| 消费毛利率 | 合计毛利除以合计主站消费，不平均每日百分比；分母不大于零时为空 |
| 本期充值额度 | 已使用 `balance` / `admin_balance` 的带符号 `value`，按 `used_at` 资金日筛选，排除 ID 1 |
| 当前用户余额 | 当前未删除、非 ID 1 用户的 `balance` 合计，附快照时间；不是所选期间期末余额 |
| 当前上游余额 | 监控最新启用账号快照、原币余额及已有倍率折算估值；不保证等于可退现金 |

点击五张指标卡可查看每日数据；日详情查看各供应商实际消费及来源状态。下方可切“每日明细 / 供应商汇总”，供应商行可直接记支出。充值额度支持用户分页、搜索及逐条兑换下钻，余额支持用户分页、搜索。

日详情的供应商行在刷新按钮旁增加“分组明细”，在同一侧栏展示该供应商当天的主站在用分组。四列依次为主站对应账号及消费、上游供应商分组、主站消费合计、供应商分组消费；展开账号查看跨主站分组的实际消费。同 Key 的多个主站账号累加，上游分组金额只计一次。每组预览最多 10 个账号，完整账号独立分页；表尾合计由服务端汇总全部在用分组，不因当前分组页或账号预览截断。

顶部“主站对应账号消费”包含名称已唯一定位该供应商的待分组账号；“供应商当日消费”沿用打开前的账号全天消费，可能包含主站未使用的上游分组，范围与表尾“在用分组合计”不同。待分组账号单列并支持完整分页，不混入在用分组合计；全天归属未核验、来源缺失和历史无归档保留明确状态或未知金额。返回按钮和 Escape 逐级返回，保留所选日期与分组页码，关闭按钮直接退出侧栏。

分组明细复用现有 `/api/cost-analysis/supplier-groups` 和原归档，不重新采集旧日或按当前关系补历史，不变更余额。已取得但未完整核验的分组金额显示“已知小计”，表尾汇总全部在用分组的已知金额；全未知保留“暂不可用”，不能把小计当完整合计或用于计算差额。历史归档与后续已知金额冲突时保留原值并明确标记。此次采集兼容与金额展示修复需同时更新 operations-center 和 provider-monitor；无新配置或数据库迁移，完整规则见[供应商分组每日消费](supplier-group-costs.md)。

充值额度不是现金收入，订阅用量也不是订阅售价。用户余额、供应商充值和其他手工收支均不加减消费毛利；充值抽奖所得是营销赠送成本，会在奖励发生的资金日从消费毛利扣除。服务器、域名、人工等费用尚未计入毛利。因此页面不将该指标称为经营净利润。

缺主站明细、上游成本或历史折算依据时，相应金额和整期毛利为空，同时展示标明天数的完整日期小计；已取得的单家供应商金额保留。认证、连接、限流或历史缺口显示来源状态，后台重试，不生成逐笔财务核验待办。辅助充值 / 余额独立加载，失败不会遮挡消费统计。

## 现金收支

第一行三张卡片为本期收入、本期支出、净现金流；第二行五张卡片依次为历史收入、历史支出、历史抽奖所得、当前用户余额、累计净结余。全部按人民币原数值计算：历史 100 USD 直接按 100 元人民币统计，CNY、其他币种及缺币种的记录也保留金额原数值，不做市场汇率换算。第一行按所选日期汇总；历史收入、历史支出、历史抽奖所得与累计净结余固定从资金时区 2026-10-01（含当天）统计至今，当前余额仍为实时快照。列表支持收支、来源、搜索及分页，这些列表筛选不改变期间合计。现金趋势与第一行使用同一来源，页面不再选择币种。

| 来源 | 现金处理 |
| --- | --- |
| 已使用余额兑换及管理员加余额 | 已使用 `balance` / `admin_balance` 按带符号 `value`、`used_at` 所属资金日自动计人民币收入，排除 ID 1；有效旧排除 / 非现金 / 未支付事实沿用 |
| 未使用及非金额兑换 | 未使用、并发、订阅、邀请等兑换的 `value` 不计金额 |
| 已关联兑换的支付订单 | 自动收入以已使用余额兑换的金额和日期为准；订单保留只读原记录，标明已合并，不再累加 `pay_amount` |
| 未关联已使用余额兑换的付款 | 有 `paid_at` 的有效已付款余额 / 订阅订单按唯一订单 ID、`pay_amount`、`paid_at` 补充一次，排除 ID 1；包括已付款尚未兑换 / 履约失败 |
| 退款申请、处理中或失败 | 原已收款保留；未取得实际退款金额与事件时不凭额度推算现金支出 |
| 线下 / 其他收入 | 已通过管理员余额兑换入账的收入自动取得，无需再记一笔；未有自动来源的其他实际收款支持简单记账 |
| 供应商付款 | 从监控目录选择供应商，按实际付款日记支出；停用不抹去过去付款 |
| 自定义支出 | 服务器、域名、带宽、短信、推广、手续费、人工等按实际付款日记一次，不摊销 |
| 实际现金退款 | 沿用旧账已保存的明确实际退款；新退款可简单记现金支出，来源单号 `refund:支付订单ID` 可消除对应原退款额度的不确定性 |

净现金流 = 本期收入 - 本期支出。自动收入采用用户确认的兑换入账代理口径，可能含赠送或优惠，不等同支付渠道实收。实付 100 获得 120 额度且已兑换时，计兑换 120，关联订单 100 不再相加。负向余额调整按原符号冲减兑换收入，不另造一笔现金支出。供应商充值是现金支出，上游实际消耗是消费成本，两种视图分别统计，不重复相减。主站 `refund_amount` 表示退款额度，不能按比例估算为实际退现金；对应实际金额缺失时相关现金净额保留未知。

补贴另建一条余额兑换，备注任意位置包含连续的“补贴”二字即可，例如 `补贴说明`、`故障补贴到账`、`余额补贴` 或 `[补贴] 故障补偿`。已使用的 `balance` / `admin_balance` 记录据此识别为零现金价值赠送，不计本期充值额度、自动收入、累计收入及用户充值下钻；关联支付订单也不能补回这笔收入。活动奖励继续沿用固定码和完整备注双标识排除。主站余额、原兑换金额、备注和运营来源快照全部保留；识别不改变已到账余额。不要求方括号或固定前缀，仅判断字面包含，因此 `不含补贴` 也会排除；空备注及不含该词的正常充值照常计入，充值和额外补贴应分别入账。

「余额（返利转入）」是 `affiliate_balance`，原生返利从 `user_affiliate_ledger` 的 `transfer` 流水合并展示；曾使用此类型的活动奖励回执也保留。充值 / 自动收入的 `balance` / `admin_balance` 类型白名单排除这些返利转入。新活动奖励使用兼容原主站的普通 `balance`、31 位固定码及“活动奖励补贴”完整备注，通过既有补贴识别排除本期 / 累计收入、充值额度和用户下钻，不需要修改主站或运营统计逻辑；历史无补贴备注的普通余额活动奖励继续按原长码和完整活动备注排除。主站即使同时增加余额和 `total_recharged`，也不会因此增加收入；当前用户余额仍保留全部实际到账部分。

“记一笔”默认支出及供应商付款，选择供应商、实际日期并填写人民币金额，无币种输入。支出不显示项目名称，按所选供应商自动命名为“供应商名称 付款”；自定义支出自动命名为“自定义支出”，用途可填备注。切换收入时显示并填写项目名称。来源单号和备注选填。修改历史支出时，收支类型及供应商未变则保留原名称。支持手工记录修改、确认删除，自动来源只读；不需要期初、分类、凭证核验或分摊。未来日期拒绝保存。

提交 UUID 防重，重试保持原请求内容，保存中禁用重复提交。填写的来源单号若与已有订单、兑换关联或手工记录一致会阻止新增；同金额但无单号的独立收付不会被擅自合并。后到的自动兑换或订单若匹配已有手工来源，只计一次贡献，原记录均保留并注明合并原因。订单与兑换通过原始来源 ID / 明确关联去重，不以金额、日期相似或用户相同猜测关联。

保存后自动切到对应日期并定位该记录，避免新增后被原筛选隐藏；可清空列表搜索查看全部。修改、删除立即更新期间汇总和累计净结余，审计保留操作者、时间和前后值。

## 累计净结余

`2026-10-01 起累计入账 - 2026-10-01 起累计支出 - 2026-10-01 起历史抽奖所得 - 当前用户余额`，起点按资金时区，包含 2026-10-01 当天。历史抽奖所得按活动奖励兑换记录的 `used_at` 汇总；当前余额仍排除 ID 1 和已删除用户。

当前余额明确只查询 `users.id <> 1 AND users.deleted_at IS NULL`，不直接修改任何余额。已删除用户发生过的收付和兑换历史仍保留，当前余额不再纳入；其他管理员 ID 按普通用户处理。

历史收入、历史支出、历史抽奖所得、当前用户余额、累计净结余统一人民币，位于本期卡片下方的独立第二行；不受日期、趋势粒度、记录搜索、收支或来源筛选影响。服务端在来源防重后按固定起点聚合，浏览器无需下载全部明细。点击收入 / 支出 / 抽奖所得 / 净结余查看累计组成、起止日期和快照时间，点击余额打开用户搜索分页。2026-10-01 以前的收支继续保留，仍可通过期间筛选查看；只是不进入这四项累计统计，无需修改配置或迁移旧账。

退款缺失按退款发生日判断：起点以前的退款不阻断当前累计；即使原收款早于起点，2026-10-01 起的退款仍须计支出，缺实际金额时累计保留未知。跨起点的订单 / 兑换先按原关联防重，再按承接收入的来源日期统计。

现金统一以原金额按人民币统计，不再应用 `FINANCE_CASH_EXCHANGE_RATES` 或旧汇率快照；该配置仅为历史环境兼容保留，新安装保持默认 `[]`，已有配置无需修改。升级不批量重写旧记录，原始币种及历史审计仍保留；新增或修改现金记录保存为 CNY。供应商实际消费的历史倍率和监控汇率继续按原规则使用。

全历史自动收款、历史抽奖奖励尚未同步、实际退款金额或当前余额缺失时，累计结果为空并显示原因；缺币种或旧现金汇率不再阻断统计。已知收支仍可查看，不把来源缺失当零。累计净结余是当前现金扣除已赠送抽奖额度和未消费余额后的结余，不表示本月经营利润。

## 历史兼容与自动运行

保留原数据卷及 `cost-ledger.json`、`daily-profit.sqlite`、`accounting.sqlite`，升级在原 SQLite 内非破坏性创建所需表；日报增加最近尝试状态，不清空快照或队列。旧手工收入、供应商支出、自定义费用按稳定 ID、原数值和付款日期延续为人民币统计，原始币种留档；旧有效非现金 / 未支付 / 重复标记与明确实际现金金额继续使用，迁移副本不再累加。旧分类、期初、政策、经营结果及审计不物理删除，新页面不再调用旧加权分摊引擎。

每日 01:00 归档昨日、今天实时、历史读本地。普通刷新不重算完整历史；漏跑、旧失败快照、历史缺口自动排入后台，失败退避重试。页面先展示归档再独立查询今天，今日超时不阻塞历史。重算失败保留最后完整结果及归档时间，最近尝试另存并按日展示；从未成功的日期保持未知。每批最多三天，单日整体计算有期限，超时让出工作器并继续其他日期。原作用域和日报唯一覆盖保持，旧日报不受核算起点或逐用户核算来源限制。日 / 周 / 月 / 年曲线均由同一每日来源合并；缺失日期断线。

按 `FINANCE_TIMEZONE` 的日历日期限制上游消费读取：除今天实时查询外，只允许当天 01:00 后首次归档前一天的消费。持久任务的 `fetch_supplier` 只由前一天的初始归档取得，失败后可在同一天自动重试；部分成功时只查询缺失供应商，已知金额和原供应商范围不变。跨日立即失去拉取资格，即使任务或读取器仍在重试也不能查询更早日期。原队列表自动添加字段，旧任务默认不授权，不清空快照。

显式 `recalculate=1`、旧版抽奖字段补算、其他历史重算及供应商详情刷新（包括昨天）都只复用已归档供应商消费，不创建监控会话或请求上游；仍可重新核验主站消费、抽奖所得并计算利润。强制重算清除原任务的上游拉取授权，普通轮询不能重新授予。共享读取器在认证前及发送请求前核验日期，默认禁止历史消费查询，避免未来新入口隐式回退到上游。例：11 月 25 日可首次归档 11 月 24 日，重算 11 月 24 日或更早日期只读原库；11 月 23 日及更早的首次缺口也只保留未知，需从备份恢复。已确认零值和部分成功金额保留，不补零。

### 历史消费恢复

上游删除明细后，接口可能成功返回零；旧版强制重算会把它当成有效消费覆盖快照，因此“接口成功”不保证历史数据仍完整。新版保护防止再次重查，不能凭空恢复已经丢失的正数。

优先核对原 `daily-profit.sqlite` 日报的供应商金额，再核对监控 `provider_daily_cost_summaries` 的原始汇总；两者都被覆盖时，需从升级前一致性备份或迁移前的数据卷恢复。按相同数据作用域、日期、供应商 ID 和上游账号身份逐项比对，修复被覆盖的零值或缺失值，保留现有主站消费、已核验抽奖、现金收支和用户余额，再重算利润及利润率；不能用上游余额差或估算金额冒充原消费。先备份现库、保留恢复前后记录，勿整库回滚而丢失新业务数据。SQLite 在线备份必须使用一致性备份 API；上游和所有备份都缺少历史时，该部分只能保留未知，不能认定没有成本。

现金订单和已使用余额兑换按 ID 分页、有界扫描，断点保存，后台每分钟同步并单实例合并并发。订单和兑换两种历史扫描均完成后才显示完整自动收入；来源缺失或只扫完部分兑换时保留已知小计，不把收入显示为完整零值。订单、兑换保留已同步快照，源站删除后不抹去旧事实；原记录更正按原 ID 替换，不追加第二笔。页面可见时自动刷新，离开停止轮询；历史同步期间今天仍至少每分钟读取一次实时消费。源记录在首次同步前已清理的历史无法恢复。

本次超时修复需配套更新运营中心与供应商监控，无新增运行依赖或必填配置。沿用主站只读连接、资金时区、监控地址和持久集成 Token。监控整份日汇总请求限时 8.5 秒、单供应商执行限时 5 秒，排队和串行等待同受整体期限限制，单家失败保留其他供应商结果；底层 HTTP 期限包含 DNS、重试退避、重定向与响应体。Sub2API 用 `total_actual_cost`，New API 用消费 `quota / quota_per_unit`，不按 Key 日志重复相加。连接、CMD Token 和监控折算配置见 [README](../README.md#供应商同步配置)，现金统一人民币不改变监控折算规则。

SQLite 使用 WAL，备份请用一致性备份 API，或停服务后备份完整数据目录，不能只复制运行中的主库。

## API 与验证

所有新接口沿用运营中心管理员会话，写入需 CSRF，现金接口为 `no-store`：

- `GET /api/cost-analysis/daily-profit`：自动消费、归档、完整日期小计及趋势。`live=0` 仅读归档与内存中的今日快照，今日行标记 `liveRefreshing`，不启动实时请求；不带该参数则查询今天。普通 `refresh=1` 不重算完整历史；维护用 `recalculate=1` 才显式排入所选历史重算。行级 `lastAttempt` / `archiveStatus` / `nextAttemptAt` 表示最近更新及重试状态，`computedAt` 仍为保留结果的计算时间。

供应商详情的 `POST /api/cost-analysis/daily-profit/provider-refresh` 对所有历史日期（包括昨天）返回 `reused=true` 及原值，不请求上游；没有该日报或供应商历史归档时分别返回 `DAILY_PROFIT_NOT_ARCHIVED` / `PROVIDER_NOT_ARCHIVED`，需等待首次归档或从备份核对，不能新增一笔零消费。只有今天执行实时刷新。

- `GET /api/cost-analysis/automatic-income/users` 和 `/users/:userKey/records`：持久兑换来源下钻。
- `GET /api/cost-analysis/cash/report`：统一人民币的期间汇总、趋势、筛选分页及独立固定起点累计；`cumulative.from` 为 `2026-10-01`，`cumulative.to` 为资金时区今天，累计明细数量与金额也按该范围；旧 `currency` 参数不再拆分数据，响应固定 CNY。
- `GET /api/cost-analysis/cash/balances`、`/provider-balances`：独立当前快照。
- `GET /api/cost-analysis/cash/records/:key`：只读原记录和变更历史。
- `POST /api/cost-analysis/cash/records`、`PUT /records/:key`、`DELETE /records/:key`：简单记账，币种统一保存为 CNY，兼容旧客户端的币种字段且金额不变；自动记录禁止改删，手工删除留审计。

旧 `/accounting/*` 和旧收支 API 为兼容与历史保留，不用于新页面核算。运行 `npm test`、`npm run check`；`npm run preview:accounting` 启动本地模拟主站 / 上游及真实 SQLite、PostgreSQL 兼容读源预览。`npm run check:accounting-ui` 需要 Playwright，支持 `PLAYWRIGHT_MODULE_PATH`、`PLAYWRIGHT_CHROMIUM_EXECUTABLE`，验证桌面、390px、320px 和系统深色偏好下的交互、图表与布局；不连接生产。
