## 资源异常：可回收缓存压低了处理预算

`conversation-archive-worker.js` 当前计算方式为：

```text
available = min(host_free, cgroup_limit - cgroup_current)
budget = max(0, min(available - 32 MiB, heap_free - 32 MiB))
maxOutputBytes = min(256 MiB, floor(budget / 8))
```

cgroup_current 包含可回收文件缓存。SQLite 读写会将缓存推近 512 MiB 容器额度，上述公式不区分匿名内存与可回收缓存，再扣 32 MiB，处理预算可能落到 0 或数百 KiB。一次无诊断 Node 的采样对应输出预算约 0.27 MiB；独立进程采样时也观察到预算会落到 0。没有观察到 OOM 杀进程。

对样本中 **10 条资源异常**使用同版处理代码、明确的 8 MiB 诊断预算重放，结果为：

- **8 条处理成功**，其中 2 条保留协议签名检查警告。
- **2 条进一步暴露 encrypted_content 不兼容**。资源保护是较早的失败点，解除资源压力后仍需处理协议兼容。

没有把诊断结果写回原记录。历史没有保存当时的瞬时预算，不能为每条历史资源异常精确复原内存值；但当前预算公式、内存构成和同原文重放共同指向资源判定过于保守。

建议优先修正运营中心的预算估算：区分匿名 / 不可回收内存与可回收的干净文件缓存，继续保留 V8 堆、外部 Buffer、容器水位和任务体量限制。暂时资源压力应保留原文并进入限速后台待处理；分别记录资源压力、解码预算、已学习敏感值数量上限等错误原因。不能仅删除资源保护或无限提高上限。资源增配可以缓解，但不是修正判断逻辑的替代方案。

## 内容异常：两个新兼容缺口

5 条 UNINSPECTABLE_CONTENT 的具体触发为：

1. **4 条 GPT Responses 加密推理**：`response.output_item.added` 中，`item.type=reasoning` 的 `item.encrypted_content`。另有前述 2 条资源异常在重放时命中相同结构。v3 目前只放行确切位置的 Claude / Gemini 协议签名，encrypted_content 仍被全局拒绝。
2. **1 条工具 JSON 的 file_id**：位于嵌套 JSON 数组对象中，值为数字字符串，未见已识别的媒体类型；仅因字段归一化为 fileid 就触发全局拒绝。需要结合所在协议位置判断其是否为真正的文件引用，不能只靠字段名或值格式放行。

建议在运营中心扩展协议适配：

- OpenAI Responses 的确切 reasoning / encrypted_content 协议位置原样保留加密值和关联字段，继续处理可读文本，独立提示“加密推理内容未检查”，保留加密原文。
- 正常工具结果中的业务文件标识按上下文和敏感信息策略做一致性替换；真正的外部文件、媒体和其他不透明内容继续明确提示检查范围，不主动抓取外部资源。
- 保持已有默认外推门禁：含未检查内容的脱敏副本不能自动作为已匿名化内容对外发送，也不隐式改发原文。
- 适配必须限定协议路径，覆盖请求、普通响应、SSE、WS 及嵌套 JSON 的负例，保留原有字节、帧和顺序。不能全面忽略同名 encrypted_content / file_id 字段。
