# 错误分析 Tab 设计与接入方案

状态：2026-11-02 用户确认开发，默认日期已由近七日改为今天，正式 Tab 和只读接口已实现，尚未部署。原 demo 保留为设计参考，正式接入范围与限制见下文。

## 目标与入口

在现有运营中心“慢请求”之后新增“错误分析”一级 Tab。按天分析主站错误，默认今天，保留昨天与近七日快捷筛选，今天标注实时截止时间；从每日概览进入“分组 → 供应商 Key → 请求链路”，同一筛选范围支持按用户统计。核心问题是辨认一次主站请求最后向下游写出了什么，以及其间哪些失败被自动重试恢复。

参考会话：[分析502重试与下游最终响应](codex://threads/01a19a81-ab42-70b1-b4b7-d9fe6f3e6a6e)。该话题确认了 HTTP 200 下的 SSE 失败、先 502 后恢复、上游 403 映射下游 502、重试后路由无账号等情况。原话题的 52 条来自 11-01 12:30 至 11-02 12:30 的跨日窗口，不能直接填进某个自然日；demo 使用独立确定性模拟数据，不伪称生产日报。

## 当前实现与接入边界

正式页面默认今天与下游最终失败类型，可按分组、供应商筛选，按十二类失败下钻分组 / Key、用户、分页请求与完整尝试链。期间总计和单日明细独立，跨 Key 与用户去重、稳定类型占比、原因 × 全结果对照沿用本方案。正常非流式响应不要求 SSE 结束事件；流式恢复必须有下游完整响应和正常终止、完整失败 / 成功尝试链；证据不全不推断恢复。

已实现的管理员只读接口合并为 `GET /api/request-errors/options`、`GET /api/request-errors/report`、`GET /api/request-errors/requests/:id`，统一返回汇总、每日、类型、分组 / Key、用户 / 请求分页与原因矩阵。参数使用 `start/end/day/groupId/providerId/scopeGroupId/keyId/userId/search/outcome/failureType/cause/view/page/pageSize/refresh`，默认今天，最大 31 天，每页最多 50 项。接口复用现有管理员会话和 no-store，不存在重试、重发、解决标记或资金写入操作。

主站读取使用既有只读 PostgreSQL 连接和 repeatable-read 快照，每批最多 10,000 条；查询前一天的边界并补取同一可信根请求在所选窗口外的后续错误，最终按根请求开始日归属。主站表缺失、来源异常与真实零数据分别呈现。读取截断明确标为部分数据；数据库切换时拒绝旧响应，失败不入缓存，同范围并发合并，事实缓存 10 秒。当日页面每分钟刷新，离页中止；历史查询不自动轮询。不新增依赖、必填配置或错误分析数据库，不恢复已撤除的日志挂载；历史覆盖仍受原有错误日志和遥测保留期限制。

可信身份只采用本地采集中的直接主站根 ID，不使用客户端 / 上游别名；用户必须一致。新采集有用户 Key ID 时一并核对，旧采集无该字段时保留错误表中的 Key ID 并检查同请求各记录身份一致，冲突保留待判定。缺直接根身份的错误逐条保留待关联，不混入准确去重请求和已确认失败总数。旧采集只有实际错误 HTTP 状态、响应写出及非 PANIC 的错误结束时才能确认 HTTP 失败。

**完整结束协议的接收、分类及配套主站采集模板均已实现，需要同时合并主站采集才能取得新的终止证据。** 新模板在现有写出之后检查有界协议元数据，发出 `request_end.resultVersion=1`、实际 HTTP、正常终止 / 完整写出、错误事件、客户端断开及准确 HTTP 尝试总数；读取用户 / 用户 Key / 分组 ID，不导出正文或凭据，不改变响应字节、HTTP 状态或自动重试策略。支持 Anthropic Messages、OpenAI Responses / Chat Completions 的标准结束与错误；未支持协议、超大 / 非法事件或观察不全保持未知。已完整观察的标准下游流在处理结束时缺必需终止符可证实提前断流；单独的上游 terminal=false 仍不是依据。即使主站未写错误表记录，可信终止采集的异常也可单独统计，错误日志行数仍为实际零条。

本轮没有自动修改现有主站工作区或部署。仅更新运营中心不能完整还原旧请求的恢复或 HTTP 200 流内失败；旧采集无相应证据时保持待判定 / 待关联，页面提示缺口，`Recovered upstream error`、HTTP 200、resolved 和用量不单独证明成功。隔离预览明确使用模拟数据，不代表生产已具备采集覆盖。配套测试通过 Go overlay 与本地真实主站类型编译 / 运行，既有安装工具只在用户显式 --apply 且所有锚点 / 目标检查通过时写入；已有插桩需按实际版本合并，不能重复覆盖。

供应商监控新增 Token / 管理员 SSO 保护的只读 `request-error-mappings` 接口，从既有 `sub2api_mapping_history` 读取账号 / Key 有效区间，删除的供应商 / Key 保留 ID。每次尝试按自身时刻映射，缺尝试时间时回退请求时刻；冲突、缺区间、监控不可用或映射读取截断时保留未映射。别名显示当前名称并明确标注，不冒充历史名称快照。正式接入此映射需要供应商监控同时具有该接口，旧版仍可分析主站账号，不会触发上游同步或测试推理。

本地预览：在 `operations-center` 执行 `npm run preview:request-errors`，默认 `http://127.0.0.1:19892/preview`，端口占用时顺延；只含隔离 PGlite 和模拟遥测。`npm run check:request-errors-ui` 使用 Playwright，可通过 `PLAYWRIGHT_MODULE_PATH` 与 `PLAYWRIGHT_CHROMIUM_EXECUTABLE` 指向本地现有运行时，不安装生产依赖。`npm run check:request-error-telemetry -- E:\path\to\sub2api` 使用 Go overlay 验证采集模板，不改主站文件；标准库包正常运行 vet，Windows 虚拟目录的 middleware overlay 单独关闭 vet 后运行测试。配套测试覆盖真实 PostgreSQL SQL、旧采集回退、终止证据 / 身份冲突、跨日迟到、Key 变更 / 删除 / 歧义、供应商失败尝试、来源故障与恢复、截断、缓存切换以及管理员鉴权。

## 下游最终失败的细分

用户进一步反馈：原版只区分 HTTP / 流式失败，不能清楚说明下游究竟遇到哪种错误。新版默认打开“下游失败类型”，期间首卡改为“下游最终失败”，单日默认筛选已确认失败；每日概览折叠保留，分析日可以独立选择。下表是已确认失败请求的互斥细分，不能用上游某一次尝试报错直接填入。

| 最终失败类型 | 确定归类的证据 | 下游实际表现示例 |
| --- | --- | --- |
| 供应商余额不足 | 明确 `insufficient_balance` 等余额错误；不能只凭 403 | 上游 403，最终下游 HTTP 502 / 错误响应 |
| 上游 Key 无效 / 无权限 | 上游认证 / 权限的结构化错误，确认责任归属上游 | 上游 401 / 403，最终下游 HTTP 502 等 |
| 上游限流 | 上游 429 / 限流代码，最终没有恢复 | 最终 HTTP 429 / 503，或明确的流内限流错误 |
| 上游服务故障 | 最终相关上游服务异常，重试状态独立记录 | 上游 5xx，最终下游 HTTP 502 等 |
| 无可用账号 / 切换失败 | 最终路由结果为无账号，包括前序失败后耗尽 | 下游 HTTP 503；可有零次上游尝试或多次尝试 |
| 连接 / 首响应超时 | 明确连接 / TLS / 首响应阶段超时 | 下游 HTTP 504 等，尚未正常输出内容 |
| 本站参数 / 权限 / 限额拒绝 | 本站校验或额度 / 并发限制代码；用户 Key 与上游 Key 区分 | 下游 HTTP 400 / 401 / 403 / 429 等 |
| 流内错误事件 | 下游已写出 `error` / `response.failed`，未定位更具体原因 | HTTP 200 + 流内错误，可能已有部分输出 |
| 输出中途超时 | 已开始输出，明确流间隔 / 输出阶段超时和下游失败证据 | HTTP 200 + 超时错误 / 已证实的流中断 |
| 响应提前结束 / 缺正常结束 | 已证实下游响应非正常结束，或网关因缺结束事件写出错误 | HTTP 200 + SSE 错误；也可能无错误事件但已证实提前断流 |
| 网关处理 / 响应转换异常 | 网关处理阶段异常并确认最终下游失败 | HTTP 500，或流建立后的转换错误 |
| 已确认失败 · 原因未明 | 下游错误 / 异常终止已确认，缺细分根因 | 已记录 HTTP 500 等，仍计入下游失败 |

最后一类与“待判定”不同：前者知道请求失败，仅根因未知；后者连下游最终结果都无法确认。上游仅 `terminal=false`、没有下游结束证据的请求仍是待判定，不能直接归入“响应提前结束”。已证实下游提前断流但未发出错误事件时，展示“提前断流 / 无错误事件”，不能声称客户端收到 SSE 错误。

最终主因按终止证据确定：最后是路由耗尽就归无可用账号，前面的 502 留在尝试链；明确余额 / 认证 / 限流 / 超时 / 转换代码优先于通用流内错误或中断。只有无法细分时才使用通用类型。传输表现（HTTP 错误、流错误、提前断流）、是否已经输出、最终上游原因、重试情况分别保存。同一类型可以对应不同下游状态，不写死“403 必然映射 502”或“某类型必然未输出”。有冲突时保留冲突证据，不强分根因。

类型表逐行展示：失败类型与阶段、下游实际 HTTP / 错误事件、去重失败请求数、占同日同范围失败请求的比例、重试后仍失败数、未重试 / 重试未知数、受影响用户。类型点击进入分组 / Key，失败数进入请求，用户数进入该类型的用户列表；所选失败类型在下钻中保持。分组 / Key 行与用户列表同时显示主要失败类型构成；用户详情保留完整类型分布，避免只展示总失败数。

“重试后仍失败”是独立维度，不是一个错误根因。必须有同请求多次尝试的可靠证据；是否重试次数耗尽、切换 Key 后失败、输出后未重试另行展示，不能凭多个错误行推断重试次数。所有互斥类型的请求数与下游失败总数对平；类型人数独立去重，不相加充当总受影响人数。占比的分母固定为同日、同分组 / 供应商 / 用户 / 来源等范围的全部确认失败，不随选中单个失败类型缩小为 100%，也不是全站错误率。

## 结果与触发原因

错误原因与最终下游结果独立保存，不把“重试成功”当作错误原因。列表以主要原因形成互斥分类，同时保留所有尝试的多种原因、阶段、原始状态和归属。

| 主要错误原因 | 举例 | 归类依据 |
| --- | --- | --- |
| 上游拒绝 | 401 / 403、429、余额不足、内容拒绝 | 结构化上游错误码 / 阶段；HTTP 状态不足以推断细分原因 |
| 上游服务异常 | 上游 500 / 502 / 503 | 实际上游响应，不能拿网关映射状态当上游状态 |
| 中途响应失败 | 缺结束事件、读流失败、连接重置、响应转换失败 | 是否开始输出、失败阶段及协议结束状态 |
| 连接 / 超时 | DNS / TLS / 拨号 / 首响应 / 流间隔超时 | 明确阶段；不是所有 600 秒都认定同一根因 |
| 本站校验 / 路由 | 参数 / 认证 / 并发限制、无可用账号、内部错误 | 平台自身事件，未发起上游时无供应商 Key |
| 其他 / 原因未知 | 历史字段不足或不支持的协议 | 不凭自由文本猜测确定原因 |

最终失败优先用最后导致终止的原因；重试恢复用首次触发重试的原因。详情显示整个因果链，不能把同请求前一次 429 当作后一次流中断的原因。

| 最终结果（互斥） | 必要证据 | 是否计入已确认下游失败 |
| --- | --- | --- |
| 重试恢复 / 下游未报错 | 同一服务端请求存在失败尝试；最终有效正常终止、完整响应及下游成功写出；没有后续错误写出或断开 / 冲突证据 | 否 |
| HTTP 失败 | 同请求的最终下游 HTTP 错误响应已写出；保留独立的上游状态 | 是 |
| 流式失败 | 流建立后错误事件已写出，或可靠记录明确下游流未正常完成；HTTP 可能仍为 200 | 是 |
| 客户端断开 | 明确客户端断开，且没有足够的错误写出证据认定上述失败 | 单列，不计成功或已确认错误返回 |
| 待判定 | 未完成、缺结束记录、关联不唯一、来源冲突、上游完成但缺下游写出证据等 | 单列，不当零或成功 |

明确的错误写出与后续客户端断开同时存在时，错误结果优先，断开事实作为独立字段保留。互相矛盾或无法确定先后的证据转待判定。仅有 `terminal=false` / 缺 terminal 字段不证明错误已向客户端写出；需区分“上游未完成”和“下游已写出错误”。“下游返回”表示网关写出的结果，不保证网络另一端实际完整接收。

`Recovered upstream error`、`resolved`、`ops_retry_attempts.status=succeeded`、HTTP 200、`usage_logs` 存在或资金已结算均不能单独证明原请求成功。人工标记已解决和管理员事后重发不改写原请求的结果。流式失败即使已有部分 / 完整用量或计费，也仍按下游证据分类。

## 页面与交互

1. 顶部筛选：开始 / 结束日期、分组、供应商；今天、昨天、近七日。首版最大 31 天，日期按现有用量时区配置，demo 为 Asia/Shanghai。
2. 四项期间概要：下游最终失败（HTTP + 流错误 / 中断及受影响人数）、重试恢复、异常请求（附错误记录数 / 失败尝试数）、其他 / 待判定（断开与未知分别展示）。保持所选期间的汇总，明细中的筛选不改变期间数字；标题、辅助文案标清期间与单日。
3. 每日概览：一日一行，展示异常请求、四类结果分布、HTTP / 流式拆分和受影响用户。选中行进入下方单日分析，今天显示截止时刻。跨日比较以条数展示；没有全请求分母时不计算成功率 / 错误率。
4. 单日四视图：默认“下游失败类型”，另有“分组 / 供应商 Key”“按用户”“请求明细”，共享用户 / 请求 ID 搜索、下游结果、失败细分和错误来源筛选。分组可折叠 / 展开 Key；数量可下钻至匹配请求。请求 / 用户分页，切换筛选回第一页；空数据和读取失败分别展示。
5. 默认失败范围下，分组 / Key 展示最终失败请求、实际失败尝试、重试后仍失败、HTTP 错误、流错误 / 中断和受影响用户，附主要失败类型构成；用户列表显示失败类型及重试结果。切到全部结果时保留恢复 / 断开 / 待判定对照，恢复请求不能进入最终失败细分。
6. 请求详情：用户、用户 Key ID、请求分组、请求 / 上游模型、实际 HTTP、持续时间、所有上游尝试与同 Key 重试 / 切 Key、下游流错误 / 正常结束、完整性 / 断开 / 用量辅助事实、证据引用与不足原因。用户 Key 与供应商 Key 明确分列，供应商凭据只显示别名 / 脱敏标识。
7. 错误原因 × 下游结果折叠表，查看同一种上游错误最终有多少恢复、多少失败；沿用同日、分组 / 供应商 / Key / 用户搜索 / 来源范围，但忽略明细下游结果与失败类型筛选，明确标注“同日全结果”。不能因默认失败筛选把重试恢复伪装成零；点击计数清除失败类型并切换到对应结果的请求。统计口径帮助集中展示规则。

## 计数、归日与 Key 归属

- 主单位为一次主站请求，内部自动尝试不增加请求数。独立保留 `error_record_count`、`failed_attempt_count`、`upstream_attempt_count`、`same_key_retry_count`、`key_switch_count`，不使用一项含糊的 retry_count 覆盖所有语义。
- 可靠服务端请求 ID + 数据源作用域 + 用户 / API Key / 请求身份一致性是聚合依据；客户端自带 request ID、相似时间 / 模型、同一用户不能合并。客户端收到失败后新发的请求有独立结果，不能把前一次失败改为恢复。缺可靠请求 ID 的错误按源 ID 单列为待关联，并明确去重不完整；不混入“已准确去重请求”合计。
- 日期使用可靠主站接收时间，在已配置时区划分 `[当日零点, 次日零点)`。跨午夜的所有后续尝试 / 完成归到原请求日；起始时间缺失回退最早可靠错误时间并记录 `day_basis=first_error`，不能把回退值冒充接收时间。
- 读取所选日的原请求集合后，按这些可靠 ID 补取窗口外后续事件；更新请求原日。不能仅按错误 created_at 截断尝试，也不能将跨日同请求重复计入两天。
- 分组取该请求历史有效的请求 / 售卖分组，不从最终账号或当前用户默认组推断。历史被删分组与用户保留 ID / 快照；缺身份单列，不静默丢弃。
- Key 行采用“接触该 Key 的请求及其最终结果”。同一请求跨 A、B Key 重试恢复时，两行各显示一次该请求的最终恢复；失败尝试只归实际失败 Key，成功接管 Key 可显示零失败尝试。分组、用户、期间、每日合计均直接按根请求去重，不加总 Key 行。UI 固定注明这个非可加性，避免将恢复结果误作该 Key 自身成功率。
- 供应商筛选同样按接触关系纳入请求；选 A 后结果来自该请求完整链路，仍可能由 B 恢复。详情必须保留完整链路；Key 行只展示当前供应商范围，失败尝试计数仅包含该供应商实际失败的尝试，不把其他供应商的失败归给它。
- 主站 account_id 不是天然的供应商 Key ID。使用 provider-monitor 已有且在请求时刻有效的账号 / Key 映射；只有验证后才展示供应商 / Key。缺历史映射显示“主站账号 #X · Key 未映射”；未请求上游显示“未到上游”，不归罪某家供应商。当前改名不能覆盖历史身份；本版不读取或导出真实 Key 字符串。
- 受影响用户 = 已确认 HTTP / 流式失败请求中的去重 user_id；只有恢复的用户不计影响，断开与未知用户单列。每日人数不可直接相加作为整期人数；零分母为 `null`。
- 本页展示所有运营错误，默认不因资金模块的 ID 1 排除规则漏掉管理员测试流量；正式版可选择排除管理员，必须同步所有计数与证据筛选。demo 没有管理员样本。

## 现有数据与缺口

| 来源 | 复用信息 | 接入限制 |
| --- | --- | --- |
| `ops_error_logs` | request / user / api_key / group / account、stream、状态、阶段、结构化 upstream_errors | `status_code` 在流式失败时可能是语义映射值；不能冒充实际 HTTP。同请求可能多条记录，上游尝试数组和其他来源须按 attempt ID 合并，缺 ID 不能靠状态码相同去重 |
| 核心原生持久上游尝试 / 恢复案件（通过现有管理员客户端） | dispatch / attempt ID、HTTP、observation、terminal / complete、断开、可信上下游关联 | 上游响应完整不等于下游完整；已 settled 仍不能证明客户端得到成功。仅持有部分案件不声明全站覆盖 |
| 主站已有结构化最终响应 / 访问事件 | 实际 HTTP、同服务端 ID 的 forward_failed、最终流错误与完成事实 | `http.access=200` 不单独证明成功；没有 request ID 的 Nginx 按秒 / IP / UA 近似匹配不作为自动确定关联 |
| 现有 `usage_logs` | 请求 / 用户关联与记录的用量 | 只作辅助；失败可能已记录部分用量，不与错误行直接相加成全请求分母 |
| provider-monitor 历史映射 | 供应商别名、主站账号和供应商 Key 的已验证关联 | 不用当前 Key 名猜历史归属，不同步模型或发测试推理 |

当前 `SchemaInspector` 识别 `ops_error_logs`，尚未提供本页只读聚合接口。现有 `BillingImportLogs.sanitizeLogEvent` 会有意丢弃错误 / 重试 / 流终止字段，不能直接拿它作为本功能判定器。若需要文件来源，在运营中心新增有界、白名单、脱敏的错误元数据读取器，复用可靠的文件 / gzip / 边界检查，不改变资金匹配读取器的含义。

本仓库维护台账已记录 10-30 撤掉历史 CSV 日志挂载；不能假设生产仍有可读取日志目录。首版先核验现存主站数据库 / API 的字段与覆盖，无结束证据时展示待判定。如需只读结构化日志挂载，列为后续用户部署时确认的实际接入条件；本轮不新增配置或自动恢复旧挂载。

如果现有来源不能稳定证明下游错误 / 正常完成，应将最小下游结束遥测列为独立后续方案，等待用户确认后再评估核心改动；不能仅为了让报表没有未知而发明历史字段或解析整段用户正文。本轮不承诺“只升运营中心就能完整判定全部历史”。

## 确认后的实现划分

所有分析仍在既有 operations-center 进程，不新建运营服务，不触发计费恢复 / 重发 / 扣费。

| 计划文件 / 位置 | 职责 |
| --- | --- |
| `src/services/request-errors-source.js` | 只读有界读取、schema / 字段能力探测、可靠关联与脱敏元数据 |
| `src/services/request-errors-classifier.js` | 纯函数建立根请求 / 尝试链、最终结果 / 原因、证据冲突与完整性 |
| `src/services/request-errors-service.js` | 日 / 分组 / Key / 用户汇总、分页、筛选、短缓存及请求失效隔离 |
| `src/app.js`、`src/server.js` | 既有管理员会话、只读数据库池与客户端注入；所有 API no-store，不复用资金写接口 |
| `public/request-errors-ui.js`、`public/request-errors.css`、`public/index.html`、`public/app.js` | 新 Tab、页内状态、筛选、下钻、详情与离页清理，沿用 Lucide / 既有组件模式 |
| 同模块原数据卷中的 `error-analysis.sqlite`（需要长期保留时） | 保存最小脱敏请求事实、每日派生结果、来源覆盖和分类器版本；待确认后实施，不保存正文 / 密钥，不成为资金账本 |

拟定接口为 GET `/api/request-errors/summary`、`/days`、`/failure-types`、`/groups`、`/users`、`/requests`、`/requests/:id`。统一 `start/end/timezone/group_id/provider_id/user_id/outcome/failure_type/cause`，分页使用稳定排序与游标；请求 ID 参数校验并固定数据源作用域。返回 counts、独立 distinct totals、稳定分母、归日 / 映射基础、source capabilities、coverage、generated_at、classifier_version，不能在截断读取时给出完整总计。事实记录分别保存 `failure_type`、`delivery_kind`、`output_state`、`retry_state` 及证据，不把重试耗尽当作上游错误类型。

今天按查询短缓存、同筛选并发合并；已结束日持久化前需要来源覆盖完整且在途请求已收敛，迟到证据按原日重算。缓存 / 归档应含源身份、时区、规则版本和数据版本，不能跨管理员 / 数据源混用。受控分页、查询超时与后台进度用于大数据日，不在打开页面时扫描所有历史文件；某源缺失保留其他可证实结果，同时明确未覆盖范围。历史源已被清理不能自动恢复。

在没有“包含无异常的全部请求”的权威来源前，不展示全站错误率、重试恢复率占全请求等指标。如果展示恢复占比，分母只能明确写“已确认结果的异常请求”，同时列未知条数；第一版 demo 以数量为主。

## 验收重点

确认后后端测试覆盖：同请求多行 / 多次尝试去重；上游 502 后同 Key 恢复；切 Key 恢复与不可加合计；403 → 502；HTTP 200 + SSE 错误；只有 terminal=false 时不凭空认定错误返回；存在用量仍失败；客户端断开；缺 / 冲突 / 迟到证据；客户端复用 ID 与新请求不合并；跨午夜归日；未到上游 / 未映射 / 删除身份；来源截断 / 表缺失 / 日志未挂载；只读 SQL 与管理员访问边界。

正式版浏览器验收覆盖期间与单日范围一致、用户去重人数、各结果与原因筛选、分组 / Key 下钻、搜索 / 翻页、详情链路与返回、零数据与来源不可用状态，以及 1440 / 1024 / 390 / 320px 和深色布局。本轮只做 demo 交互和设计验证，不将其视为业务功能测试。

新版另验收十二类失败与总失败数对平、具体根因只取终止原因、已确认原因未知与结果未知隔离、输出中超时与连接超时区分、无错误事件但已证实的提前断流、重试与类型不混淆、占比分母不随单类型下钻改变，以及失败类型 → 分组 / Key → 请求 / 用户链路保持筛选。

最初 demo 位于当前会话可视化目录 `request-error-analysis.html`，默认今天，只含确定性示例，无主站 / 上游网络请求。上述原方案中尚未落地的长期归档与正式生产接入不应理解为已部署能力；当前实际接口和范围以本文“当前实现与接入边界”为准。
