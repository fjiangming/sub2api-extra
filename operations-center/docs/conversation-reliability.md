# 对话优先的采集与持久接收

此改造优先保持正常对话，减少可避免的收尾丢字节和投递失败。它不能承诺零开销、上游永不断流或所有请求均有归档。本地实现不表示服务器已经更新。

## 数据经过的阶段

1. 主站沿原转发路径复制实际观察到的字节，不重发推理，不在主站写磁盘暂存。用户返回路径不等待归档或上游 EOF。
2. 在已知终态的实际结束位置，或关闭 HTTP 错误响应时，满足条件才接入受限后台补读；最多同时两条，每条总计 1 秒、空闲 200ms，原生在途 Read 退出后才读取剩余原始字节，压缩响应也不重新编码。同一上游客户端有新请求时立即取消旧补读，旧前台响应仍照常读取，但不再补读。已取消、请求未收全、已有读取错误、封装不支持或资源不足时沿用原关闭。普通 Close 的在途读取 / WriterTo 仍在独立 finalizer 最多收尾 250ms，之后迟到数据不改写已封存日志。没有并行读取同一 body 或新增通用读取泵。
3. 后台发送按原 ID、原 envelope 与摘要投递；最多三次，失败后分别退避 500ms / 2s，期间可先发送其他日志。补读、待收尾、待发送和重试共用 32 项限制及 64 MiB 观察预算；每条补读的 16 KiB 临时缓冲也计入，不各自扩容。
4. 运营中心的独立接收进程校验输入、当前 / 采集时策略、用户 / 模型和原文字节摘要，将 AES-GCM 原文、紧凑元数据及待处理任务在同一 FULL 同步 SQLite 事务提交，之后才返回匹配 ID / 摘要的 ACK。此时不做脱敏或完成事件解析。
5. 独立处理进程从持久任务取出原文，检查完成证据、按当前规则处理，在短事务内复核规则、用户 / 模型 / 保留期、容量、记录和任务代次，发布完整副本与处理状态。接收可以在另一条日志处理期间继续；写 SQLite 的短事务仍会互斥。

原文模式仍保留原文；双副本模式发布脱敏副本并保留原文；仅脱敏模式在待处理阶段也暂存加密原文，只有成功且没有未检查内容时才移除。格式 / 隐私检查 / 内存 / 副本空间异常时保留原文，显示固定错误码，可手动重新处理。明文不会落入新暂存文件，沿用既有 archive.sqlite / archive.key，无新增卷或环境变量。

成功、失败、拒绝、非 2xx 均可完整保存；完整与否只取决于请求 / 响应实际字节是否收全及真实读取错误，不取决于模型是否回答成功。协议终态仅允许补读，不会把原始传输标记直接改成完整。补读超时 / 被新请求抢占仍可能显示读取异常或提前关闭，不能为了消除状态而清除它。只有 EOF 或达到真实声明长度，并且没有观察到读取错误，才确认原始读取完整。

终态通知覆盖当前 OpenAI Responses / chat / messages 及 Anthropic-to-chat/responses 的流内错误关闭；原本持续读到 EOF 的原生 Anthropic / Gemini 不改读取循环。Zstd 解压器会自行异步预读，保持其原生并行度和取消 / 关闭，不启动第二个原始补读者；已有在途观察收尾仍有效。未知封装 / 尚未接入的提前结束协议仍按原生关闭，不宣称所有协议都能自动补读。后台保留实际连接计数，实际关闭仍先取消再关闭解压器 / 原响应，避免旧读取污染下一条连接。新请求的让行不等待补读完成，但取消 / 调度和共享 CPU、网络仍非硬隔离。等待在途读取结束后也会重查实际 EOF / 长度 / 错误，已结束或已失败均不再额外读。

## 故障与优先级

接收与处理分别单并发、256 MiB old-space 和 20s 后台期限，处理的系统优先级低于接收。主 HTTP 进程不解析正文，不因后台失败同步回退。接收忙、不可用、信封内存准入失败、容量不足时拒收整条；主站仍正常对话。

持久待处理最多 10,000 条，并受对话日志物理容量上限 / 磁盘预留约束；物理文件达到容量上限时拒收新归档，不淘汰历史。计入容量只用于参考，不替代物理容量判断。任务租约为 30s，进程中断后可重新领取；连续三次领取未能发布会转 `PROCESSING_INTERRUPTED`，原文保留并提供手动重试，不无限密集重启同一内容。进程在原文事务提交前退出仍可能整条丢失；提交后而 ACK 丢失时，重发相同事件会获得幂等确认。

处理在接收空隙派发；历史检查、索引准备和外部推送在新接收 / 待办繁忙时让行。推送优先级心跳失效时停止派发后续任务，不反复取消已经开始的上传；已开始的 CPU / SQLite / 网络工作不能完全抢占。显式清空仍按原边界后台小批执行，删除同步移除待办；旧任务不能复活删除记录或覆盖同 ID 后续重收的不同代次。自动保留期由处理进程在空隙每秒最多删除一条，有界回收 SQLite 空间；推送进程在网络等待间隙也可执行最多 128 页的增量回收，容量达到 80% 时提高到 1024 页；正文读取租约、前台请求或 SQLite 忙时立即让行。保留期 0 不删除。

原文与脱敏的所有外推都要求待处理结束，并继续满足原 `complete / reason` 门禁。自动推送游标不会越过待处理记录，处理发布或明确失败后继续，因此较早的慢任务也可能暂时延后后续推送。脱敏处理失败 / 规则过期 / 不透明内容内部未检查时，继续拒绝脱敏推送，不改发原文。

## 兼容和升级

运营中心先更新，即可对旧采集器使用持久接收与后台处理；协议仍为原 JSON/base64、原事件字段和原文字节摘要。新策略仅在正式独立接收链路广告 `durable_receipt_version: 1`；配套新主站据此将后台 POST 期限从 2s 调整到 5s，策略读取仍为 200ms。额外时间只属于后台归档，不延长用户请求。主站收尾与调度改进需要另行升级主站 dev；新旧版本交叉兼容。

迁移仅加默认空 / 0 字段、小任务表、索引和触发器，旧密文、策略、密钥和原始传输标记不重写，不自动全库重处理。新任务不扫描历史。回滚到旧程序之前应先处理完待办，否则旧程序不知道这些新待办；回滚不应删除表、密钥或数据卷。

CPU、复制、GC、磁盘和网卡仍与主站共享，压力下主动牺牲归档。上游真实断流、用户取消、读取没有发生、资源耗尽和主站进程在送达前退出仍可能丢失内容。摘要匹配证明实际采集字节保存一致，不证明上游语义或用户端完整收到；已有缺失字节不能靠重处理补回。验证方法与实测见[性能复核](conversation-performance-review.md)。

## 完整性相关设置

无需新增开关或扩大默认补读预算。部署时应核对两端已更新、保存已开启、实际上游模型名已选中、需要保留的用户未被排除；这些门禁会有意留下会话缺口。需永久保留时使用保留天数 0，并核对对话日志物理容量、磁盘预留和可用空间；容量满仍停止新归档，不能承诺后续都有记录。需要长期保留原始字节时选择原文或双副本，成功的仅脱敏模式会移除原文。采集走代理时还需核对其正文 / 超时限制。上述均是待部署核对项，本轮不修改服务器配置或历史。

相比原单归档进程，接收与处理分离增加常驻内存；仅脱敏模式的临时加密原文和后续副本也增加写盘。系统优先级、内存准入和主动让行不是硬资源隔离。本地流式复测既出现接近改造前的样本，也出现首段约高 1–2ms 的样本，不能承诺零延迟影响。收尾期间内存不足仍整条放弃，不发送清空正文后的残缺记录。
