# 计费核查如何使用上游数据

本文描述本地代码的计费保护、逐请求查单与补记流程。改动需要主站、运营中心、供应商监控三个配套镜像发布并更新后才生效；不表示生产服务器已经更新。

## 数据从哪里来

1. 主站在每次实际付费 dispatch 前，把用户 / Key / 上游账号 / 分组 ID 与名称快照、模型、客户端及上游请求标识、历史售价、同步 / 流式模式保存到 PostgreSQL。存储失败不发出请求；不保存提示词、响应正文或密钥。
2. 接收响应时持久保存已观察到的数值用量、最终 / 部分状态、响应 ID、HTTP 状态、耗时和下游断开标志。未知维度保留未知，初始输出 0 不代表最终输出 0。无效字段或截断不能成为完整用量凭据。
3. 供应商监控继续按连接计划同步真实业务日志。运营中心人工查单及后台发现异常时，也可调用定向刷新接口读取该账号历史映射 Key 的请求日志，随后重新查询样本。不发模型请求，不运行主动检测，不重试推理。
4. 运营中心将异常副本、所有权、查单证据、核对结果、退避进度和分页游标保存到自己的 SQLite，服务重启后继续。主站 PostgreSQL 仍是使用记录与资金结算的唯一来源。

定向刷新通过集成 Token 调用 `POST /api/integrations/billing-samples/refresh`，或使用管理员 SSO 和 CSRF 调用 `POST /api/billing-samples/refresh`；查询仍使用 `/api/integrations/latency-samples` 或 `/api/latency-samples`。后台需要已有持久管理员凭据和供应商集成 Token，短期浏览器 SSO 只供当前会话操作。

只有适配器支持逐请求日志、凭据有读取权限、历史 Key 映射有效时才能取得上游账单。余额、累计消费或相近时间不能代替逐请求最终用量；上游缺少日志接口时记录会持续保留待核查。

## 同步请求为什么改用上游流式

同步响应长时间没有字节，供应商前的 CDN 可能先返回 524，而供应商源站继续生成并扣费。仅延长本站 Nginx 或 Go 的超时无法恢复被上游 CDN 丢弃的最终 usage。

保护开启时，标准 Anthropic Messages、OpenAI Chat Completions / Responses、Gemini generateContent 的同步 JSON 请求在内部接收上游 SSE，再还原原同步 JSON。下游不需要切换流式。心跳和 Token 分片可避免上游读超时；下游断开后已发出的请求在独立期限内继续接收用量，然后走原生计费。上游若不发送心跳、忽略 stream 或先自行中断，仍可能没有最终 usage。

原有流式、媒体、WebSocket、AWS 签名及非标准协议保留其原生处理路径和持久交接；不对签名请求改写请求体或关联 Header。该桥接不包括 OpenAI background 响应，也不改变 simple mode 不扣余额的规则。不能按供应商名称推定一个新协议自动受支持。

| 核心进程环境变量 | 默认值与范围 |
| --- | --- |
| `BILLING_RECOVERY_ENABLED` | `true`；`false` 关闭持久保护，不推荐 |
| `BILLING_RECOVERY_SYNC_STREAM` | `true`；`false` 仅关闭同步转流式桥接，保留意图及计费持久化 |
| `BILLING_RECOVERY_TIMEOUT_SECONDS` | `1800`，允许 30–7200 秒；到期未知则保留核查 |

同步转换只处理不超过 4 MiB 的可重读 JSON 请求，聚合 SSE 最多 64 MiB。数值观察器的单 JSON / SSE 行上限为 2 MiB，超过后明确标记不完整。大请求和其他协议使用原生路径。Docker 的 `.env` 不会自动转为容器环境变量，覆盖开关时需显式写入目标服务的 `environment`。

## 怎样比较同一次请求

查询按异常记录的 Sub2API account_id 定位历史账号 / 上游 Key 映射，时间窗为请求前 15 分钟到请求后 2 小时（不超过查询时刻），最多返回 2000 条。匹配必须同时满足：可信请求 ID 完全相同、候选唯一、事件发生时历史映射有效、查询未截断、映射 Key 的日志同步成功且覆盖对应时间段。当前映射不能证明历史归属。客户端自带且可能重复的 ID，包括被上游回显的 ID，不作为唯一资金关联凭据。

比较的数值是输入 Token、输出 Token、缓存创建 Token、缓存读取 Token，差额为上游值减本地使用记录值。缺少本地记录或上游维度时显示未知，不把缺失值当零。

exact 表示找到了满足上述条件的账单，不代表金额已核准或所有消费已核对。接口返回覆盖状态、上游费用、币种和完整性；上游非整数、负数、缺失或不支持的用量维度不能标记为最终完整用量。供应商监控 schema 33 新增可空的 `usage_complete`；旧样本保留原值且完整性为未知，不能自动视为已验证。

上游实际费用只作支出证据，不能直接当作下游扣费金额。标准 Token 用量可使用主站在 dispatch 前冻结的历史售价和倍率生成补记草稿，不使用今天的价格；缺少快照或涉及媒体、内置工具、特殊 tier / effort、响应模型定价时，须人工核定原生维度与历史价格。缓存创建时长未确认也不能猜测。该功能不进行人民币、美元、额度及充值折扣自动换算。

上述后台草稿保留历史价要求。“CSV 补记”另有管理员确认的自动报价流程：历史快照优先，缺失时读取当前主站模型 / 渠道价格及用户 / 原分组倍率，明确显示来源和报价时间，确认后使用冻结预览结算。自动报价不会改变后台草稿规则、已有快照或已结算账单；已知不支持的维度不能按当前 Token 价格补算。

定向刷新按连接串行，使用 1 个请求并发和分页间隔，最多读取 1000 条；正常冷却至少 60 秒，限流后至少 5 分钟。同连接全量同步与定向刷新互斥，定向读取不冒充全供应商同步完成。未覆盖、超限或日志接口不可用均保留未解决。

## 哪些行为自动执行

| 工作 | 当前触发方式 |
| --- | --- |
| 供应商数据同步 | 既有计划、供应商页手动同步，以及异常查单的有界定向日志刷新 |
| 主站计费意图、最终用量交接 | 请求处理时自动执行 |
| prepared 待结算、settled 但缓存未完成的到期待办 | 运营中心每 30 秒最多处理 100 条；进程重启后重新读取持久待办 |
| unknown / review / 已结算但观察不完整的异常发现 | 每轮各扫描一页 100 条，持久化各自游标，每轮最多核查 20 条到期记录 |
| 查询上游、比较用量、保存证据 | 后台退避执行；管理员也可在详情触发 |
| 标准 Token 最终用量与历史价格均有效的补记草稿 | 后台或“生成核查草稿”，保存为 review；发现上下游用量冲突则阻止草稿 |
| 核查确认、原生多模态 / 特殊价格补记、额外用量差额 | 管理员操作；不自动批准草稿 |
| 已审核账单结算失败后的重试 | 自动退避；prepared 连续失败 12 次转回 review，缓存重试保留已结算状态 |
| 历史 CSV 导入、匹配与报价预览 | 管理员导入并分析，自动排除已核实账单、定位唯一请求、读取主站价格；核对归属、最终用量和价格来源后确认补记，详见 [CSV 补记](billing-csv-import.md) |
| 所有普通已结算请求的全量财务审计 | 当前没有实现；自动发现范围仍是持久意图中的异常及不完整账单 |

新建请求须超过其保护期限加 60 秒，且最近一分钟无更新，才进入补记处理。后台查单失败使用有上限的指数退避，最长 6 小时，5 分钟租约避免进程中断后永久占用。已经确认一致的部分账单在核心版本或用量证据变化后重新入队。`unknown` 和 `review` 均不自动转为 prepared，不自动批准扣费。

## 核定与补记步骤

先在供应商监控确认连接可同步逐请求日志，对应的上游 Key 已映射到正确的 Sub2API 账号，并核对同步时间、覆盖范围与截断状态。上游只返回累计消费 / 余额的连接不能完成逐请求核查。

在运营中心按用户 ID、Key、上游账号、请求 ID 或超时条件定位异常。列表 / 详情保留用户邮箱与 ID、Key / 账号 / 分组名称快照、已观察 Token、本地已记用量、HTTP 状态及请求标识；上游查单结果重启后仍能读取。上游监控不可用时，主站已经持久化的最终标准用量仍可生成草稿。

核对请求 ID、历史归属、模型、缓存时长和最终用量后生成草稿，或人工填写原生使用记录与历史价格凭据。原生 TotalCost 是售卖标准费用，ActualCost 由核心按 TotalCost × RateMultiplier 核定。保存后进入 review，管理员确认后转 prepared，再由原生事务一起写 usage_logs、原生 dedup 和资金效果；自动恢复可处理 prepared 的后续结算。主站新增 `POST /api/v1/admin/billing-recovery/:id/quote` 只读报价接口，仍受管理员鉴权和版本校验保护。

已经 settled 的记录保留原账。后续发现额外用量时，对最后一个已结算节点提交整条请求的最终累计使用记录，核心扣除已结算父链，生成差额子记录后重新审核。重试结算依靠原生幂等去重，既不会重新推理，也不会把同一条使用记录重复扣费。

## 持久化、备份与更新

运营中心新增 `<OPERATIONS_CENTER_DATA_DIR>/billing-recovery/billing-recovery.sqlite`，采用 SQLite WAL 和 FULL 同步，包含异常镜像、用户归属、查单结果和队列；默认 Compose 数据卷不变。运行中备份须使用 SQLite 在线备份 API，或停止运营中心后归档整个数据目录，不能只复制活跃的 `.sqlite` 主文件而遗漏 WAL。供应商监控使用自身 SQLite 在线备份或停机一致性备份；主站仍需 PostgreSQL 备份。

后续应一起更新主站 fork 镜像、`operations-center-latest`、`provider-monitor-latest`，保留现有卷、网络、加密 Secret 和认证。只拉镜像即可，不需要生产源码；操作前将三个服务的配置、镜像身份、数据库及卷备份放到 `/root/sub2api-deploy/backups/` 的同一专用目录，详见[更新手册](billing-recovery-update.md)。

已经发生且没有持久意图的历史丢单，可用 CSV 与仍保留的原生错误或完整结构化文件日志生成用户候选。日志来源声明由运营中心读取并经管理员确认，核心验证身份、时间、模型及原生防重，不会自行认证原文件；摘要不是签名，也不会写伪造错误记录。没有原始归属证据、日志被清理、无唯一候选时不能仅凭模型和时间断言用户。时间候选必须经管理员核对，歧义要明确选择并填写依据。上游始终不提供最终 usage / 账单、独立期限耗尽、进程被强杀或存储故障时，只能保留已持久化意图和已知用量等待核查，不能声称已经准确扣费，更不能估算 Token 后自动扣余额。
