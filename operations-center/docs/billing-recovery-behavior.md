# 计费核查如何使用上游数据

本文描述当前已经实现的行为。计费异常恢复、逐请求上游查单、全量财务对账是不同范围的工作。

## 数据从哪里来

1. Sub2API 在实际发出请求前，把用户、Key、账号、模型和请求意图保存到 PostgreSQL；后续保存已观察的用量、上游请求 ID、计费使用记录及结算状态。
2. 供应商监控按各连接的同步计划，从已配置的上游读取数据。默认间隔 15 分钟，可有最多 20% 的抖动及队列延迟。只有适配器支持逐请求日志、认证权限允许且对应 Key 已监控或映射时，才会产生请求样本。
3. 运营中心详情页点击“上游查单”，调用供应商监控只读的 `/api/integrations/latency-samples`（集成 Token），或通过当前管理员 SSO 调用 `/api/latency-samples`。查单读取已同步样本，不强制即时同步上游，也不发起模型推理。

原始样本存于供应商监控 SQLite；异常状态与资金结算凭据存于主站 PostgreSQL。运营中心不另建余额账本。

## 怎样比较同一次请求

查询按异常记录的 Sub2API account_id 定位历史账号 / 上游 Key 映射，时间窗为请求前 15 分钟到请求后 2 小时（不超过查询时刻），最多 2000 条。只有上游请求 ID 完全相同、候选唯一、历史映射有效且查询未标记截断时，当前界面才返回 exact。

比较的数值是输入 Token、输出 Token、缓存创建 Token、缓存读取 Token，差额为上游值减本地使用记录值。缺少本地记录或上游维度时显示未知，不把缺失值当零。

exact 表示找到了满足上述条件的请求样本，不代表金额已核准或整段账单已完整核对。接口还返回同步覆盖信息，但当前查单不会据此自动完成全范围覆盖审计。同步失败、旧样本、历史数据超出保留期、日志页数限制等情况仍需人工检查。

上游样本表可以保存 actual_cost，但这个查单接口当前没有返回金额 / 币种 / 历史售卖价格；因此计费核查尚不能自动做人民币、美元、额度及充值折扣换算，也不会用上游支出直接作为下游扣费金额。图片、视频、搜索等维度可人工补充原生使用记录，当前自动差异表只覆盖四类 Token。

## 哪些行为自动执行

| 工作 | 当前触发方式 |
| --- | --- |
| 供应商数据同步 | 供应商监控按连接计划执行，也可在供应商页手动同步 |
| 主站计费意图、最终用量交接 | 请求处理时自动执行 |
| prepared 待结算、settled 但缓存未完成的到期待办 | 运营中心每 30 秒最多处理 100 条；进程重启后重新读取持久待办 |
| unknown / review 查询上游、比较与核定 | 管理员打开详情并点击上游查单 |
| 保存历史用量与价格、审核补记 | 管理员操作 |
| 已审核账单结算失败后的重试 | 自动退避；prepared 连续失败 12 次转回 review，缓存重试保留已结算状态 |
| 全量上下游请求扫描、自动发现差额、历史 CSV 导入 | 当前没有实现 |

后台自动执行需要运营中心已有的持久管理员认证；浏览器 SSO 只供当前会话。`unknown` 和 `review` 不会被后台自动核定用量或自动批准扣费。

## 核定与补记步骤

先在供应商监控确认连接可同步逐请求日志，对应的上游 Key 已映射到正确的 Sub2API 账号，并核对同步时间、覆盖范围与截断状态。上游只返回累计消费 / 余额的连接不能完成逐请求核查。

在运营中心选择异常，执行上游查单，核对请求 ID、历史归属、模型与最终用量。没有唯一匹配时继续保留待核查；不能仅凭相近时间、模型或总额强行归属。

根据原请求时的下游售价和倍率填写使用记录及价格凭据。原生 TotalCost 是售卖标准费用，ActualCost 由核心按 TotalCost × RateMultiplier 核定，不能直接填上游采购支出。保存后进入 review，管理员确认后转 prepared，再由原生事务写 usage_logs 并完成扣费；自动恢复可处理 prepared 的后续结算。

已经 settled 的记录保留原账。后续发现额外用量时，对最后一个已结算节点提交整条请求的最终累计使用记录，核心扣除已结算父链，生成差额子记录后重新审核。重试结算依靠原生幂等去重，既不会重新推理，也不会把同一条使用记录重复扣费。

当前能力保证持久跟踪升级后的待计费事项；对于上游始终不提供最终用量的请求，仍需查单及人工核定。它不承诺在证据不足时自动得到准确账单。
