# 存储增长与清理影响评估

## 1. 结论与边界

当前没有生产数据库大小、磁盘挂载或流量测量，下面是基于源码的功能依赖评估，不是已经完成的生产容量审计。

最终采用：**测量增长来源，验证原生汇总，复用已有保留机制，将请求明细控制为 30 天，不建立冷归档或明细副本。** 资金、身份和权益数据长期保留；站点级日/月用量保留 730 天。完整口径见[最终保留策略](retention-policy.md)。

服务默认仅生成清理预览与聚合覆盖检查。显式启用独立维护连接后，可手动执行固定白名单小批清理，也可选择启用每日自动调度；自动任务仍强制经过预览、覆盖检查、预览后原生备份和执行前复核。持续滚动窗口优先由 Sub2API 原生保留任务负责，运营中心调度作为可观测的补充机制。未知表、未知字段和新版本新增对象默认保护。

“保护”指新服务不删除、不缩短保留期，不表示基座原有任务已经停止。接入时必须同时展示基座正在执行的清理，尤其是原始用量默认保留期，否则新服务即使不删，历史仍可能继续丢失。

## 2. 已有保留机制

以下是评估提交的源码默认行为，不能直接当作线上当前配置。

| 机制 | 源码行为 | 新服务的处理 |
| --- | --- | --- |
| 仪表盘聚合任务 | 默认启用；用量明细 90 天、小时汇总 180 天、日汇总 730 天；旧扣费去重记录默认 365 天后迁到归档表 | 逐日核对完成后，将用量明细和小时汇总调整为 30 天，日汇总保持 730 天 |
| 人工用量清理任务 | 默认每批 5,000 行，单任务范围最多 31 天；完成后触发仪表盘重算，删除过程还使分组汇总失效 | 不直接包装成“无损归档清理” |
| 运维清理 | 默认开启；错误、系统日志、分钟指标及小时指标保留默认均为 30 天 | 检查运行时设置覆盖、最近任务结果和实际最早记录 |
| 运维日汇总 | 当前与小时汇总共用 `hourly_metrics_retention_days` | 不能承诺只调一个现有配置就能“小时 90 天、日 730 天”；需另建长期汇总或修改基座 |
| 运维特殊天数 | `opsCleanupPlan` 中负数跳过、0 是整表清空、正数按时间删除 | 新服务不把“无限保留”转换为 0；不同子系统的天数语义分别适配 |
| 渠道监控 V2 | 用户分钟数据 3 天；其他分钟及 5 分钟汇总 7 天；小时 30 天、12 小时 45 天、日 90 天 | 默认沿用原生分层和现有摘要，不为延长趋势另存副本；确认原生 UI 支持窗口后再讨论额外缩减 |
| 通用幂等记录 | 原生任务按 `expires_at` 过期清理 | 与扣费防重表区别对待，检查任务是否积压即可 |
| 调度 outbox | 按已消费水位清理；鉴权缓存失效 outbox 在成功处理后确认删除 | 不按创建时间强制删除未消费事件 |
| 批量图片 | 配置默认终态后输入保留 24 小时、输出 72 小时，输出保留上限配置 7 天；实际清理依赖任务及文件到期状态 | 尊重已向用户承诺的下载期限，沿用原生状态机，不能扫描旧文件名直接删 |
| 内容审核日志 | 默认命中记录 180 天、未命中 3 天，有独立清理逻辑 | 命中证据及未决申诉单独保护；不归类为普通 debug 日志 |
| 管理审计 | 有独立保留循环，保留天数来自设置 | 核对现有策略并保护关键操作凭证 |
| 备份 | 原生备份服务有历史清理、失败中间文件清理 | 先核对备份链和可恢复性，不并行新增盲删任务 |

同一类数据只由一个任务负责实际删除。原生服务已有合适生命周期时，新服务负责展示、检测失效、输出调整方案和记录结果；需要调整原生配置时，先展示具体变化，不暗中修改。不能假设新服务自己的锁能阻止基座独立清理任务。

## 3. 清理候选与影响矩阵

表中天数是后续实施的建议起点，不是立即执行的策略。实际保留至少满足已承诺的查询/下载期限、故障处理周期和更长的现有业务要求。已有永久保留要求的对象不自动变成有限保留。

| 数据 | 建议处理/保留 | 受影响功能与用户体验 | 范围与前置条件 |
| --- | --- | --- | --- |
| `usage_logs` | 逐日聚合验证后滚动保留至少 30 天 | 超期逐笔请求、请求级扣费、用户/Key/模型/渠道历史查询和导出不可恢复 | 首次收缩可用运营中心精确截止点小批删除；持续保留优先用原生任务，也可显式纳入运营中心自动目标。原生月分区删除只处理完整超期分区，因此实际窗口可能长于 30 天 |
| 已轮转应用、反向代理、Docker 日志 | 按大小轮转并保留 7 天，故障证据按审计策略另行保护 | 旧时间段排障、访问追踪不可查；通常不影响余额及正常调用 | 只处理确认关闭的日志及日志驱动管理的文件；不直接删除正在写入的文件，不把唯一审计凭证当日志删 |
| `ops_system_logs` | 保留 7 天 | 管理员旧系统日志搜索和请求链路关联缩短 | 注意原生删除接口是否支持排除事故保留对象，不支持时不要把关键证据放进普通系统日志 |
| `ops_error_logs` | 保留 30 天 | **用户的错误列表与错误详情也会受影响**，客服无法查看更早失败原因 | 页面明确 30 天期限；延长期限不能恢复已经删除的历史 |
| `ops_ingress_reject_aggregates`、历史 `ops_alert_events` | 保留 30 天，规则和有效静默不清理 | 旧拒绝趋势、告警发生记录和复盘证据减少 | 资金或安全事故证据进入专门审计，不依赖该短期表 |
| `ops_system_metrics` | 分钟数据 30 天 | 旧 CPU/内存/吞吐高精度曲线不能回放 | 原生定时任务正常后启用 |
| `ops_metrics_hourly/daily` | 保留 30 天 | 更早运维看板与性能趋势不可查 | 当前小时和日表共用保留配置，不额外建立长期运维汇总 |
| `channel_monitor_histories`、`channel_monitor_daily_rollups`、`channel_monitor_v2_*` 历史指标 | 原生分层优先；不删除配置及聚合水位 | 渠道历史可用性、分位延迟、用户分布及故障趋势精度降低 | 区分旧版/V2、分钟/汇总、有效与删除状态；确认汇总完成及原生 UI 支持窗口后再缩减 |
| `scheduled_test_results` 历史探测结果 | 保留 30 天及各账号最近结果，不删除测试计划 | 历史测试排障减少 | 需按实际查询与引用检测；单表大小较小时不列为优先目标 |
| 备份/导出产生的临时文件 | 已完成或已中止、无下载/任务引用的临时副本参考 7 天 | 过期下载失效，失败任务不能再利用该临时副本 | 通过任务状态和路径白名单识别；进行中的导出、唯一可用备份不删 |
| 已到期的批量生成输入/输出 | 使用原生任务到期逻辑；不主动提前 | **历史输出、图片或视频下载可能失效**，重试可能失去输入 | 在承诺下载期内属于重要用户数据；新服务仅检测，不跨越任务状态直接清理对象存储 |
| 历史备份集 | 示例方案：日备份 7 份、周备份 4 份、月备份 12 份，按恢复目标调整 | 可恢复的历史时间点减少 | 仅完整、可验证、具备替代恢复点的旧备份集；增量链整组评估，不能按单文件年龄删 |
| 未命中内容审核记录 | 沿用原生短保留策略 | 旧审核过程无法复查，可能影响误判调查 | 与命中日志、prompt 审计和未决投诉隔离；不能以“包含正文、体积大”为唯一删除理由 |
| 过期 `pending_auth_sessions`、通用 `idempotency_records` | 优先由原生过期机制管理 | 已过期流程不能继续；可能失去旧请求响应回放 | 必须确认真实过期且不再被处理/重试依赖，不能按“创建超过 N 天”代替生命周期 |
| 已消费 outbox | 由各自原生消费者确认后清理 | 正确清理不影响业务；误删会丢更新通知或使权限缓存陈旧 | 不代替原生确认、不删除失败重试事件 |
| Docker 旧镜像和构建缓存 | 宿主机运维建议，不由默认容器直接操作 | 删除唯一回滚镜像会降低回滚能力 | 保留运行镜像和约定回滚版本；命名卷不在清理范围 |

上表除明确的原生行为外，都是候选设计。哪些项目收益最高，按实测“体积、增长速度、可回收比例、业务影响”排序，不预设一定是 `usage_logs` 最大。

## 4. 重要数据保护清单

| 数据 | 保护原因与误删影响 |
| --- | --- |
| `users`、`api_keys`、认证身份、passkey、密钥与安全配置 | 登录、余额、并发、权限与账户归属；禁用/软删除不意味着可以物理删除 |
| `user_subscriptions`、订阅计划、配额及相关关联 | 用户已购买的服务权益、订阅历史、限额计算；不能以过期为由直接清空历史 |
| `payment_orders`、`payment_audit_logs` | 收款/退款证据、付款历史、待发放与退款重试依赖；包括失败、取消、过期订单，迟到支付可能恢复订单 |
| 已使用/仍有效的 `redeem_codes`，人工余额调整记录 | 用户充值历史、累计充值、余额发放幂等、客服查账；“兑换码已用过”不是可删依据 |
| 推广、奖励与 `user_affiliate_ledger` 等账本 | 邀请奖励、转余额和纠纷对账；属于资产相关记录 |
| `usage_billing_dedup` 与 `usage_billing_dedup_archive` | 防止同一请求重复扣费；归档表也会在扣费路径中查询，不能当普通历史日志清掉 |
| 最近 30 天的 `usage_logs` | 用户逐笔用量、费用解释、按 Key/模型的统计与导出；窗口内禁止提前删除 |
| `usage_dashboard_*`、`usage_group_daily_rollups` 及聚合状态 | 历史统计与重算边界；没有原始数据时不能随意重建或删除 |
| 管理审计、删除 Key 审计、命中审核、prompt 审计 | 权限/资金/风控操作追溯及申诉；日志名称不代表低价值 |
| 进行中的图片/视频/异步任务、未过期结果和对象引用 | 任务查询、继续执行、下载、计费结算与重试；老创建时间不代表已结束 |
| 未消费队列、调度/鉴权失效事件、有效 Redis 状态 | 正确路由、权限撤销、幂等、会话和并发协调依赖 |
| 账号、分组、渠道、路由、价格、插件配置及插件状态 | 正常业务运行及历史解释；不能从当前引用少推断无用 |
| 原生聚合水位、日汇总和日活用户集合 | 支撑清理后的两年站点统计；新服务不另存这些数据 |

已过期未使用兑换码、已软删除用户、旧公告已读标记等低体积业务数据暂不作为自动清理对象。其潜在体验损失通常大于容量收益，只有实测占用显著且依赖已核对后才另立策略。

## 5. 用量日志清理的具体影响

### 5.1 原站功能不会自动读取新服务汇总

源码中的 `GetUserStatsAggregated`、`GetAPIKeyStatsAggregated` 等仍直接聚合 `usage_logs`。因此，即使原生日/月聚合完整，删除原始记录后，Sub2API 原页面的以下功能仍可能变化：

- 用户用量列表、单条详情、筛选和明细导出失去被删区间。
- 用户/Key 的历史费用、Token、模型分布及趋势因查询剩余明细而缩小。
- 管理员按用户、账号、模型、分组、渠道查询历史使用情况的完整性下降。
- 原生人工清理会触发仪表盘重算；分组汇总也有删除失效机制，累计值可能下降。保留旧聚合表不等于永远保留旧累计值。
- `provider-monitor` 会按日期拉取基座用量，并在其覆盖窗口内标记缺失源记录；过早清理会影响成本追溯、回填及数据完整性标记。不得承诺第三方消费方无感。

正常删除历史日志并不直接退款或重新扣余额，但会损害费用解释和历史统计；余额数值不变不代表用户体验不变。删除去重表则是另一类风险，可能破坏防重复扣费能力。

### 5.2 最终 30 天策略

本方案接受上述用户体验变化，不建立归档查询。`usage_logs` 在完整保留 30 天后可由运营中心已预览的小批任务首次收缩，并由原生保留任务或显式启用的运营中心每日调度持续滚动，但必须先满足：

1. 原生日汇总和日活用户集合按 Sub2API 配置时区逐日完整，缺口已在原始明细存在时完成回填。
2. 资金、余额、订单、兑换、订阅与扣费防重表不在清理目标内。
3. `provider-monitor` 等下游已同步到安全水位，且其最长故障恢复窗口不超过 30 天。
4. 用户页、管理员页和导出明确标注“最近 30 天”；站点级长期统计明确标注最长 730 天和实际配置时区。
5. 日常滚动保留使用 `dashboard_aggregation.retention`，不用会触发历史重算的人工用量清理任务。
6. 聚合水位异常、日桶缺失、下游落后、未知版本或备份不可恢复时停止切换或暂停清理。

30 天后仍保留当前余额和长期资金记录，但不再宣称能够按单次请求证明历史扣费。详细期限与启用步骤见[最终保留策略](retention-policy.md)。

## 6. 整体容量体检

### 6.1 数据库

只读采集 `pg_database_size`、`pg_total_relation_size`、`pg_relation_size`、`pg_indexes_size`、`pg_stat_user_tables` 和分区目录信息。分开报告堆表、索引、TOAST、估算活行/死行、最后 VACUUM/ANALYZE 时间，以及分区与父表的对应关系，避免重复相加。

关系排行使用系统目录和统计估算，不对每个大表执行 `EXPLAIN ANALYZE`。正式清理预览会对固定候选区间执行精确 `COUNT(*)`；若超出只读查询预算则预览失败，不退化成不准确执行。逻辑体积仍是按关系大小与行数比例估算，不能当作文件系统回收值。

同时关注 WAL、复制槽积压、长事务、临时文件和自动 vacuum 是否跟得上。数据库关系大小不含所有 WAL、备份和文件系统开销；只看最大的表无法解释整个磁盘。

### 6.2 文件系统与 Redis

磁盘来源至少分为 PostgreSQL 数据卷、WAL 所在盘、Redis 持久化、应用日志、Docker 日志/镜像、备份临时目录及图片/视频/导出目录。新服务不建立业务数据卷或归档库。

必须采集**实际承载这些目录的文件系统**的总量、可用量和 inode，关联宿主机/远程数据库节点标识。容器自身根目录的可用空间不能充当远程 PostgreSQL 磁盘容量。没有宿主机或数据库节点测量权限时，显示“不可用”，不显示伪造的磁盘剩余天数。

Redis 在当前部署模板中启用了 RDB 与 AOF。只评估内存、键数量/TTL 分布、持久化大小和 rewrite 状态，默认无清理权限；不执行 `FLUSHDB/FLUSHALL`，不手工删除正在使用的 AOF/RDB。AOF 重写由 Redis 自身机制处理，并需要瞬时额外空间。

### 6.3 估算与告警

连续运行并在有上限的内存环形缓冲区采样 7-14 天后估算增长速度，分别记录低峰/高峰并剔除备份、vacuum、原生防重记录迁移等造成的突变。新服务重启后样本重新积累；若要求跨重启长期容量趋势，就必须放宽“不增加持久化存储”的约束或接入现有监控系统。

```text
某类稳态存储约等于 日新增行数 x 实测每行物理占用（含索引/TOAST）x 在线保留天数
达到警戒线的天数约等于 （警戒线容量 - 当前已用容量）/ 近期正向日增长
净节省约等于 主库明细减少 - 原生汇总增长 - 清理产生的暂时性 WAL/维护开销
```

仅作量级例子：若每天 10 万条用量、每条包含索引后约 2 KiB，30 天约 5.7 GiB，90 天约 17.2 GiB；非分区表从 90 天降至 30 天的逻辑差额约 11.4 GiB。月分区表会保留与截止点相交的整月分区，稳定窗口可能接近 30-61 天，实际节省小于这个理想差额。上述估算未计汇总、WAL、死元组、备份和维护余量，不能当作本站测量结果或文件系统立即释放量。

建议初始提示线为 70%/80%/90%，同时考虑预计 30/14/7 天达到警戒线；阈值需要按机器规模调整。增长非正或采样不足时不输出确定耗尽日期。高占用状态优先抑制无关导出、减少可选日志、迁移备份/扩容；不启动大规模表重写来应急。

清理预览分别展示“符合条件的行/逻辑数据估计”“预计数据库内可复用空间”“预期归还文件系统空间”。后者没有可靠测量就标未知，不能直接等于删掉行数乘平均行宽。

## 7. 删除与实际释放空间

- PostgreSQL `DELETE` 会产生死元组，也会产生 WAL；通常先增加维护压力。普通 `VACUUM` 主要使空间可复用，不保证把全部空间归还操作系统。
- 不安排日常 `VACUUM FULL`。它会重写表、持有强锁，并可能需要大量额外磁盘；接近满盘时尤其不适合。需要物理缩容时另做维护窗口与容量评估。
- 已有按时间分区的表，完整超期分区在聚合验证后可由明确的生命周期处理；当前分区迁移只为**已经分区**的 `usage_logs` 建子分区，不能假定线上已自动转换为分区表。
- 普通表改分区是独立迁移工程，涉及主键/外键/唯一约束、写入路由、回填和回滚；不作为首期在线清理的附带动作。
- 不直接删除 PostgreSQL 数据文件、WAL、Redis 持久化文件，也不运行带卷删除的 Docker 清理。
- 索引看起来很大也不能直接删除；唯一约束、查询性能和近期未被使用的低频路径都需要评估。

## 8. 保留策略变更与原生任务流程

页面根据当前配置与源码能力实时生成目标白名单、条件、保留期、依赖任务和保护范围，默认只读预览；开启后可手动执行显式的小批数据库清理。每日自动调度是独立的二次开关，目标列表和执行时间由部署环境配置，不另存一套策略或任务数据库。

自动任务不会绕过人工路径的数据库安全条件：它先创建相同预览，阻断时立即结束；只有目标存在超期行时才触发原生备份，并等待一份完成时间不早于预览的成功备份，然后使用相同执行接口提交批次。自动目标默认只有普通系统日志、错误事件和运维指标；请求明细和长期日汇总必须显式加入。进程重启不补跑错过的场次，多实例部署仍应保持单副本，数据库 advisory lock 是最终并发保护而不是调度协调系统。

变更过程为：生成预览，确认聚合/引用条件，在现有运维变更系统中记录配置版本，限定观察窗口，修改 Sub2API 原生保留配置并核对影响。启用后的原生滚动策略自动运行，不需要每批人工确认；扩大范围或缩短期限必须重新评估。

当前源码对非分区 `usage_logs` 使用固定 10,000 行批次，在聚合作业的超时范围内循环；已分区时则删除完整超期月分区。小时聚合的超期删除也不是自适应限速任务。原生实现没有按 WAL 或复制延迟自动调速，也没有供本服务调用的安全取消接口。

因此首次收缩不能直接假定一次从默认窗口切到最终窗口没有压力。建议在低峰按 `90 -> 75 -> 60 -> 45 -> 30` 天逐档预览和执行，并分档降低小时汇总；每档都要完成预览后的原生备份，并核对延迟、WAL、复制、死元组及磁盘余量。阈值异常时停止后续批次；已提交删除无法撤回。同一时段不要再启动 Sub2API 原生人工用量清理。

页面展示自身预览的精确截止点、符合行数、逻辑体积、聚合/备份检查和删除结果，同时读取原生人工用量任务与运维 heartbeat。取消只在当前批次结束后阻止后续批次，不能撤回已提交删除；本方案没有日常查询归档，超期数据不能承诺“点击撤销”。

新服务不持久化财务事实、容量样本或任务副本；运行日志输出到 stdout 并保留 7 天，查询缓存只存在内存。维护状态和审计读取 Sub2API 原生记录。

## 9. 验收重点

- 任意策略都不触及余额、订单、兑换凭证、订阅、30 天窗口内用量明细及扣费防重；未知表不能被通配规则匹配删除。
- 基座清理启用但聚合或下游落后时能报告风险；新服务自身不维护同步副本。
- 保留期、到期边界、尚未完成的任务、投诉保留记录、活跃下载和在用文件被正确保护。
- 用户用量、错误详情、充值记录、订阅权益和下载期限在承诺窗口内通过验证；历史聚合不被删除后回填清零。
- 失败、超时、取消、多实例竞争及源库版本变化不会扩大删除范围；运行报告通过 stdout 和进程内 JSON 复现预览条件。进程重启会丢失内存记录，但不会继续未完成批次。
- 分别验证逻辑行数变化、数据库可复用空间和文件系统实际变化，不把“删除成功”当成“磁盘已经腾出”。
