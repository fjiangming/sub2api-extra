# 三个不降智线路共享订阅配置手册

日期：2026-10-31。适用版本：当前 fork 的 dev，已核对源码提交 `6f8c5c205`。
本手册提供管理员网页操作步骤；本轮未执行配置、部署、生产写入或真实收费模型请求。

## 1. 本次采用的订阅参数

采用一份订阅、一个 Key、一个共享月额度。用户通过模型别名选择基础、稳定、Pro 线路，三个线路不单独分配额度。

| 项目 | 配置值 |
| --- | --- |
| 套餐名称 | GPT不降智三线月卡 |
| 实际售价 | CNY 199 元 |
| 有效期 | 30 天，单位选“天” |
| 共享月额度 | 后台数值 199 |
| 日额度、周额度 | 留空 / null |
| 订阅组平台 | composite（组合） |
| 订阅组类型 | subscription（订阅） |
| 分组倍率 | 1 |
| 基础线路扣额系数 | 0.135，比原 0.15 优惠 10% |
| 稳定线路扣额系数 | 0.196，比原 0.20 优惠 2% |
| Pro 线路扣额系数 | 0.2376，比原 0.24 优惠 1% |

“共享月额度 199”是后台的记账金额数值，页面可能显示美元符号，不代表采购 199 美元。实际收款是人民币 199 元。采购倍率沿用你确认的“每 1 美元模型基准用量对应多少人民币成本”，不另乘市场汇率。

后台没有独立的“线路扣额系数”输入框。本手册把系数写入每个别名的模型单价，分组倍率保持 1。

### 1.1 不亏本的测算前提

按本轮只读核查的最高可调度账号成本，暂计支付手续费 2%、每份订阅固定成本分摊 5 元、异常预留 2 元：

| 用户把整份额度用于 | 最高采购倍率 | 满额采购支出 | 扣除手续费、固定成本及预留后的余款 |
| --- | ---: | ---: | ---: |
| 基础 | 0.11 | 162.15 元 | 25.87 元 |
| 稳定 | 0.17 | 172.60 元 | 15.42 元 |
| Pro | 0.20 | 167.51 元 | 20.51 元 |

任意混合使用时，采购成本上界由稳定线路决定。上述 2% 和固定成本分摊是测算假设，支付后台向用户加收的手续费目前为 0，并不证明支付服务商的实际结算费率为 0。

先用真实账单核对固定成本：`每份固定成本 = 每月服务器及其他固定支出 / 当月有效付费订阅数`。在本例中，保持 2 元异常预留时，每份固定成本需低于约 20.41 元才能仍有正余款。

当前文本订阅不参与通用在途费用预占，月额度不能精确封住最后一批并发请求。因此本手册是“按已知成本及额度模型不亏”的操作方案，不构成任何并发超额、供应商涨价或额外费用下的绝对不亏保证。首批用户并发建议设为 1，验收结算行为后再调整。

## 2. 配置顺序和准备材料

按“账号映射 -> 新订阅组 -> 专用渠道 -> 验收 -> 套餐上架”的顺序操作。

1. 记录三个原分组及账号现有的关联分组、模型映射和账号成本倍率，保留配置恢复依据。
2. 记录渠道和支付设置的现值；不需要停用原来的按量计费分组。
3. 准备一个专用普通测试用户。管理员 ID 1 可能影响运营报表统计，不作为盈利验收用户。
4. 当前三个原分组都是 standard 类型，应新建 subscription 组，不把原组转换为订阅组。
5. 原分组参考：79 = GPT不降智；39 = GPT 不降智稳定；40 = GPT Pro不降智。
6. 全程使用管理员网页操作，不执行数据库 UPDATE，不复制或重建上游密钥。

配置完成后的关系：

```text
GPT不降智三线月卡（199 元 / 30 天）
  -> 新 composite 订阅组，月额度 199
  -> 同一个 API Key
  -> basic/模型名  -> 原 79 组对应的账号集合
  -> stable/模型名 -> 原 39 组对应的账号集合
  -> pro/模型名    -> 原 40 组对应的账号集合
```

原组 ID 只用于核对账号归属；新订阅不会同时绑定 79、39、40 三个原组。

### 3.3 逐个账号操作

1. 打开账号编辑，保留原有模型白名单和映射行。
2. 在“模型映射”中逐行追加“公开别名 -> 原来实际发送给上游的模型名”，使用精确模型名，不用 `*`。
3. 例如账号 230 追加 `basic/gpt-6.1-sol -> gpt-6.1-sol`；账号 226 追加 `stable/gpt-6.1-sol -> gpt-6.1-sol`。
4. 账号 270 同时属于三条线路，对它原本支持的每个模型追加三种前缀。
5. 保持“OpenAI 透传”关闭，确保账号级模型映射会执行。
6. 保持账号现有采购倍率和原分组关联；稍后只增加新订阅组的关联。
7. 保存后重新打开，检查原有模型仍在，新增别名没有被清空。

账号 270 针对一个模型的追加片段如下。它只是新增映射示例，不能覆盖整个 credentials 或整个 model_mapping：

```json
{
  "basic/gpt-6.1-sol": "gpt-6.1-sol",
  "stable/gpt-6.1-sol": "gpt-6.1-sol",
  "pro/gpt-6.1-sol": "gpt-6.1-sol"
}
```

别名保存在共享账号上，可能也出现在原分组的模型发现结果中；在原组调用仍按原组定价计费。若要调整原组显示或白名单，应另行核对现有客户端使用的模型名，避免误封。

## 6. 首版将服务档位固定为 Standard

入口：后台“系统设置”，找到“OpenAI Fast/Flex 策略”。

本手册价格表先覆盖 Standard。当前价格配置不能完整表达所有 ultrafast / 特殊缓存档位，所以首版把订阅用户显式传入的 service_tier 过滤掉，避免额外采购费用改变成本模型。

增加一条规则：

| 字段 | 设置 |
| --- | --- |
| service_tier 匹配 | 全部 tier 值 |
| 处理方式 | 过滤（移除 service_tier） |
| 生效范围 | 仅 API Key 账号 |
| 指定用户 | 先选测试用户，上架后维护为所有本套餐用户 |
| 目标模型 | 第 3.2 节的六个真实模型名，不填 basic/stable/pro 别名 |
| 其他模型处理方式 | 透传 |
| 规则顺序 | 放在可能匹配这些用户及模型的既有规则之前 |

保存系统设置，确保没有针对这些用户的“省略 tier -> 强制 priority”规则，也没有启用分组强制 Fast。每新增订阅用户，应把用户加入该规则；不能只写一句套餐说明就认为系统已经限制。

这是现有配置的一个限制：Fast/Flex 策略按用户、上游账号类型和实际上游模型匹配，没有“仅此订阅组”的条件；该规则也会影响选中用户其他 Key 对这六个模型的请求。若需要同一用户的其他 Key 继续使用 Fast，应另行设计或核验完整档位计费，不能照本规则承诺互不影响。

供应商仍可能自行强制某档服务。验收时应核对实际返回的 service_tier 和供应商账单；仅移除请求字段不能证明上游实际成本不变。

## 7. 配置收款和套餐，但先保持下架

### 7.1 先核对人民币实付

后台“订单/支付”的支付配置中核对：

- 使用实际结算币种为 CNY 的支付通道。
- 本轮查到 `SUBSCRIPTION_USD_TO_CNY_RATE` 为空，即未启用订阅换算，`price=199` 走按数值直付的兼容逻辑。
- 本轮查到后台 `RECHARGE_FEE_RATE=0.00`。不因本手册测算预留 2% 就把它改成 2%；它会改变向客户加收的金额。
- 不要为此套餐修改全站订阅汇率，以免影响既有套餐。
- 在当前未启用换算、向客户加收手续费为 0、CNY 通道的条件下，套餐 price 填 199，实际应付是 199 元。
- 若配置当日已有换算汇率 r > 0，CNY 通道的基数会是 `price × r`，即使套餐标签写 CNY 也一样。此时按实际支付预览倒推 price，并同时核对对外展示；不直接照填 199。
- 售价、币种标签和网关实付分别核对，不能仅凭套餐列表中的人民币符号确认收款正确。

### 7.2 新建套餐

入口：后台“订单管理” -> “套餐管理”（路由 `/admin/orders/plans`）。

| 字段 | 填写 |
| --- | --- |
| 名称 | GPT不降智三线月卡 |
| 分组 | 新 composite 订阅组 |
| 描述 | 基础、稳定、Pro 三条不降智线路共享 30 天额度 |
| 价格 | 当前直付条件下填 199 |
| 币种 | CNY |
| 原价 | 留空或 0，不编造统一原价 |
| 有效期 | 30 |
| 有效期单位 | 天 |
| 上架销售 | 先关闭 |

月额度在“分组”中配置，不是在套餐中再配置一份。不要额外向用户充值 199 余额，那会变成“订阅之外再送可消费余额”。

本手册只配置一个额度档位。不同额度的月卡应使用不同订阅组，因为月限额属于分组配置；不同套餐绑定同一组不会获得独立的额度设置。

## 8. 用普通测试用户验收

入口：后台“订阅管理”（`/admin/subscriptions`），给专用普通测试用户分配新组订阅，有效期 30 天。测试用户建立一个绑定新组的 Key，用户总并发先设为 1。

以下请求会产生真实上游费用，应由配置人员在自己的验收阶段执行；本轮编写手册没有执行。

### 8.1 路由和共享扣额验收

用同一个 Key 分别请求：

```json
{
  "model": "basic/gpt-6.1-sol",
  "input": "Reply with OK.",
  "max_output_tokens": 128
}
```

把 model 分别改成 `stable/gpt-6.1-sol` 和 `pro/gpt-6.1-sol` 再请求。接口为站点的 OpenAI Responses 路径 `/v1/responses`，Base URL 和 Key 使用现有客户端配置。

在使用记录、订阅进度和供应商用量中逐项核对：

| 检查项 | 预期结果 |
| --- | --- |
| 客户公开模型 | 对应 basic / stable / pro 别名 |
| 实际上游模型 | gpt-6.1-sol |
| 基础线路实际账号 | 原 79 组集合中的账号 |
| 稳定线路实际账号 | 原 39 组集合中的账号 |
| Pro 线路实际账号 | 原 40 组集合中的账号 |
| 计费类型 | 订阅 |
| 扣额归属 | 同一个新组订阅，三个请求累计到同一份月用量 |
| 原按量组余额 | 这些订阅请求不另扣用户余额 |
| 定价来源 | 对应别名的显式渠道价格，组倍率 1 |
| 账号成本统计 | 独立按实际上游模型及账号倍率计算，未把优惠售价当采购基价 |

不同请求的 Token 数可能不同，不能只比较三笔扣额大小。短上下文、Standard、纯文本的 gpt-6.1-sol，预期扣额为：

`线路系数 × (普通输入Token × 2 + 输出Token × 10 + 缓存读取Token × 0.1 + 缓存写入Token × 2.5) / 1000000`

普通输入应使用扣除缓存读取后的实际计费输入；若日志已提供分项，直接使用分项，避免把缓存再次计入普通输入。思考 Token 如已包含于输出，不重复相加。

### 8.2 必须验证的拒绝及边界情况

1. 同一个 Key 请求不带前缀的 `gpt-6.1-sol`，应被模型白名单拒绝。
2. 请求 `gpt-image-2`、Claude、Gemini、其他未列名模型，应被拒绝。
3. 验证不能选中对应前缀之外的账号；所有归属账号不可用时应失败，不能跨到另一线路兜底。
4. 发送 priority、ultrafast、flex 请求，核对已按第 6 节归一为 Standard，并检查上游实际账单档位。
5. 用独立的小额度测试组验证：已结算月用量达到上限后，下一请求拒绝；不要为了验收而把正式共享组月额度临时调低。
6. 长上下文用独立验收数据检查 272000 / 272001 边界、缓存命中和高档扣价；不要把未经验证的低上下文试用当作全量计费通过。
7. 验证到期后拒绝；确认已有订阅提前续费是延长有效期，不是无条件立即补满当前月额度。
8. 搜索、图像输入、托管工具等额外收费没有包含在上述纯文本公式里。不要设置 0 元免费来“关闭”能力；只把实际完成价格和采购核验的能力列入套餐承诺。模型白名单本身不按 tools 字段禁止托管工具。
9. 关闭客户端 WebSocket 复用后重连再验证线路切换；现有会话不能假定通过改 model 就能重新选择线路。

收款验收另行创建一笔订单，先核对 CNY 通道实际待付金额为 199 元。订单是否付费由配置人员决定；管理员分配测试订阅不证明真实支付回调已通过。

## 9. 上架及日常维护

验收通过后，到套餐管理开启“上架销售”。客户购买后进入“API Key 管理”，创建或选择绑定新订阅组的 Key；在客户端通过公开模型别名切换线路。

首次上架建议先开放少量用户，逐个确认：

- 有且只有所购新组的一份有效订阅，没有误送余额。
- 用户使用同一个 Key 切换别名，月额度共享。
- 第 6 节的用户范围已加入该用户，普通用户总并发暂为 1。
- 针对新订阅组没有小于 1 的用户倍率覆盖、高峰折扣或额外赠额。
- 上游同步、批量编辑后，账号原模型与新增别名都仍保留。
- 新加入账号只有在支持模型和成本倍率均复核后才关联新组。

每日核对订单净实收、这份订阅对应的真实供应商现金成本和固定分摊，不把“已扣订阅额度”再次算成新收现金。运营中心消费报表可辅助查支出和用量；订阅收入以已支付订单及退款记录为准。

### 9.1 成本变化的暂停线

沿用 199 元售价、199 额度、2% 手续费、7 元分摊与预留时，各线路最高采购倍率达到以下值前，就应暂停新售并重新核算；实际费用更高时阈值还需降低：

| 线路 | 当前最高采购倍率 | 理论保本上界，向下截断 |
| --- | ---: | ---: |
| 基础 | 0.11 | 0.12755 |
| 稳定 | 0.17 | 0.18518 |
| Pro | 0.20 | 0.22449 |

这些是理论保本边界，不是建议把成本用满的目标。组合组不适用当前 OpenAI/Grok 分组利润门，不能靠勾选利润控制自动守住上述边界。

通用复算公式：

```text
P = 套餐实际现金售价
Q = 共享记账额度
f = 实际手续费率
H = 固定成本分摊 + 异常预留
U_i = 线路 i 的最高采购倍率
m_i = 线路 i 的实际扣额系数

采购成本上界 = Q × max(U_i / m_i)
测算余款 = P × (1 - f) - H - 采购成本上界
```

在当前价格与额度不变时，不带其他补贴的促销实收至少需高于约 183.27 元才达到上述假设下的理论保本点；达到保本点即几乎没有超额缓冲，不推荐据此做低价促销。

## 10. 异常处理及恢复

发现串池、扣额不足、供应商涨价或收款错误：

1. 先关闭该套餐“上架销售”，暂停新增订单。
2. 需要阻止继续请求时，单独停用新订阅组；仅下架套餐不会暂停已购用户。已经发出的请求仍可能继续产生费用。
3. 保留原三个按量组、账号和历史使用记录，依据步骤 2 的记录恢复映射或配置。
4. 不清空月用量、不手动重置正式订阅、不直接写余额或删账单。计费差错通过现有计费核查与原生结算流程处理。
5. 配置及采购账单复核完成后，用测试用户重新验收，再恢复新组和套餐销售。
