# 旧域名访问追踪：只读排查与模块建议

排查日期：2026-11-13。目标服务器：`154.36.173.220`。目标旧域名：`epoint2api.fjmooo.cn`。本文仅记录分析，尚未开发访问记录模块或启用采集。

## 结论

后续识别仍在使用旧域名的 API 用户可行，建议在现有运营中心增加“域名访问”模块，并补充可信的入口采集。现有记录不足以恢复完整的历史用户清单；目前没有确认到可以据此通知的普通用户。记录缺失不代表没有人使用旧域名。

优先方案是新增 Nginx 结构化域名日志，由运营中心关联主站已有的请求身份记录。对于能唯一关联的 API 请求，不必先修改主站业务源码。网页登录访问若也要求精确到用户，需要补充鉴权后的身份事件；只读取 Nginx 日志不能保证做到。

## 服务器证据

| 来源 | 只读观察 | 对需求的影响 |
| --- | --- | --- |
| Nginx 路由 | `/etc/nginx/conf.d/migrated-services.conf` 中，旧域名单独一个 server；`aihub.fo2.us.ci`、`yunhop.cc`、`www.yunhop.cc` 共用另一个 server，主业务均转发到 `127.0.0.1:9000` | 请求经过共同主站，但入口域名不同 |
| Nginx 访问日志 | 上述 server 都写 `/var/log/nginx/epoint2api_access.log`；站点未指定日志格式，实际为默认 combined，未记录 Host、请求 ID、用户 ID 或 Key ID | 文件名不能证明一条访问来自旧域名；不能把全文件归为旧域名流量 |
| Nginx 保留策略 | 每日轮转，`rotate 10`、压缩并延迟一次压缩；当前文件加 10 份轮转文件 | 现有常规访问历史约 10 天，更早记录不能由模块凭空恢复 |
| 访问日志内容 | 本次统计共 837,693 行，覆盖北京时间约 11-03 13:00 至 11-13 14:36；其中 608 行 Referer 的主机名为旧域名 | Referer 是来源页面，可能缺失、伪造或跨域，不能当作请求 Host，也不能直接认领用户 |
| Nginx 错误日志 | 统计时有 54 行显式 `host: "epoint2api.fjmooo.cn"`，均为连接上游失败；其中包含反复出现的首页、公开设置及模型列表探测 | 能证明部分旧域名请求存在，不能证明是 54 次付费调用，也不能可靠关联注册用户 |
| 主站文件日志 | 扫描全部 11 个保留文件，共 3,426,596 行，约覆盖北京时间 11-10 08:51 至 11-13 14:40，没有旧域名字面值；抽样 2,000 条访问事件未发现域名字段或用户 ID | 当前文件日志不能补出域名；访问事件中的请求 ID 本来可供未来关联 |
| 主站数据库 | `usage_logs` 有 `user_id`、`api_key_id`、`request_id`，没有入口域名列；最早保留用量记录为 08-15 | 有用量历史，不等于有域名历史 |
| 系统日志 host | `ops_system_logs.host` 当前为容器节点名；源码来源为 `os.Hostname()` | 该字段不是用户访问的域名，不能拿它作筛选 |
| 历史订单 | `payment_orders.src_host` 为旧域名的 6 笔订单，全部归属管理员 ID 1，时间为 05-12 至 05-19 | 可确认管理员过去通过旧域名创建过订单，不能据此得到普通用户迁移名单或证明当前 API 配置 |
| 当前入口 | 通过本机 Nginx 分别指定旧域名及 `yunhop.cc` 请求公开设置接口，都返回 200 | 旧入口在本机路由层仍可用；本次未验收公网 DNS、Cloudflare 或客户端完整链路 |

日志时间需规范化：Nginx 原始时间带 `-0500`，主站文件日志带 `+0800`；页面统一显示北京时间。以上数量是不同排查时点的快照，非同一时刻的全站统计。

本轮 PostgreSQL 查询均处于只读事务，并设置单语句 5 秒限制。一次按日志 component 查询触发限时，随后改为按主键限定最近记录；没有执行写入、清理或迁移。

## API 用户关联方案

1. 在相关主站 Nginx server 增加独立 JSON 日志，记录时间及偏移、规范化的实际 Host、方法、去除查询参数的路径、HTTP 状态、来源地址、受限 User-Agent、服务端关联号。保留原有代理业务参数。
2. 运营中心增量读取这份日志，沿用现有数据卷保存访问明细、用户汇总及采集检查点。处理日志轮转、进程重启、防重、最大保留量和丢失区间；读取权限仅覆盖指定日志目录，不给容器服务器密码或 Docker socket。
3. 用可信请求关联号，读取 `sub2api_custom.billing_recovery.request_snapshot.request_id` 等原生关联字段，取得已验证的 `user_id` 和 `api_key_id`；错误请求可另由 `ops_error_logs` 关联。需要时通过受限只读接口读取，不扩大为业务写入权限。
4. 同一个客户端请求可能产生多次上游尝试。只有身份一致且请求关联唯一时才确认用户；多条恢复记录不能重复增加入口访问次数。无法关联、身份冲突或采集未覆盖的记录明确显示状态，不用 IP 和相近时间猜测。

线上最新 100 条恢复记录都包含请求 ID、客户端请求 ID、用户 ID 和 Key ID，其中请求 ID 去重后为 98 个，说明需要合并同一请求的多条尝试。最新 200 条用量的 `request_id` 都采用 `dispatch:` 形式，因此不能直接把响应 `X-Request-ID` 等同于 `usage_logs.request_id`。

公开设置接口实测返回 `X-Request-ID`，未返回 `X-Client-Request-ID`，不能假设每条路由都有后者。后续实现须核验 API 各协议的成功、拒绝、错误和流式路径；对可由客户端传入或复用的 ID 必须做可信关联设计，不能仅凭字符串相同跨用户认领。

该方案的身份含义是“使用该 Key 的主站账号”。用户共享 Key 或由其他中转代调用时，不能进一步识别 Key 后面的实际个人。

## 覆盖边界

| 访问情形 | 可达到的识别能力 |
| --- | --- |
| 已鉴权且存在原生请求身份记录的 API 调用 | 新日志记录入口域名后，按唯一证据关联用户和 Key |
| 已鉴权但在建立恢复记录前被限额等规则拒绝 | 只有已有错误记录或鉴权事件能证明身份时才能关联；不能只靠成功用量表 |
| 无效 Key、未登录、爬虫或扫描 | 记录匿名访问，不分配注册用户 |
| 网页登录后访问用户接口 | 如需完整身份覆盖，增加主站鉴权后的事件，或正式设计并验证等效的可信采集途径 |
| 静态页面、首页和网页首次加载 | 没有已验证身份时保持匿名；不从登录 IP 推定之前的访问者 |
| 已经轮转删除、原来未记录 Host 的历史 | 不能保证恢复；已有 Referer 或错误线索单独标记，不能混为确认用户 |

如果此前已有 Cloudflare Logpush、外部日志平台或旧服务器备份，可另行评估是否含原始 Host 与可靠请求关联号。本轮没有核验这些外部数据，也不能假设 Cloudflare 事后能补生成以前未保存的逐请求日志。

## 运营中心模块建议

建议菜单名为“域名访问”，默认关注旧域名，也可比较现有新入口。

- 概览：旧域名确认用户数、已关联 API 请求、匿名及未关联访问、最近一次旧域名请求、采集起止时间与覆盖缺口。
- 用户列表：用户 ID、用户名或邮箱、使用的 Key 名称及 ID、旧域名首次和最后访问、近 1/7/30 天请求、新域名最近访问、通知处理状态。
- 请求明细：时间、入口域名、路径、状态、关联来源及证据状态；HTTP 200 流式请求不能直接标为模型生成成功。
- 迁移观察：区分“最近仍使用旧域名”“观察期内仅见新域名”“观察期内无访问”。使用过新域名不能证明其所有客户端都已迁移。
- 操作：筛选、分页、导出确认用户；复用现有“用户消息”生成待审草稿，发送由管理员明确执行并保留处理记录。
- 保留：建议明细默认 90 天、按用户与域名的每日汇总 365 天，可配置且有容量限制；数据不足和采集间断始终可见。

只保存必要请求元数据，不保存明文 API Key、Authorization、Cookie、登录 Token、请求/响应正文或 URL 查询参数。配置中的域名必须有明确允许列表，不能信任任意客户端提交的用户 ID 或转发头。

## 分阶段交付

第一阶段优先解决“哪些 API 用户仍在调用旧域名”：独立域名日志、增量采集、原生身份关联、确认用户列表、导出和通知草稿。验收包含旧/新域名、不同用户及 Key、多协议、长流、错误、重复 ID、重试、匿名、轮转、重启及采集缺口。没有证据的记录保持未关联。

第二阶段按实际需要扩展网页登录和用户接口的鉴权后采集，避免将有限 API 覆盖误称为全站逐用户访问追踪。

历史导入保留证据等级和原始覆盖范围，不把旧文件名、Referer 或共享 IP 转换成已确认用户。即使先上线追踪，也应保留旧入口观察一段时间；关闭域名的时间点由管理员决定，不能把跨域重定向当成所有 API 客户端都能自动迁移。

本轮只新增本分析文档和维护记录，没有修改业务源码、测试、服务器配置或业务数据，没有重载、重启、部署或发送用户消息。主站及运营中心排查前后 StartedAt 一致、均为 healthy。SSH 密码不写入文档或仓库。
