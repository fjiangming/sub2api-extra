## 为什么显示无法完整检查

`src/services/conversation-sensitive.js` 的 `assertInspectable` 会拒绝将签名、加密内容、外部文件或媒体标记为已检查。普通键名 `url` 下的 HTTP URL 也会统一触发，缺少是否为实际媒体 / 外部文件引用的上下文区分，因此用户消息和工具内容中的普通链接也可能失败。

有限抽取的 15 条原文中，类别可重叠：

| 命中类别 | 记录数 |
| --- | ---: |
| thinking 内容的 `signature` | 10 |
| `signature_delta` 的签名 | 8 |
| `url` 字段 | 13 |

进一步定位这些记录内的 83 个 URL 均在消息上下文。该结果说明签名和较保守的 URL 规则是这些样本失败的直接触发点，不能据此断言全库的比例，也不能保证签名或链接内部没有敏感信息。

失败会保留 AES-GCM 加密原文，整条不生成脱敏副本；不代表原文被删除或上游请求失败。仅脱敏模式下的加密原文是用户此前要求的异常回退。同样的原文与同样的处理规则通常会再次失败；不能靠重复点击消除这些提示。默认脱敏推送会跳过这类记录，不回退发送原文。

“处理策略 v5”是处理时使用的保存策略版本，脱敏引擎版本是独立字段，当时为 2。此次没有放宽脱敏规则或把不透明内容标为已检查，只改进了页面的分类说明。要减少误报，需要分别定义普通链接、签名与实际媒体的检查范围和对外副本约定，不能简单删除签名或整轮消息而破坏原有上下文。

## 为什么显示读取中断

主站采集器将正文读取中的所有非 `io.EOF` 错误统一标记为 `read_error`，没有持久保存具体错误枚举及请求 / 响应发生侧。因此，现有记录不能精确回溯是客户端取消、超时、网络断流，还是应用已经结束后上游未正常关闭。

对 9 条 `read_error` SSE 记录进行结构化有限抽查，9 条均已包含顶层 `response.completed`，且其中的 `response.status` 为 `completed`；4 条还含 `[DONE]`。这说明至少这些记录已观察到上游应用层完成事件，后续传输问题也被归入“读取中断”。该事件不能证明下游用户一定收齐全部字节，也不能将所有历史中断记录都判为完整。

主站 `backend/internal/service/openai_gateway_passthrough.go` 在终止事件后的空行退出，不等待底层 EOF，避免某些上游延迟关闭造成额外 8 至 46 秒等待。为了改善日志标签而改为等待 EOF 会影响用户体验，不能采用。本轮不修改主站采集器、不补发推理、不把历史 `complete=false` 自动改为完整。后续若需要精确区分，应增加轻量错误分类与“已见应用终止事件”证据，仍保留字节完整性和业务完成状态的区别。

这些结果不等于生产峰值压测，无法承诺共享宿主 CPU / IO 严格零成本。清理不进入推理调用链，采用低优先级、每批最多 1 条、250ms 间隔和锁忙退避降低竞争，不强制 checkpoint / VACUUM，也不影响主站计费数据。本轮未提交、发布或部署该功能。
