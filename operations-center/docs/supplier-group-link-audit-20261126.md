## 已确认原因

- 运营中心与供应商监控实际 revision 均为 `5371db2c86be725a696dd9b547ec7d9128ec4ac0`，并非服务器仍运行旧前端。
- 11 月 26 日 00:05 左右报表有 9 家启用定时检查的供应商；`apiclub / uselink / lingsu / ailzd / zhiam` 返回空 Key 列表，虽然监控目录分别已有 23 / 10 / 42 / 16 / 1 个非 missing Key，且全部存在完整 Key 指纹。
- `lingsu` 在主站有 33 个名称候选账号，但报表 Key 为空，无法继续核验分组。旧首页又从上游 Key 建组，所以整家供应商和账号均未展示。目录没有丢失，也不是缺少指纹。
- 对上述 5 家供应商现有会话执行 GET：`user/profile` 和 `usage/stats` 均成功，账号日汇总约 131–429ms。进一步对真实分组读取路径作只读复现：`apiclub` 用时 6,007ms，47 个请求中完成 46 个；`lingsu` 用时 6,044ms，49 个请求中完成 47 个，均触发 `TIMEOUT`。原单供应商 6 秒预算内未完成全部 Key 查询，末尾核验失败后丢弃整次结果；没有旧快照则以 `keys: []` 返回。逐 Key 需要多次 HTTP 查询，因此汇总可用不代表完整分组采集能在期限内完成。
- 另一独立原因是把所有 `updated_at` 晚于当天首请求的账号标为整日身份不稳定。11 月 25 日已有 34 个账号被拦；例如 11 月 26 日账号 #360 `https://tuokeapi.com/--gpt不降智` 首请求 00:00:38，更新时间 00:04:34。时间戳只能证明账号行更新，不能单独证明 Key / 名称变化；已有当日稳定观察仍会被旧规则否决。初次观察前是否轮换无法仅凭本次证据确定。
- 共有 14 家供应商配置，其中 5 家关闭定时检查，原成本报表按既有规则不纳入：`ai.max66.xyz / ai2api / aikangs / hubway / wanfaai`。本轮不擅自启用。
- `tuokeapi` 目录只有 1 个 Key，而名称候选有 4 个，仍存在完整 Key 无法核验的账号。名称可以定位供应商，但不能据此猜测上游分组。

## 本地改造

1. 名称唯一定位供应商后保留账号及主站实际消费；完整 Key 唯一核验后归入真实上游分组，否则在该供应商下列为待核对。停止自动截取半名匹配，保留完整名称、去 API 后缀及显式简称。
2. 今日消费读取失败且没有旧快照时返回已同步目录中的关联信息，消费 / 请求数全部为未知。禁止将今日目录用于历史补算，禁止把失败保存为成功消费快照。
3. 已可信观察且名称 / Key 均未变化时，不因其他字段带来的更新时间变化破坏关联；首次历史依据不足、真实身份变化及既有变更标记仍保留待核对。
4. 表格改为主站账号在第一列，上游分组第二列；只有主站有关联账号的分组参与列表、分页和供应商合计，当日零消费账号也保留。同 Key 的多账号和跨主站分组消费累加，上游分组消费只计一次。

该改造恢复账号可见性，不保证所有供应商的全部 Key 消费都能在现有期限内完成。未核验金额继续显示未知；需要同时更新 operations-center 和 provider-monitor 后才在线上生效。本轮只完成本地修改及验证，服务器保持原版本。

验证：运营中心供应商分组 18 项、Provider Monitor 分组 12 项专项通过，包含历史禁止回拉、真实 SQL 跨组汇总和迟到不能写入的回归。运营中心语法门禁、分组 5 种视口及原核算 4 种视口浏览器检查通过；复核桌面和 320px 截图，账号、金额与待核对状态无整页横向溢出。北京时间 00:27 收尾只读复核，两组件均 running、重启计数 0、revision 未变，健康接口均 HTTP 200；所有 SSH 调用均已关闭。本机隔离演示为 `http://127.0.0.1:19884/preview`，使用虚构供应商与临时数据库，不连接生产。

### 分组消费的两个独立失败原因

1. **重复解密占用读取预算。** 在不写快照的同路径复现中，lingsu 6,014ms 后超时；49 次 HTTP 请求完成 47 次，供应商凭据解密 **102 次 / 4,703ms**。`ProviderRepository.#credentialSnapshot()` 每次核验都解密，`readCurrent()` 在每次请求和凭据协调中重复调用，耗尽大部分 6 秒预算；单独查询该站分组 20 仅约 179ms，接口有正常分组名和实际消费。
2. **实时两次查询没有相同统计截点。** tuokeapi 的 snapshot-v2 返回分组请求数 2,756、原始实际消费 12.130784244；紧接着 `/usage/stats` 已增长到 2,757 次 / 12.1325997。金额为上游原始额度，未折 CNY。适配器要求两次查询金额和请求数严格相等，触发 `SCHEMA_MISMATCH: Group totals do not cover key usage`；单 Key 被置为未知，继而账号覆盖校验也失败。即使 Key 已唯一关联，也会丢失消费。另一次单独探测成功返回该分组 2,639 次 / 11.787169932，说明这不是永久缺少分组能力。

实际 GET 还验证 apiclub 分组 64 约 405ms 返回完整分组结构及消费。上游 `groups`、`group_id`、`group_name`、`actual_cost`、`requests` 字段均兼容，非字段名称错误。部分 lingsu / ailzd 账号另外存在完整 Key 未匹配，本次不猜测其分组。

后续修复应分别处理：当前分组展示与历史消费可信度解耦；在保留配置 / 凭据变化校验的前提下减少相同密文的重复解密；使用同一快照或固定时间截点核对分组及汇总，不放松真实完整性校验。本次仅分析并记录，未修改产品源码、生产配置或数据，未重新提交 GitHub、部署或重启。01:17 收尾两组件健康接口均 HTTP 200、revision 未变、重启计数均为 0，所有 SSH 调用已结束。
