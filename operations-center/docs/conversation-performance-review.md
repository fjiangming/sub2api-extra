# 对话日志对用户体验与性能的复核

复核日期：2026-11-16。用户优先级是正常对话第一、归档第二。先只读审计，再按用户要求完善两端代码并用虚构数据验证；未向模型厂商发送请求，未读取生产对话正文，未更新服务器。

## 本次完善及复测

不能承诺严格零开销或生产高峰完全零影响。新版消除归档网络 / 磁盘 / 脱敏的同步等待，保留有界的正文复制成本；后台工作仍共享 CPU、内存、GC、磁盘和网卡。核心更新需要配套升级两端程序，源码 / 镜像发布不等于服务器已更新。

- 主站先检查后台策略缓存；关闭、排除、缓存无效时尽早退出。缓存锁与 WS 观察锁使用 TryLock，竞争时丢弃采集；预算 CAS 最多重试 8 次。HTTP 合并为 16 KiB 块，避免每个小 SSE read 分配；无正文解析、归档网络或磁盘等待。
- WS 热路径只复制不可变帧并非阻塞入队，独立 worker 负责模型、分段及结束事件；待处理队列 16,384 项、完成队列 32 项，均受全局 64 MiB 观察预算保护。任一队列满、scope 锁竞争或预算不足会放弃受影响采集段，剩余租约停止观察；此前已完成段可保留。避免为了排队或解析拖延双向 relay。
- 主站后台按块计算摘要并流式 base64 编码，保持相同 JSON 协议、Content-Length 和字节 ACK；拒收 / 超时关闭 pipe 并等待编码协程退出后才释放正文。模型单次扫描复用解析结果，只复制短模型名，避免持有整篇 JSON 字符串。
- 保留底层支持的 WriterTo 快速复制，避免在可以使用它的传输路径上退化成大量小写入；已知 Content-Length 的 Go HTTP 路径仍可能包装 LimitedReader，因此不能由该优化推导出与原生 transport 完全等价的速度。
- 运营中心通过内部 loopback 流把 envelope 转给独立低优先级子进程；JSON/base64 解析、脱敏、加密、写盘、重处理和定时过期清理移出主 API 事件循环。仅单任务、无等待队列；繁忙、不可用、内存准入拒绝时整条跳过，20 秒期限后终止处理进程，退出后间隔 5 秒重启。生产不会自动回退到同步接收。主站两秒后台发送期限独立，不阻塞用户推理。
- 子进程 V8 old-space 256 MiB；按宿主 / cgroup 空余内存及堆余量、预留 32 MiB 和估算放大倍数动态准入。不承诺接收任何大小：大 envelope / 内存不足可能整条拒收；解码处理超预算但仍能加密原文时保存原文和异常，OOM / 超时杀进程发生在提交前时可能整条丢失，不谎称保证原文回退。256 MiB 解压上界之外还有运行时更小的资源预算，均不截断原文。
- 处理不持 SQLite 写事务；最终短事务重新核对当前用户 / 模型 / 开关 / 保留期 / 空间和幂等键。重处理在更新前再次核对策略及记录版本，避免跨进程策略竞争写入新排除用户或覆盖新副本。正文读取和已有外推仍可能占用运营中心主线程及共享 IO，并未声称整个运营中心零负载。

## 完善前结论

不能确认“完全不影响用户使用与速度”。可以确认本地新版已把归档网络等待移出 HTTP 上游转发路径，但正文复制、分配、锁和 WebSocket 解析仍在转发路径；后台工作也共享主站进程或服务器资源。服务器实际运行的旧版还保留同步策略查询，不能将新版的旁路行为当成已经上线。

当前服务器资源采样有余量，未发现持续 CPU / IO 饱和；这是短时观察，不是生产首字延迟、逐段延迟或高峰 P95 / P99 的 A/B 结果。按“对话优先”的标准，当前实现仍有应在发布前完善的性能边界。

## 本地新版的剩余开销

| 环节 | 实际行为 | 对用户的意义 |
| --- | --- | --- |
| HTTP 上游 Request / Response | 每次 Read 后，短暂加锁、申请预算并复制该块，再把结果返回转发方 | 没有等待运营中心，但有同步 CPU / 内存成本；大请求可增加发送及首字等待，响应复制可增加逐段转发时间 |
| WebSocket 上游入站 | `ReadMessage` 返回调用者前执行 `RecordFrame`，复制帧并用 JSON 解码判断结束事件 | 大帧会直接延后向客户端转发；客户端使用 HTTP，而网关选用 WS 上游时也适用 |
| WebSocket 出站 | 写入上游后同步做模型候选扫描、复制；同一 scope 的双向观察共享锁 | 不一定延后已经发出的字节，但可能延迟发送调用返回、后续读取及反向帧处理；不能当成全异步 |
| 模型过滤 | HTTP 模型识别在后台，识别前仍进行有界内存观察 | 名单外不落盘，但不代表名单外完全没有复制开销；排除用户可在观察正文前跳过 |
| 主站后台 worker | 组装、模型扫描、摘要及 JSON/base64 编码都在主站进程内 | 不串行等待推理，却仍竞争 CPU、堆和 GC，影响可能体现为高峰长尾延迟 |
| 运营中心归档 | 解码、脱敏、加密、SQLite FULL 写入同步执行在 Node 事件循环 | 大正文和复杂脱敏会阻塞运营中心 API；经旧版同步策略查询还会间接传到主站 |
| 队列 / 内存压力 | 队列满或观察预算耗尽时放弃整条，释放已持有的观察内容 | 防止无界积压，但丢弃前的复制和临时解析仍已付出；不是 CPU / RSS 的硬隔离 |
| 磁盘和外推 | 独立 SQLite、后台发送，但仍共用物理磁盘和网卡 | 高归档量、批量重处理或推送仍可能与主站 / PostgreSQL 争用宿主资源 |

WebSocket 的模型扫描当前发生在预算检查之前，预算耗尽并不能约束该扫描的临时分配。64 MiB 只计入观察正文及约定元数据，不包括组装、解析、编码或整个进程的 RSS。不能由“有 64 MiB 上限”推导出“不会增加主站 OOM / GC 风险”。

## 服务器资源观察

只读采样得到 8 vCPU、约 15.36 GiB 内存，可用约 12.5 GiB；主站约 361 MiB，运营中心约 134 MiB。运营中心限制为 1 CPU / 512 MiB，主站未设置对应硬限制。短时 `vmstat` 区间 CPU 空闲约 95%、IO wait 为 0；两容器 healthy，当前状态没有 OOM 标记。

主站实际宿主监听端口为 9000；纠正初次试探的 8080 后，连续五次健康请求全部 200，主站约 1.05–1.55ms，运营中心约 1.68–2.23ms。初次 8080 未监听不属于服务故障。健康请求不经过模型推理和完整采集路径，不能用这些耗时证明对话性能没有变化。

运营中心存在历史 CPU quota throttling 计数，不能将其累计值当作当前持续饱和。1 CPU 限制有助于保护同机其他服务，但不预留主站核心，也不隔离磁盘 / 网络。新接收上限和较大正文可能产生的临时内存，应与 512 MiB 容器限额一起验证；本轮未做生产压测或制造 OOM。

## 建议顺序

1. 保留新版后台策略缓存、故障跳过、无发送锁阻塞和不等待归档回执的行为，发布时两端配套升级。
2. 优先降低 WS 路径的同步全量扫描 / 临时复制，并让丢弃后的观察尽早返回；确保用户、模型、结束事件和消息次序仍正确。
3. 将大正文脱敏与运营中心 API 事件循环隔离，限制并行量，并对超时 / 内存不足保留原文与处理异常；不以截断内容代替资源治理。
4. 为主站后台编码和运营中心接收 / 处理计算完整内存预算，增加压力旁路 / 退避。再以脱敏后的指标验证同负载开关采集的首字、逐段延迟、P95 / P99 和 GC，满足用户体验标准后发布。

本轮额外重跑四项既有故障 / 非阻塞 / 预算专项，均通过。没有新增永久性能测试或调整生产资源。现有证据支持“新版显著减少直接等待”，不支持“采集完全零开销”或“高峰用户体验已经保证不变”。
