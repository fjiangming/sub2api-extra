# CSV 补记与用户扣费

入口：运营中心 → 计费核查 → CSV 补记。本功能导入上游的逐请求最终账单，将缺失请求归属到主站用户，先展示扣费预览，管理员确认后补记原生使用记录并结算。导入、匹配、预览均不扣费；不调用余额管理接口，不重发推理。

## 使用步骤

1. 选择上游 CSV 和编码，导入批次。支持 UTF-8（含 BOM）及 GB18030；可展开字段映射，对无法自动识别的表头手动指定。已导入的同一份内容会回到已有批次。
2. 将 CSV 的每个上游 Key 名映射到对应的 Sub2API 上游账号。Key 名不是下游用户，空 Key 名也必须单独映射，不能自动归到其他 Key。映射依据应是导出时实际使用该 Key 的账号。
3. 点击“分析账单并生成预览”。默认使用 Asia/Shanghai、自动核对时间含义和 5 秒容差；匹配后自动对当前页最多 20 个请求或候选组入口读取主站价格，不需要填写售卖规则。整组报价会带齐其他页的全部成员。时区、时钟偏移和缓存解释在折叠的高级设置中调整。每 Key 至少 3 个有区分度的原生用量样本、90% 以上一致，才自动判断开始 / 结束时间；不足或与显式设置冲突时保留待核查。后续表头与 Key 集合相同的导入会沿用最近成功分析的映射及时间设置，仍应检查账号是否正确。
4. 默认查看“可补记”，核对逐笔用户、Key、原分组、Token、金额、价格来源及上游支出差额。其余筛选为“待核查”“已计费”“已补记”“全部记录”。“待核查”可按用户筛选整批记录并翻页，同一用户的并发请求集中核查，但不会因用户相同自动选择具体请求。没有唯一归属、用量不完整或自动报价失败的记录显示具体原因；选择候选并补充归属依据后可以重新生成所选预览。售卖规则默认“自动读取主站价格”：有请求历史快照时优先使用，没有时明确显示“当前主站价格”及报价时间。缺缓存计数不能当零；缓存总数有值却缺少时长拆分时，可在高级设置核定 5 分钟 / 1 小时归属，不需要手填价格。
5. 勾选一次，确认所选请求的用户归属、CSV 最终用量、价格来源和金额，再点击“确认补记并扣费”。此前所有操作均不扣费。成功后可筛选“已补记”查看核心案件 ID 和回执；处理失败保留原预览供续办。若连接中断，重新打开同一批次，不要另建裸余额扣款。

逐笔预览和按用户 / 本页所选汇总显示上游支出、本站拟补记和“上游多扣余额差额”。差额为 CSV 上游实际 USD 支出减本站拟补扣金额：正数表示上游支出更高，负数显示“本站拟多收”，不表示已经收回资金或证明供应商错扣。订阅增加历史用量，单列上游成本，不计入余额差额。缺失、负值、非 USD 或格式不识别的支出保持未知；费用不完整时仅汇总已知支出，合计差额未知。金额按 8 位小数比较，不再乘上游或账号倍率。

逐笔记录每次最多确认 20 笔；整组每组 2–20 笔，必须全选，单次包含组成员最多 400 笔。翻页会自动为该页入口报价；跨页组会展开所有成员、原预览总额及各自状态，不能只确认其中一页。每笔资金仍由原生事务单独提交，批次可能部分成功，失败记录与成功回执分别保留。开始确认后不能更改匹配设置，但允许以原设置重新分析其余未开始的行；已经确认、失败或预留的行及回执不被覆盖。更改归属、缓存解释或价格模式后须重新生成所选预览；更改匹配配置后须重新分析。修订已保留的核心使用记录应从“异常请求”按案件 ID 核查处理。

历史快照按请求独立报价，包含当次用户 / 分组倍率；不存在快照时，主站按原请求的分组 ID 解析当前模型 / 渠道价格及该用户的专属倍率，不能套用 Key 后来迁移到的新分组。当前价格无法还原过去的规则，确认框会同时要求核对价格来源。需要严格恢复旧售价时，可展开可选的“人工核定历史售价”，按实际用户 / 分组 / 时期分开选取并提供依据；普通流程无需填写该表。已保存的预览冻结金额，确认时不会重新报价。

## 匹配依据

### 按 CSV 请求时间读取证据

查询范围由文件内有效、已映射账号的账单时间及每行耗时决定，与导入当天、昨天或服务器当前日期无关。先按 CSV 显式时区 / 配置时区解析，再应用时钟修正；已知耗时的行同时覆盖“账单时间减耗时”和“账单时间加耗时”，供开始 / 结束时间的独立核对。长于四小时和跨日请求使用完整耗时，前后保留至少五分钟读取余量；未提供耗时的行使用前后四小时读源余量，但不把这个范围作为确定归属的证据。无效、未映射和完全重复行不扩大源查询。

页面显示 CSV 账单时间、证据读取时段、采用的时区、时间校准证据和各类本地来源数量。每行分别显示 CSV 时间、校准后的请求开始 / 结束时间、匹配依据和候选来源。自动识别时间含义只用独立的原生完整用量，不用正在追查的漏扣请求投票；同一本地请求被多行指向时不能贡献多票。无足够证据时需确认时间含义，不会按最近一天代替。

历史证据只使用当时实际留下的字段。新加的主站日志不能补回过去；早于个性化案件上线的请求仍可通过旧错误或完整业务文件日志核查。日志已清理、未挂载、缺少完整关联或价格来源不确定的记录继续保留核查，不推断其必然未扣费。

| 本地来源 | 处理 |
| --- | --- |
| fork 的持久化 dispatch 意图 | 优先使用；保留实际尝试的用户 / Key / 账号与历史价格快照 |
| 原版 `ops_error_logs` | 使用原生用户 / Key / 账号 / 分组归属；原生错误通常在结束时写入，用 `created_at - response_latency_ms` 还原开始时间 |
| 错误中的 `upstream_errors` | 区分不同上游尝试；多次尝试或缺耗时的记录保留不确定时间区间，单靠宽泛区间不能选定扣费请求 |
| 原生 `usage_logs` | 优先用同账号 / 模型、四类完整 Token 和时间排除已有用量；再检查原生扣费防重热表 / 归档或恢复案件 settled 状态。仅 ActualCost 非零也不冒充已核实扣费 |
| 主站结构化文件日志（可选只读挂载） | 通过服务端 request_id 关联用户 / Key / 分组、唯一账号选择及访问结束记录，找回被取消忽略策略排除的历史归属；可补全对应原生错误的开始时间 |

匹配先核对已有原生完整用量和请求 ID，再在尚未占用的本地来源中按账号、模型和开始时间查找。四类 Token 相同但在不同时段重复出现时，先按时间缩小候选，再做整批一对一核对，不要求 Token 组合在整天唯一。排除已有用量时同时检查开始 / 结束两种时间含义，避免表单设置错误把已付费请求匹配到另一个未付费意图。已验证对应 CSV 的本地记录不再污染其他行的候选；一笔本地记录被多条不同账单争用时保留冲突，不能把一笔扣费算成多笔。ID 与 Token 证据矛盾也转核查。已有使用记录且无完整计费凭据的单列“扣费待核查”，已有部分用量的单列差额核查，均不再收整笔费用。

精确开始时间候选优先于无耗时的四小时区间；宽泛区间只显示时间证据不足。算法版本 6 对已有完整用量和待补记精确候选分别做有界的整批一对一分析：只有某条对应关系在所有完整分配中都必然成立才选定，不使用最近时间猜测。单个连通分量最多 160 行 / 400 个来源；触及阻断来源、超过边界或不能完整分配时，整组转核查，不能把其中一个暂时唯一的选择当作可扣费请求。同用户并发多解仅在满足下一节整组核查条件时进入整组报价；跨用户、Key 或分组的歧义仍保留核查。客户端可重复 ID 不授权自动扣费，时间匹配仍需在最终确认时核对。

同一持久意图与其原生错误 / 使用记录会合并来源；多个真实 dispatch 仍保留独立候选。CSV 的完全重复行保守标记，不自行当作两笔独立消费。字段不全、非法计数、超过查询上限、源查询失败或候选超过 30 个时不生成可扣费预览。时间、模型或 Token 相似都不构成用户归属的保证。

### 自动核查候选

点击“分析账单并生成预览”同时执行以下核查，不需要另配匹配规则：

- 在同账号、用户、Key、分组和模型范围，用共同的服务端请求 ID 或已核实的上游请求 ID 关联错误、文件和持久案件证据，展示来源证据份数。多个实际 dispatch 案件仍分别保留；可复用的客户端 ID、时间接近或只有同一用户不能作为合并依据。
- 持久案件已经观察到的标准 Token 参与排除：完整最终用量须一致，未完整用量只作为下限，未知计数不能当零。含缓存输入但缓存拆分未知时不强行计算净输入；不支持维度或无有效观察保持原核查约束。匹配更唯一后仍须通过原生报价及最终确认。
- 对仍多解的关联组显示账单行数、候选来源数、来源类型、相同 / 不同归属、能否一对一分配及关联 ID 缺口。候选来源数不是实际调用次数，错误与案件可能重复描述一次调用；数量相等也不等于证据完整。

版本 6 增加整组核查：组内用户、Key、原分组、上游账号及余额计费必须一致；上游非重复账单数等于独立本地来源数，存在完整一对一分配，每个来源有本地关联 ID，CSV 标准 Token 和缓存时长完整。只接受 2–20 笔历史错误 / 完整文件来源；持久案件、订阅、来源不足或超过上限仍逐笔核查。即使精确候选数量相等，只要同一时段还有组外可能的已有用量、持久案件或缺耗时来源，也阻止整组补记，不能忽略宽泛区间来假定完整覆盖。

通过上述核查后，对每笔账单的每个可能来源调用主站只读报价。所有对应方式的用户费用和计费维度均一致、且没有 Key 滚动限额或账号配额，才生成全组预览。组内使用稳定账单摘要和来源排序进行记账分配，并明确标注“组内分配不表示逐笔历史对应”；它只证明同一人的整组金额等价，不伪造确定请求关系。人工售价不能绕过整组等价检查；条件不满足显示待核查和原因。

最终确认时，主站先在一个 PostgreSQL 事务内认领所有账单和来源、冻结每笔用量与金额，任一认领冲突则全组回滚，不扣费。随后逐笔沿用原生 review → prepared → settle。部分结算成功后重启或重试，仍使用原组成员、原案件和原金额，已成功的成员不再扣费。原生认领已提交而回包丢失时先核对认领；未提交则必须重新检查来源。重新导入时读取历史认领，已结算标记已计费，未完成标记须续办原案件；关联来源别名也不能再次补扣。

2026-10-23 的既有离线 Lingsu 快照中，148 条唯一请求候选和 961 条同用户候选仍保持不变，整组新增可报价数为 0。原文件未保存文件来源的余额 / 订阅配置；即便用同一快照的无订阅案件补充余额类型进行模拟，仍有 108 组缺少共同关联 ID、170 组有组外缺耗时错误来源、1 组来源不足，不能证明完整覆盖，均继续待核查。程序不能补造历史证据或把 961 条全部标为可扣费。148 条 CSV 采购支出合计 47.47758491 USD，不是主站实际报价或已确认用户补扣金额；本轮没有连接生产核价或认领。

### Lingsu 的例子

现有导出表头含 `Time`、`API Key Name`、`Model`、四类 Token、`Duration (ms)`、`Billed Cost` 等，可以直接识别。2026-10-23 这份导出的 `Time` 经原生用量验证为请求结束时间，不能设为开始时间。将 `ccmax-key` 映射到主站对应上游账号，选择自动核对或结束时间，再用 `Time - Duration` 与本地开始时间生成候选。

上游耗时 174 秒、本地错误耗时 125 秒可以是同一次调用；比较的是开始时间，不能要求两边结束时间相同。CSV 的最终 Token 可补足 CDN 超时后本站没收到的部分，但前提是能核对归属和最终账单。此流程无需 Lingsu 提供逐条日志 API，也不会主动读取供应商监控；CSV 替代了上游用量输入，供应商监控的原有后台查单继续独立运行。

旧版可能忽略客户端取消错误、异步日志队列丢弃，或按保留策略清理日志。完整的结构化文件日志也可作为管理员核对的来源，不要求向原生错误表补造记录。需有同一服务端请求 ID 的唯一账号选择、唯一访问结束、用户 / Key / 分组一致，以及失败状态和一致的开始时间 / 耗时；仍需 CSV 唯一匹配及最终用量。CSV 只有上游 Key 名且所有本地归属证据都丢失时无法恢复用户。无候选不表示“无人使用”，不能按比例向其他用户分摊费用。

### 可选文件日志读取

部署时可在运营中心已有容器增加只读卷，并显式传入环境变量。例如现有服务器路径对应的增量为：

```yaml
services:
  operations-center:
    environment:
      OPERATIONS_CENTER_BILLING_LOG_DIR: /app/sub2api-logs
    volumes:
      - /root/sub2api-deploy/data/logs:/app/sub2api-logs:ro
```

合并到现有 Compose，不覆盖已有 environment / volumes；容器非 root 用户须有读取权限。未配置时仍能用原生数据库 / 恢复案件匹配，界面明确提示没有文件日志；显式配置但不可读则整次匹配失败。只读角色还需现有 `usage_billing_dedup` 和 `usage_billing_dedup_archive` 的 SELECT 权限，缺表时显示扣费未核实，权限错误不降级成已收费。

仅读取目录内 `sub2api*.log` / `.log.gz` 常规文件，不递归、不跟随文件符号链接。单次最多 128 个文件、解压后 1 GiB、600000 个窗口内事件、单行 64 KiB，超限或 gzip 损坏停止匹配。日志只提取允许的时间 / ID / 归属 / 模型 / 状态元数据，不保存正文或错误明文；日志轮转、缺行和未挂载均不能当作全量覆盖证明。这是本地代码提供的可选接入，尚未修改服务器挂载或权限。

运营中心将已核对的结构化日志元数据和 SHA-256 摘要作为 `log_source` 提交给核心。它是受管理员认证保护的来源声明，摘要不是签名；核心不会再次独立读取或认证原始文件。核心重新验证身份、时间 / 耗时、失败状态、模型、原生使用记录、持久意图和扣费防重 / 归档，确认时在原事务锁下再次检查。仅有一行错误文本或不完整关联仍不可补记。

CSV 可以没有请求 ID，但用于补记的原生错误日志至少须保留本地请求 / 客户端关联 ID 或原生上游尝试 ID，供核心排除已有账单和持久意图。所有本地关联 ID 均丢失的错误只展示候选，阻止 CSV 确认扣费；不能用 CSV 自带的一个 ID 冒充本地关联证据。

## 价格和资金语义

默认调用受管理员认证保护的 `POST /api/v1/admin/billing-recovery/imports/quote`，报价只读，不创建案件、预留、使用记录或资金效果。有冻结快照时不覆盖；没有快照时复用主站原生模型 / 渠道定价解析、区间价、当前时间规则、用户专属 / 原分组倍率及账号成本规则，并明确返回当前价格来源与报价时间。已知不支持标准 Token 的快照不能降级为当前价。

最终 ActualCost 由主站按 TotalCost × RateMultiplier 并量化到 8 位小数核定；确认使用冻结的预览金额。例如原分组售卖倍率 0.9、账号倍率 0.79 时，按主站模型规则算出标准费后乘 0.9；0.79 用于账号成本 / 限额，不再乘进用户费用。不能简单拿上游 CSV 支出除 0.79 再乘 0.9，因为上游基础单价、缓存规则可能不同。上游采购价、充值折扣及币种换算均不自动套用。

本次 CSV 批量流程覆盖标准 Token 计费。图片、视频、音频、工具收费、特殊 tier / effort 和非标准金额维度不凭这些列推算，应使用“异常请求”的原生维度核查流程。已有记录但少计的请求不通过 CSV 再收整笔费用：已有持久案件的，从最后已结算节点提交最终累计用量，核心生成差额；仅有原版使用记录而没有持久案件的，保留核查结果，不伪造原账或自动补差。

如果核心快照已明确不能进行标准 Token 报价，CSV 流程阻止预览并转上述原生核查，不用一组手工 Token 单价掩盖已知的不支持维度。

确认依次执行：核心预留导入来源 → 保存历史使用记录为 review → 审核为 prepared → 原生 Apply 事务写 `usage_logs`、dedup 和资金效果。仅预留导入来源不会产生使用记录或资金变化。原生服务与运营中心重试都依靠相同核心案件与原生幂等键，回包丢失后先重读结算状态，不新增第二笔消费。

## 防重、持久化和边界

- 同内容文件回到同一批次；每行保存稳定的上游身份摘要。调整时区、时钟或输入缓存解释不会改变其摘要。无请求 ID 的指纹无法识别供应商重新改写时间、模型、Key 名或 Token 后的账单，因此还要依赖本地请求预留和人工核查，不能声称任意 CSV 变体都能全局去重。
- PostgreSQL `sub2api_custom.billing_import_claims` 同时唯一约束上游账号 + 上游账单身份、本地请求来源，绑定预览摘要。重复导出、跨批次和多人同时确认不能为同一来源生成第二笔补记。
- 原生使用明细已清理时，核心仍检查现存 `usage_billing_dedup` 及其长期归档；已有原生扣费键的请求拒绝再建历史案件。只有日志查不到使用明细，不能推断它从未扣费。
- SQLite 与原核查队列共库，增加 `import_batches` / `import_rows` 保存原 CSV、选项、规范化行、候选、预览和回执；不新增资金账本。确认使用版本 CAS 和 5 分钟租约，中断后可恢复；普通未确认预览 1 小时有效，已开始确认的记录按原预览续办。
- 预览前、首次确认前重新读取本地来源，已有用量、归属候选、整批分配、时间 / 状态 / 计费类型、已观察用量或关联文件证据摘要变化时停止补扣；确认后重试继续依靠原生预留和回执恢复。版本 3 / 4 / 5 未开始确认的匹配和预览须重新分析；已进入 confirming / failed 的版本 3 / 4 / 5 补记仍按冻结预览恢复，不受新算法阻断。更早版本继续要求人工核对核心回执，不能另导一份规避冻结。
- 原生日志查询只取归属、模型、时间、计数和关联 ID；不读取提示词、响应正文或日志明文错误详情。导入文件自身原样保留在管理员数据目录，备份须保护 CSV 中的用户 / IP 等信息。
- 每批最大 8 MiB、20,000 行、100 列、单行 64 KiB，账单时间跨度最多 31 天、包含请求耗时的证据时段最多 33 天（另加前后读取余量），最多 20 个上游 Key 映射。每类原生源及持久案件最多 20,000 条，超过即停止并要求缩小范围；时间容差 1–120 秒、时钟修正 ±300 秒。
- 历史请求必须超过独立处理期限加 60 秒。正常意图还须最近一分钟无更新；新建的历史错误 / 日志案件只豁免其新 staging 时间，不豁免原请求的保护期限。已删除用户 / Key / 账号、历史订阅不唯一或归属不一致时核心拒绝补记。

本次版本 6 需要同时更新主站 fork 和运营中心。主站新增受原管理员认证保护的 `POST /imports/reserve-group`、`GET /imports/claims`（完整前缀 `/api/v1/admin/billing-recovery`）及 `custom_20261025_billing_import_groups.sql`，只新增整组认领回执表，保留现有业务表和资金事务。缺少新接口时不开放整组核查，逐笔原流程仍保留；不能仅更新运营中心就宣称已启用跨批次整组防重。仅做 CSV 导入无需新增机器、定时任务或供应商 API 凭据。数据与配置继续按[更新手册](billing-recovery-update.md)备份到同一专用目录；本地实现不代表生产已经部署。

## 本地验证

运行 `npm test`、`npm run check`。`node scripts/billing-import-replay.cjs <外部审计目录>` 可回放此前保存的 `import-rows.json`、`sources.json`、`billing-evidence.ndjson`、`access-events.json` 及两份匹配基线；核对旧误报、已有原生用量和文件日志归属，仅读本地文件、不连接生产、不预留或扣费。可选 `--saved-balance-context` 仅从已保存案件的无订阅情况推断文件来源的余额类型，输出明确标注推断，不代表已核实现存 Key、配额、价格和主站认领。真实证据不纳入 Git。`npm run preview:billing-import` 启动只绑定 127.0.0.1 的隔离演示（默认 19876，端口占用则递增），输出可直接访问的 `/preview` 地址；演示包含一组两笔同用户历史错误，只使用模拟用户与结算状态，不连接真实数据库或上游，`/sample.csv` 提供示例文件。
