## 两类问题需要分别处理

1. **页面将预期的请求取消误报为故障，已本地复现同一句提示。** 延迟列表请求，立即切换到采集状态，旧请求由 `ConversationLogsUi.load()` 的 `AbortController.abort()` 主动取消。模块内部的事件处理忽略 AbortError，但首次加载的拒绝沿 `loadCurrentView()` 外层 catch 继续上抛，后者没有过滤取消，遂显示数据源异常和英文提示。正常取消不能证明采集失败或日志损坏。
2. **生产运营中心实际失去响应，不能仅隐藏提示。** 源站 `/healthz` 也超时、容器 unhealthy，主 Node 进程阻塞于读取对话归档数据库。当前有较强的磁盘读取与内存回收压力证据，状态 / 列表全表聚合和大正文同步解密读取是代码中对应的阻塞路径；没有直接采集运行中的 SQL，不能唯一指认某个 HTTP 请求或某条语句。

## 修复建议

这些改动均可限定在运营中心，无需修改 sub2api：

1. 外层页面加载识别 AbortError 与过期加载结果；切换视图、刷新或退出引起的取消不弹错误，真实服务错误仍显示。仅翻译或屏蔽英文不能解决服务失去响应。
2. 将统计、列表 / 会话 / 导出和正文解密读取移到受限的独立读取进程，限制并发、队列与执行期限，合并重复读取；主 HTTP 进程及时响应健康检查、策略读取与归档转发。
3. 统计 / 筛选使用紧凑元数据、合适覆盖索引及有失效机制的汇总缓存，避免从大正文表反复全表聚合。历史索引 / 元数据回填需限速并避让归档，不能在启动或首个页面请求里无期限同步建索引，更不能直接对线上大库做一次性改写。
4. 详情和正文按需读取，预览与完整下载分开限制工作进程资源，保持归档原文字节不变，不以截断正文解决性能问题。单纯提高内存或重启只能缓解现象，仍需移除主进程同步重 IO。
