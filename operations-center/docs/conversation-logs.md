# 对话日志接入

本模块随 `fjiangming/sub2api-extra` 的 main 发布，配套 `fjiangming/sub2api` 的 dev 采集器。主站负责鉴权后识别用户和旁路读取上游正文，运营中心负责独立归档、策略、脱敏和查询，不写主站业务表，不参与余额或计费。主站新 dev 基于上游新 main，不包含此前旧 dev 的计费恢复定制；运营中心既有模块遇到缺少旧 API 时沿用其不可用 / 降级处理。

## 持久接收与后台处理

新归档在独立接收进程校验并加密保存原文后即确认接收，随后由独立处理进程检查完成证据与脱敏。页面显示“原文已保存 · 待处理”，后台完成后自动刷新；仅脱敏模式也暂存加密原文，成功且无检查范围警告后才移除。处理故障保留原文，可重新处理。待办有持久重启恢复 / 容量 / 次数上限，自动推送仍先等待该阶段结束，不跳过待处理游标；手动下载或批量推送可按“脱敏优先、不可用则原文”规则使用已保存原文，并保留待处理回退原因。

主站配套改进包含在途读取收尾、归档退避，以及明确终态 / HTTP 错误关闭时的受限后台原始补读。用户返回不等待 EOF 或归档，同一上游客户端有新请求时旧补读立即让行，不改变原推理、用户超时、计费或 failover。运营中心部分先独立升级即可兼容旧采集器；主站收尾与调度优化需要另行更新 dev。无需新增环境变量 / 卷，保存策略与历史保留。具体优先级、默认边界、完整性设置、升级与回滚见[可靠性说明](conversation-reliability.md)。

## 查询与历史索引

状态、列表、会话、CSV 索引导出、详情和正文读取均由运营中心的独立低优先级子进程处理，主 HTTP 进程只鉴权和流式转发。汇总 / 筛选使用同库紧凑元数据表，不再反复扫描含大型加密正文的 `cl_records`。HTTP 详情不解密正文，WebSocket 帧详情及正文仅在需要时读取所选副本；原文、格式、压缩字节和保存完整性标记不变。页面的 64K 预览仍只是显示限制。

首次升级只加空元数据表、索引和同步触发器，不在启动或首个查询里扫描全部历史。新归档及重处理 / 完成证据更新 / 清理在原事务中同步元数据。旧记录后台按最新时间逐条准备，每秒最多一条，避让归档、清理和历史检查；活跃回填也会被归档活动或交互读取中止，稍后重试。每条先在短写锁之外读取旧元数据，再通过 1ms 写锁和并发复核写入，不能覆盖刚更新的副本或复活已删除日志。原始密文不重写、不解密、不截断，不做全库压缩或强制 checkpoint。

准备期间显示“历史日志索引正在后台准备”及条数进度，列表 / 会话和相应汇总只代表已准备的记录；全库记录数仍可用，未完成的全库完整性 / 正文字节汇总显示“准备中”。JSONL 下载与兼容 CSV 索引 API 暂时拒绝，避免误导为完整范围。页面每 5 秒刷新准备进度，离开后取消；服务重启后从缺失记录继续。大量历史或持续繁忙时可能需要较长时间，正常保存新日志无需等待。

读取进程最多一个、同时一项请求、最多八项等候；排队 5 秒、读取 15 秒、单条回填 10 秒后明确失败并回收相应进程。客户端取消正在执行的读取只回收读取进程，不重启归档或主站。空闲 15 秒退出，下一次按需启动。子进程 old-space 上限 192 MiB、SQLite 缓存 2 MiB；启动至少预留 96 MiB 可用预算，正文 / WS 解密另按当前共享内存和堆余量准入。解压文本另按解密后的剩余预算限制输出，文本查看不足时明确拒绝；直接原始下载不解压，JSON 原始字节接口仍可返回原 base64。内存不足返回可重试的错误，正文仍完整保留；极大的日志可能需要资源充足时再读取。此为资源保护，不能用以承诺任何大小都可在 512 MiB 容器内解密。

正常切换视图、刷新或退出导致的 AbortError 不再弹出 `signal is aborted without reason`，同视图过期加载也不能覆盖新状态；真实超时 / 服务故障仍显示。升级只需运营中心，既有 sub2api 采集端不变。进程隔离消除了这些查询在主 Node 事件循环中的同步阻塞，但同宿主 CPU / IO / 内存仍共享，不能保证绝对零性能成本。线上现象、范围和证据见[只读诊断](conversation-diagnostics-20261117-abort-stall.md)；该历史报告不表示本次已经部署。

## JSONL 下载

“请求日志”筛选区下可设置“最近条数”和“导出副本”，点击下载按钮取得 `.jsonl`。最近条数为 **1–10,000，默认 1,000**；采用当前搜索 / 日期 / 协议 / 完整性 / 会话等筛选，按日志时间从新到旧，同毫秒按 ID 升序，与列表一致，**不受当前分页影响**。后台开始读取时固定最新 N 条；此后新增日志不挤入这次下载。缺少副本的记录会计入选中和跳过数，不拿更早的记录补足 N 条，实际导出数可能小于 N。

每行与新推送一致，**仅含 `request_id`、`request`、`response`**，请求 ID 直接取已归档的网关字段，不外发 schema、用户元数据、处理状态或摘要。有效 UTF-8 正文直接输出字符串，gzip / br / deflate / zstd 在后台受内存预算限制解压，不解析重排正文 JSON，保留大整数、数值拼写、未知字段、空白、BOM 和 SSE 分隔。WS 按两侧输出消息数组，无法解码的字节以 data URI 无损保留，具体规则见[接收格式](#接收格式)。外层 JSON 对引号 / 换行的转义在读取一行 JSON 后还原。文件本身为 UTF-8、每行一个 JSON 对象、LF 结尾、无 BOM，不将多次请求合成一个会话。下载是当前筛选的一个文件，不按模型分卷；日期 / 模型分组和 10 GB 滚动仍由 S3 推送完成。Request / Response 面板的 `.raw` 下载继续用于原传输字节诊断，旧 `/index` CSV API 保留兼容。

默认“脱敏优先（不可用则原文）”，沿用当前用户排除和模型名单。尚在后台处理、处理失败、脱敏副本缺失、部分内容未检查或脱敏规则过期时，有保留的原文就逐条回退，不因此省略该条；脱敏密文损坏或读取失败且原文正常时也可回退。实际副本 `source`、请求副本 `requested_source` 和回退原因 `fallback_reason` 仅用于内部跟踪，不加入新下载的三字段数据；原归档字节、WS 帧、处理异常和完整性诊断保持，不能把回退行称为已脱敏。页面显示实际回退条数与原因，文件名为 `masked-or-original`，可能含未替换敏感信息。两份均缺失或被当前用户 / 模型规则排除的记录仍明确显示原因，不用更早记录填补；丢失或超出筛选的轮次无法补回，不承诺整个会话必然完整。传输未确认也允许下载，本地保留 `complete=false`、原 `reason` 和诊断；如只需完整采集，先选对应筛选。全部选中记录不可导出或筛选为空时明确报错。

下载由**另一个独立低优先级只读进程**执行，单并发、192 MiB old-space、2 MiB SQLite 缓存、默认 2 MiB/s，逐条解密、小块输出和 HTTP 背压；不阻塞普通查询队列、不把整个文件放入主进程 / 页面内存，也不额外落地明文文件。按记录及约 256 KiB 输出检查点避让采集、待处理、历史任务和交互读取；已开始的单条读取 / 解密无法被抢占，仍共享宿主资源。连续繁忙超过 30 秒、单次超过 24 小时、内存不足等会中止下载，不修改原归档或回退主线程处理。

导出内存准入按本条实际可能读取的副本长度估算，不再将原文与脱敏副本的总存储量相加放大；正常脱敏可能回退原文时按两者较大值预留。读取长度只取 SQLite 标量，不预加载正文。总可用内存和 V8 堆分别预留副本长度的 8 倍和 4 倍加 1 MiB，两者各保留 32 MiB 余量，避免将密文 / 解码 Buffer 的全部外部内存成本误算入 192 MiB old-space。下载直接按共享正文规则生成三字段输出，省去内部摘要与正文重复转换；加密认证通过后才解析原文，无需的整份明文 Buffer 拼接也被省去，旧推送格式不变。

每条输出后释放正文及序列化迭代器；内存压力时仅在独立下载进程回收已释放内存，最多等待 **30 秒**再检查，页面显示“等待导出内存释放”，继续保留当前条的采集 / 会话 / 保存规则及删除保护。启动前不足 96 MiB 预算时也先等待，等待期间不启动子进程，仍支持取消和会话失效；队列期限覆盖该等待和正常启动。一次回收重试后，仅当总可用内存或堆预算回升至少 1 MiB 才再次准备，避免持续重读大正文。真正不足仍明确失败，不跳过、不截断、不改变输出表示；压缩解码仍有独立动态预算，大单条错误附请求 ID 和副本大小，减少总条数不一定有用。原文回退统计与内存错误无直接等价关系。本地已验证 20.1 MiB 副本位于 100 条中的第 43 条及更大的 WebSocket 日志完整导出，但这不承诺任意大小或生产共享内存不足时均可导出。

创建 / 取消需要管理员与 CSRF；状态仅属于创建会话。下载使用两分钟、一次性、固定筛选 / 副本 / N 并绑定原实时会话的票据，支持内嵌页只有 Session header、无 Cookie 的情况，URL 不含管理员 Session。取消、登出 / 会话过期、输出期间检测到所选记录删改或保存规则更新、连接 / 进程中断都会停止本次输出；已发送到浏览器的字节无法撤回，失败下载不应作为完整文件。成功需后台完整生成、字节数与最终回执一致且向浏览器连接发送结束；页面“导出已发送”不等于证明浏览器已写入磁盘。导出任务及票据只在内存保留，重启后需重新发起下载。

正常完成、失败、取消或断连后都会终止对应下载进程，由操作系统回收其正文、堆和 SQLite 缓存，无需刷新页面；主进程只保留最多 20 项不含正文的任务状态，容器总内存仍含常驻服务及系统文件缓存，不承诺归零。新下载等待旧进程实际退出，不重叠运行；旧进程启动失败只结算其原请求，不能误伤刚提交的替代下载。刷新页面不会修复大单条的内存需求；失败下载中已导出的部分行不能当作整个选中范围已导出，应以新任务完成状态、条数和摘要为准。

本功能仅需更新运营中心，无新增强制主站或数据库配置。仓库 Compose 和 `.env.example` 的内存默认已改为 **1 GiB**，CPU 保持 **1 核**，可通过 Compose 插值变量 `OPERATIONS_CENTER_MEMORY_LIMIT` 覆盖。镜像无法自行改变宿主机容器配额；既有服务器需采用更新后的 Compose / 插值配置并重建运营中心容器，已有显式 `512m` 或自有 Compose 的限制仍要分别调整。内存保护保持，大单条仍可能暂时无法导出。配置细节见 [JSONL 服务器清单](conversation-jsonl-push.md#服务器配置待确认)，本轮不自动应用服务器变更。

## 待确认的接入配置

先更新两个程序，再接入私有网络。以下是参考配置，本次不会应用到服务器。

主站环境变量：

```dotenv
CONVERSATION_LOGS_URL=http://operations-center:9872
CONVERSATION_LOGS_TOKEN=<独立随机值，至少32字符>
```

运营中心环境变量：

```dotenv
CONVERSATION_LOGS_TOKEN=<与主站相同的值>
OPERATIONS_CENTER_DATA_DIR=/app/data
OPERATIONS_CENTER_IMAGE=ghcr.io/fjiangming/sub2api-extra:operations-center-latest
```

`operations-center` 主机名要求两个容器共享可解析的私有 Docker 网络；分开运行时，应先核查网络、服务名和已有挂载。主站 URL 仅允许 HTTPS 或私有 / loopback HTTP，不经系统代理、不跟随重定向。不要向公网额外开放采集端口。现有管理员登录 / SSO 和 CSRF 保护继续适用，采集 token 不具备管理员读取权限。

先在“对话日志 → 保存策略”选择排除用户、采集模型、保存版本和容量，再启用保存。新建默认关闭，原文与脱敏双副本、保留 7 天、容量 10 GiB、预留磁盘 2 GiB；升级不覆盖已有容量和保留期。保留天数设为 0 可永久保留。空间不足整条拒收，不清空正文后写一条假日志，不淘汰历史，也不阻断推理。新版已移除单条正文上限配置；两端均需更新，页面会提示旧采集器。

归档容量按数据库有效占用加完整 WAL / SHM 文件计算；SQLite 已释放的内部空页和等待 checkpoint 缩小的尾部空间不再占用归档配额。清空 / 删除后无需先压缩整个数据库即可恢复采集，但仍必须满足真实磁盘预留要求；页面分别显示计入容量、文件占用、可复用空间和当前暂停原因。页面统计读取失败时保守按物理文件全额计算，不放宽容量保护。文件不立即缩小属于正常复用，WAL 本身达到上限或磁盘预留不足仍会暂停；本改动不在请求、策略读取或清空完成时加入强制 checkpoint / 全库压缩，也不自动提高现有容量上限。此修复只需更新运营中心，无需再更新主站。

排除按主站鉴权用户 ID，覆盖其全部 API Key。采集前、发送前和接收端入库前检查，策略读取失败则停止本次采集。保存排除后，尚未入库的记录也会丢弃；不新增正文、用户元数据、索引、会话和该用户缺口。已存在的历史归档不会隐式删除，仍按当前保留期清理。主站原有业务用量和原生诊断记录属于原有功能，不受本归档开关控制。

## 采集模型

在“保存策略 → 采集模型”开启“仅记录所选模型”，每行填写一个模型名（最多 100 个、每个最多 200 字符），另可勾选“Kimi K3 及后续版本”。名单为空且 Kimi 未勾选时不记录任何模型；关闭筛选则恢复按其他保存条件采集。

按网关实际发送给上游的模型匹配，不使用客户端改写前的别名，也不改变原始正文或模型字段。忽略大小写及空格；Fable5 / Fable5.1 和 Opus5 / Opus5.5 兼容 `claude-fable-5` / `claude-fable-5-1` 和 `claude-opus-5` / `claude-opus-5-5`，Gemini carbon 对应 `gemini-carbon`。其他模型与版本按名单精确匹配，不自动包含 Fable5.2、模型日期后缀或其他 Gemini 版本。Kimi 范围包含 K3、K3.1、K4 等后续版本及常见版本后缀，不包含 K2 系列。

新建归档的建议名单为 `gpt-6-astra`、`gpt-6-sol`、`gpt-6.1-sol`、`gpt-5.6-sol`、`claude-fable-5`、`claude-fable-5-1`、`claude-opus-5`、`claude-opus-5-5`、`gemini-carbon`，并勾选 Kimi K3 及后续版本。旧加密策略升级时保持原采集范围，模型筛选默认关闭，需显式保存新策略；旧客户端未提供模型配置时保留当前模型设置。

主站在后台完成 HTTP 正文组装和模型识别，再检查原始及当前名单，运营中心入库前也会检查；不匹配或无法识别时不新增正文、元数据、索引、会话或该模型缺口。在途旧策略也必须符合当前名单。HTTP 从实际请求体或 Gemini / Vertex 的 `/models/` 路径取值；WebSocket 兼容顶层 / response 内的模型及同租约后续消息段继承。识别前只使用有界内存观察，不写原文临时文件，不阻断推理。

用户排除始终优先，即使模型已选中仍不采集该用户。历史记录不因名单变化被删除，仍可读取；当前名单外的历史记录不能通过重新处理写入新副本。启用此功能需更新主站采集器和运营中心。

## 清空全部历史

对话日志各视图顶部的“一键清空历史”在确认后提交后台任务，清空**任务被服务器接受前**所有已入库的对话日志：包括全部用户、全部模型（含未知模型）、原文、脱敏副本、处理异常 / 正文缺失记录、查询和会话索引，以及关联的本地推送任务和 JSONL 成员快照。不受当前筛选、模型名单、用户排除或保存开关限制。已发送到外部接口 / 存储的数据不会被撤回；聚合推送文件的操作状态 / 路径及清理审计计数保留，不包含已删除的对话正文。

保存策略、加密密钥和归档开关保持。固定入库 rowid 上界并复用现有推送的单调到达序号，避免最高旧行被并发过期清理后 rowid 复用而误删新日志；无需解密 / 复制全库正文或回填历史序号。任务接受后才入库的请求（包括先发起、后完成的对话）保留。因此采集开启时，清空完成后仍可能显示新日志；如需持续为空，可另行关闭日志保存，对话服务仍正常运行。

点击返回后台任务与进度，不同步等待全库删除。重复提交同一 `request_id` 始终复用原任务，完成后重试也不会扩大范围；再次明确点击会创建新的清空范围。与名单外模型清理互斥，可先停止原任务。页面支持“停止清空”、刷新查看和关闭后继续；已删除记录不能恢复，停止不回滚已完成批次。任务持久化，进程故障 / 服务重启后续办；保存策略变化不扩大既定范围。

复用独立低优先级清理进程及每批最多 1 条删除 / 250ms 间隔。每批派发前避让活跃归档；SQLite 写锁等待 1ms、繁忙退避 1 秒、单批 10 秒期限、进程故障后每 5 秒续办，管理触发 / 停止也使用 1ms 写锁等待。不解密正文、不整库 VACUUM、不强制 checkpoint、不停止服务、不调用主站计费或修改用量余额。释放的加密 BLOB 页留作 SQLite 复用，数据库文件未必立即缩小；仍共享宿主 CPU / IO，无法保证严格零开销。

管理员 API：`GET /api/conversation-logs/history-clear` 查询本类最近任务；`POST` 同路径提交 `{ "request_id": "<UUID>", "confirm": "clear-all-history" }`；`POST /api/conversation-logs/history-clear/:id/cancel` 停止本类任务。写操作要求管理员会话、CSRF、限流及明确确认值；采集 token 无权调用。升级不会自动创建清空任务。本功能只改运营中心，无需修改 sub2api 源码。

## 历史模型清理

“对话日志 → 保存策略”底部的“后台清理名单外日志”按当前**已保存**的采集模型名单执行。先开启“仅记录所选模型”，保存至少一个模型或 Kimi 范围；存在未保存更改时不能启动清理。匹配规则与新日志采集相同，兼容上述别名和 Kimi 版本范围；无法识别模型的旧记录也属于删除范围。

点击只提交后台任务，不等待全库完成。任务固定启动时的历史边界，分批删除名单外记录的原文、脱敏副本、索引及关联的本地推送任务 / JSONL 成员；所选模型和后续合规新增日志保留。已发往外部的副本不会被撤回。页面显示扫描 / 删除计数，关闭页面仍继续，刷新可恢复查看；重复点击复用活动任务。

“停止清理”在当前小事务结束后生效，不撤销已经完成的删除。任务和游标持久化，进程故障或服务重启后继续同一任务；模型名单或 Kimi 范围的实际语义改变时自动暂停，核对并保存新名单后可重新点击创建任务。其他保存设置变化不扩大本次删除范围。删除不可恢复，不会在升级或单纯修改名单时自动执行。

清理由独立低优先级进程执行，96 MiB old-space；每批只读取最多 64 条模型元数据、最多删除 1 条，批间隔 250ms。SQLite 写锁等待 1ms，忙时退避 1 秒，不读取 / 解密正文，不调用主站或修改用量、余额。没有活动任务时不启动清理进程。仅清理连接关闭加密 BLOB 的空闲页覆写，保留其他连接的原安全设置；不执行全库 VACUUM 或强制 checkpoint。删除空间留给 SQLite 后续复用，数据库文件不会立即缩小。

这项功能只需升级运营中心，沿用现有数据卷；与主站 PostgreSQL 的“清理控制”模块独立，不受该模块的 `OPERATIONS_CENTER_ENABLE_CLEANUP` 开关控制。主站推理不等待清理，但 CPU / 磁盘仍共享，不能承诺严格零开销。磁盘或存储繁忙时清理让出机会，优先继续正常对话和采集。

管理员 API：`GET /api/conversation-logs/model-cleanup` 查询最近任务；`POST` 同路径提交 `{ "policy_version": <当前保存策略版本> }`；`POST /api/conversation-logs/model-cleanup/:id/cancel` 停止。写入接口复用管理员会话、CSRF、限流和策略版本校验，采集令牌不能调用。

## Raw 和完整性

保存的是网关实际发往上游的请求正文、HTTP transport 暴露给网关的响应正文，以及上游 WebSocket 应用消息。保留原字节，不对原文 JSON 解析后重新序列化；未知字段、大整数、数值写法、空白和 SSE 顺序保留。入库 envelope 用 base64 承载字节，下载 `.raw` 时还原原字节，页面附 SHA-256。

这是应用正文归档，不是 TCP / TLS 抓包，不保存 Authorization 等 HTTP Header 或 URL 查询参数。若底层 HTTP transport 已自动解压，保存其解压后的原正文；若仍带 Content-Encoding，则保存压缩字节。查看支持 UTF-8、gzip、br、deflate；不支持的编码和二进制可在“仅原文”模式保存 / 下载。不会为了采集修改原有压缩协商或推理请求。

HTTP 每次真实 RoundTrip 独立保存，包括 TLS 指纹请求、账号切换和 Grok 回退。同次入站共享随机请求编号。WebSocket 在当前租约 / relay 边界归属身份；保留消息方向、次序和相对时间。池化连接不会沿用连接创建者的用户身份；WebSocket Host 无可靠采集值时显示未提供。只保留一个完成事件以内的消息段，连接关闭前未见结束事件会标记不完整。

会话只使用客户端 `session-id` 经按用户、Key 加盐 HMAC 的标识关联，不按文本相似、时间或 IP 猜测。未提供标识的请求仍可独立查询。同会话内同次请求的重试不重复计算请求数。排除 / 策略读取失败的持续 WebSocket 连接需要重连后恢复采集。

“完整采集”表示已读完上游应用字节或见到该 WebSocket 段的结束事件，不代表模型成功、SSE 语义结束或业务计费成功，也不保证多轮会话没有缺失。新采集器不再按单条大小或 10,000 帧截断；Request、Response 和帧元数据共同受原有 64 MiB 全局观察预算保护，队列 32。单条或并发占满预算时整次放弃归档，释放全部已采集内容并累计丢弃，不保存前缀、不等待磁盘、不阻断用户流式返回。64 MiB 是观察预算，组装 / 编码 / 发送还需要额外堆内存，不能理解为进程总 RSS 上限。

采集策略在后台每秒刷新，读取超时 200ms；缓存超过 3 秒、读取失败或启动尚未取得有效策略时跳过采集。发送前、每次重试前和入库前再检查用户 / 模型，因此缓存窗口不会使新排除的用户落盘。单后台 worker、每次发送超时 2 秒、最多 3 次同 ID 重试；核对包含字节长度、两侧正文及帧顺序 / 方向 / 时间 / binary 标记的 SHA-256，回执 ID / 摘要不匹配不计为成功。发送不会持有正文读取锁。无磁盘 spool、跨重启恢复或退出强制排空，也不补发推理。丢弃统计不附用户身份，重启归零，多实例显示最近上报值。

HTTP 合并 16 KiB 观察块；WebSocket 热路径只复制 / 非阻塞排队，由独立 worker 解析，待处理队列 16,384 项。缓存 / WS 锁竞争、队列满或预算不足均放弃受影响采集并继续对话。发送按块编码，不组装巨大的 base64 JSON。正文复制、后台 GC 和宿主资源竞争仍有开销，不能承诺首字或总耗时严格零影响；[性能复核](conversation-performance-review.md)记录实际测量和边界。

正式接收与后台处理分别在独立低优先级子进程执行，主 API 只流式转发。接收单任务，忙 / 不可用 / 动态内存准入失败时整条拒收；原文提交后另有最多 10,000 条持久待办，处理单任务并让行新接收。各自 20 秒后台期限、5 秒退出重启、256 MiB old-space，另按 cgroup / 系统空闲及堆余量准入；不会回退到主线程同步处理。后台处理 / 定时过期清理 / 查询 / 推送和共享 IO 仍有负载，动态资源保护可能拒收大日志。接收最终事务复核当前排除用户 / 模型 / 开关；处理发布另复核当前规则、排除 / 模型 / 保留期 / 空间和任务代次。

## 脱敏与存储

三种模式：原文 + 脱敏副本、仅脱敏副本、仅原文。默认八类规则为邮箱、电话、密码 / 凭据 / 验证码、身份证 / 护照等证件、银行卡 / 金融账户、姓名 / 地址等个人资料、IPv4 / IPv6、设备 / 社交标识；各自可关闭，另支持最多 50 条字面量替换。中国身份证、卡号和 IBAN 的自由文本识别复用 validator 校验；其他证件、姓名、地址、生日、定位、健康资料等主要依赖字段 / 文字标签，不能等同于任意自然语言识别。具体覆盖和边界见[完整性与敏感信息评估](conversation-integrity-privacy.md)。

脱敏定位 JSON 字符串和数字 token，保留字段名、未知字段、未修改的数值拼写和包装。敏感数字替换为字符串占位符，因此仅该敏感值会改变 JSON 类型；原文字节不变。角色、消息 / 工具关联 ID、工具名、模型按协议位置保护，普通客户对象中的 id / name 不再一律跳过。协议 ID 不按电话识别；自定义规则若会改变关联字段则整次处理失败。同一类型且完全相同的值使用稳定 HMAC 占位符，不落盘保存反向映射。结构化已识别的部分个人值也会替换同一负载的文字引用；不把短姓名替换进其他英文单词。

OpenAI Responses / Chat、Claude 和 Gemini 常见流式文本按消息组拼接脱敏，再映射回原事件；保留消息、角色、工具关联、事件顺序、未知字段、多行 SSE、CR / LF / CRLF、NDJSON 和文本。合法内嵌 JSON 字符串递归处理，普通工具文字及不完整参数按文本规则处理，不删除整轮消息。支持运行时可用的 zstd；原文下载始终保留原压缩字节。处理解压上限 256 MiB 或其他处理资源边界只会使脱敏失败并保留原文，不会截断原文。

按用户明确指定的异常策略，自定义规则冲突、无效 JSON、编码 / 解压、二进制，或未兼容的媒体 / 外部文件 / 未识别签名 / 加密正文无法完整检查时，保留收到的 **AES-GCM 加密原文**（包括“仅脱敏”模式），整次不生成脱敏副本，不将无法检查的内容标为已脱敏。已知协议图片、签名和加密推理的有限检查兼容见下文，仍保留原文并禁止脱敏推送。页面正文旁显示安全分类与“重新处理”，不在异常文本中泄露原始片段。采集完整性与处理状态独立：读取完整但处理失败仍是完整采集；资源丢弃或提前断流的字节不能凭空补齐。

脱敏引擎 v5 延续按字段上下文区分普通 HTTP URL 和实际媒体引用。消息 / 工具中的普通 `url` 不再仅因是链接而报错；URL 只在内存解析，不访问目标，按原有规则替换路径、凭据和参数中的敏感值，保留非敏感组件、参数名与拼写。异常百分号编码无法可靠检查时仍回退原文，图片 / 音频 / 文件引用不会被当成普通链接放行。

已确认路径的 Claude thinking `signature` / `signature_delta` 和 Gemini `thoughtSignature` 原样保留，其余可读文本继续脱敏。记录新增独立 `inspection_warnings=["OPAQUE_SIGNATURE"]`，页面显示“可读文本已处理 · 部分内容未检查”，不再把整次文本处理视为失败；即使“仅脱敏”也保留加密原文。只对已知协议位置的签名做此兼容，工具内嵌 JSON、任意客户对象的同名字段或疑似明文敏感值不享受豁免。自定义规则若会改变签名仍报告保护字段冲突。Gemini 工具名及调用关联 ID 同样按确切协议位置保护，工具参数中的普通姓名 / ID 仍脱敏。保留签名不代表检查过其内部，也不保证修改文本后的副本能通过厂商签名校验或用于原协议回放。

“处理策略 v5”等数字是处理时使用的保存策略版本，不是错误等级或脱敏引擎版本。旧引擎的普通链接 / 协议签名异常，可用保留的原文按新引擎重处理；不会升级时扫描或自动改写全库。“读取中断”是采集侧非 EOF 错误的统一分类，可能包含应用终止事件之后的传输异常；本次兼容不修改采集完整性、不补齐原文字节。线上有限抽样及其局限见[2026-11-17 诊断记录](conversation-diagnostics-20261117.md)。

v4 识别 Responses 请求 `input[].type=reasoning`、响应 `output[]`、确切 `response.output_item.added / done` 的 `item`，以及对应 `response.create` / 响应事件包装中的 `encrypted_content`。只对确切字段、协议路径和不透明编码值原样保留，添加 `OPAQUE_ENCRYPTED_REASONING` 检查范围警告，其余可读内容继续脱敏。真实 reasoning 项的 ID / 类型 / 状态和 summary 类型也按协议位置保护，避免破坏 item_id 关联；普通业务对象仍按数据处理。嵌套工具数据中伪装的协议不享受豁免；自定义规则碰到加密值或这些协议字段仍报保护字段冲突。警告记录始终保留精确加密原文，默认脱敏推送门禁与签名相同。

v5 对有模型信息的 Responses `input[].content[].type=input_image` 和 `input[].type=function_call_output / custom_tool_call_output` 的多模态 `output[].type=input_image`，以及 WS `response.create` 的对应位置，原样保留 `image_url`。同时兼容 Chat `messages[].content[].type=image_url` 的 `image_url.url` 与 Claude `messages[].content[].type=image` 的 `source`，核对角色、确切路径、类型和图片编码 / HTTP(S) 引用格式；工具返回还须有字符串 `call_id`。数据 URL 只接受已知图片 MIME 与 base64 形状；不解码、转换、重压缩或下载图片，不修改原 JSON 拼写、消息顺序和工具关联。自定义规则会改写图片值或已识别图片类型 / 来源元数据时仍整次失败；未知位置、内嵌工具 JSON 伪装、其他媒体和未知加密字段继续保护。

Claude 的 `messages[].content[].type=tool_result` 内 `content[].type=image` 也按确切路径兼容，要求消息角色为 user 且有字符串 `tool_use_id`，图片来源沿用已知 base64 / HTTP(S) 格式检查。工具返回文字继续脱敏，图片、来源元数据和工具关联原样保留；缺少关联 ID、错误角色 / 类型、内嵌业务 JSON 的协议伪装不享受兼容。

这些图片添加 `OPAQUE_IMAGE`，页面显示“协议图片原样保留”，可读文字继续脱敏，并明确图片中的文字、人脸等敏感信息未识别。外部图片引用可能包含凭据，保留引用不等于移除敏感值；含图片警告的副本仅供管理员查看，不可通过 webhook / S3 或 JSONL 脱敏推送，旧队列也重新核验。即使“仅脱敏”也保留精确加密原文。图片兼容不清除原 `read_error` 或改变传输完整性，不保证 OCR 或匿名化；旧图片异常需要单条“重新处理”或管理员显式启动后台检查，升级不自动扫描历史。根因与只读重放记录见[图片兼容诊断](conversation-diagnostics-20261117-images.md)。

v6 补齐 Responses 加密压缩上下文：确切请求 `input[].type=compaction`、JSON `object=response.compaction` 或 `object=response` 的 `output[]`、`response.output_item.added / done` 的 `item`、已识别响应事件和 WS `response.create` 包装中的对应项。`encrypted_content` 和协议项 ID / 类型 / 状态保持原 JSON 拼写，其余可读文本继续处理，添加 `OPAQUE_ENCRYPTED_COMPACTION`。不解密或用占位符替换压缩内容，避免破坏后续上下文；加密内部仍未检查，始终保留加密原文，禁止其脱敏副本外推。普通业务 / 嵌套工具数据中伪装的同名字段不享受豁免，自定义规则冲突仍失败。旧异常需管理员显式重处理，原始 read_error 不会因此消失；升级不主动全库扫描。排查证据与无法承诺完美兼容的边界见[本次诊断](conversation-diagnostics-20261118-capture.md)。

真实工具参数 / 结果内的普通业务 `file_id` 按证件标识策略一致替换，关联文字中相同值也会替换。识别依赖工具协议上下文，贯穿合法内嵌 JSON 和参数流分片；不因其为数字就全面放行。媒体类型 / MIME / 文件对象下的字段、实际 `file-...` 等上传引用和任意未知位置的同名字段仍按不可检查处理，不下载文件，也不改变工具调用关联 ID。

## 运营中心兼容检查

这部分只需更新运营中心，主站现有采集端和环境变量无需变化。新归档在隔离归档进程中生成独立的 `upstream_status` / `upstream_evidence` / `completion_source`，不改变采集原始 `complete` / `reason`。严格解析 JSON、SSE 完整事件和收到的 WS 帧，检查 Responses 完成 / 失败 / incomplete、Chat finish reason、Claude message_stop、Gemini finishReason；字符串中的假完成事件、无事件分隔符、后续坏 JSON、矛盾状态或未结束的新响应均不能当作完成。所有 WS 入站消息段都参与检查。

完成检查 v2 同时识别正文开头的真实 SSE 字段 / 注释，兼容采集协议标记为 JSON、正文实际是 SSE 的上游。仍解析全部事件、核对类型 / 状态和完整分隔符，不以正文字符串包含 `response.completed` 判定完成；JSON 字符串内伪造事件、截断尾部、错误后续事件均继续保护。保留原协议标记、原文字节、原 `complete / reason` 和推送资格。旧检查 v1 可通过显式后台兼容检查升级；仅剩脱敏副本时只注明该副本的完成证据。

`read_error` 是采集器记录的非 EOF 读取错误，可能发生于请求或响应，也可能为完成后的取消；现有记录没有底层错误枚举、发生侧或发生顺序，不能据此认定供应商中途断流或日志写入中断。采集器在收到有效应用结束事件后仍可能因底层连接异常保留该标记；也可能确实缺失字节，因此不能只根据应用完成就覆盖采集完整性。[连接与近期日志只读排查](conversation-diagnostics-20261117-connection-integrity.md)记录了实际核验范围。

应用检查最多解码 8 MiB，且受动态内存预算约束；超过预算 / 二进制 / 格式不兼容只记无法核验，不截断原文、不把该分析当作采集成功条件。原采集异常但已核对上游完成时显示“上游已完成 / 传输结束未确认”（原“传输采集异常”），不能证明请求、响应或用户下游逐字节完整。历史仅剩脱敏副本时显示“副本含完成事件”，不当作原文证据。外推仍要求原始完整采集，不能只因应用状态为 completed 就放行。

可选的读取诊断 v1 需要配套新版主站采集器。运营中心在原策略响应中声明 `transport_diagnostics_version=1`，新采集器在首次发送前读取新策略，仅对支持的接收端附加 `transport_diagnostics`；旧采集器忽略此能力，新采集器对旧中心保持原 envelope。请求 / 响应分别记录已观察字节、声明长度（-1 表示未知）、是否读到 EOF、首次读取错误枚举（cancelled / deadline / unexpected_eof / closed / timeout / network / other）和该错误返回时 Close 是否已开始。不会保存错误原文、URL、令牌或上下文正文；数字与归档原始字节数核对。只加源表的默认空标量列，按主键读取详情，列表 / 汇总不读取正文、不迁移紧凑元数据或扫描历史。

诊断不追加读取、不等待 EOF、不重试用户请求，不更改取消和原错误。关闭阶段只说明观察顺序，不能证明关闭导致错误；归档结束后的晚到读取不会再改变已发送事件，也不为取得错误详情等待后台 reader。首次发送选定的字段在重试中保持不变；如果中途接收端降级为不支持，则放弃该归档并计入丢弃，不改指纹重新投递。建议先发布运营中心再升级采集器，无新环境变量或策略开关。历史未采集这些字段只能显示“无法区分具体原因”，重新处理不能补造信息或恢复缺失字节。

归档、重处理与 JSONL 推送使用同一内存估算：兼容 cgroup v1 / v2 和宿主 MemAvailable，仅折算一半干净 inactive file 缓存，排除共享、dirty / writeback 等，不把匿名内存当可回收；同时保留 32 MiB 余量、V8 堆保护、单任务与原文回退。缺少统计时不增加预算。瞬时处理预算不足记 `REDACTION_MEMORY_PRESSURE`，固定敏感值学习数量保护记 `REDACTION_VALUE_LIMIT`，旧 `REDACTION_RESOURCE_LIMIT` 可在历史检查中重试。它们都不表示原文被截断，也不移除原有保护上限。

在“对话日志 → 采集状态 → 历史兼容检查”点击“后台检查并重新处理”。升级只做加法迁移，不自动启动历史处理；任务固定启动前的历史边界并保存游标。原文可用且处理异常或规则过旧时按当前规则重新处理；仅脱敏副本也可独立检查完成证据。排除用户、名单外模型、过期或无正文记录直接跳过，不解密这些正文；成功后按记录原模式保存副本，原文规则同上。

历史任务按需启动独立低优先级进程，256 MiB old-space / 8 MiB semi-space，最多每秒处理一条正文；元数据跳过间隔 250ms。派发前避让正在归档的任务和模型清理，单条预算不足或空间不足暂缓，不生成半份副本；20 秒单条期限，故障 5 秒后续办，同一中断项最多尝试 3 次后暂缓。资源暂缓项可稍后再次手动启动检查。没有任务就退出后台进程。所有处理和解析在写事务外，提交前复核原文版本、保存策略、排除条件与停止状态；数据更新与进度计数同事务提交，写锁等待 1ms，繁忙退避。不会主动全库 VACUUM / 强制 checkpoint，只释放已经加密的旧 BLOB 页供后续复用。

“停止检查”的状态落库后，尚未通过提交前复核的当前结果不会落库，已完成提交的结果保留；关闭页面仍继续，进程故障或服务重启会恢复同一活动任务。任何保存策略版本变化都会暂停任务，核对后重新启动；停止 / 暂停后的新任务跳过已符合规则且已检查的记录。缺失字节、旧无原文记录和真实不可检查媒体不能由本功能恢复。新归档同毫秒的边界项可能留到下一轮检查；并发新增记录不会因 SQLite rowid 复用混入历史处理。

管理员 API：`GET /api/conversation-logs/history-repair` 查看状态，`POST` 同路径提交 `{ "policy_version": <当前保存策略版本> }`，`POST /api/conversation-logs/history-repair/:id/cancel` 停止。沿用管理员会话、CSRF、限流，采集 token 不可调用。任务不读取主站 PostgreSQL、不调用模型、不重放推理、不改变余额；仍共享宿主 CPU / 内存 / IO，避让是尽力而为，不能承诺严格零性能影响。

重新处理采用点击时的最新脱敏规则，但保留该记录原有保存模式和采集策略版本；独立记录处理策略版本及时间。成功后才原子替换副本，“仅脱敏”模式在没有未检查内容时移除临时原文；双副本或仍含协议签名警告的记录继续保留原文。再次失败保留原文并更新异常。管理员会话、CSRF、频率限制、策略 / 记录版本校验和空间预检均生效；当前已排除用户不允许重处理。开关关闭仍允许管理员处理未排除的已有历史，不产生新采集。旧 `redaction_failed` / 超限记录若没有保留原文，不能重处理或恢复。

新副本记录脱敏引擎版本及规则摘要。含未检查内容、旧引擎或旧规则的副本不冒充检查完整的新版脱敏数据；“脱敏优先”输出改用保留原文，并在内部以 `INSPECTION_INCOMPLETE` 或 `REDACTION_OUTDATED` 标记回退原因，可能含未替换敏感信息。有原文时仍可一键重处理，无需先制造处理异常。原文已不存在的旧“仅脱敏”记录无法重新识别所有敏感值，不输出失效副本；原始采集缺字节的历史也不能恢复。升级不自动改写历史、密钥或加密策略。

“部分内容未检查”是检查范围警告，与正文缺失或处理失败独立：图片内部、厂商签名、加密推理和压缩上下文无法靠相同文字规则进一步检查。已经按当前规则成功生成副本、只剩这些警告时，不启用反复“重新处理”，接口也拒绝无效重复任务；真实处理异常或规则 / 引擎更新且有原文时重新启用。保留警告、精确原文和脱敏推送拒绝，不删除图片或替换加密值来隐藏提示、破坏上下文。

归档位于数据卷 `conversation-logs/archive.sqlite`，正文和策略使用 AES-256-GCM，随机 key 位于同目录 `archive.key`；元数据索引用于查询。目录 0700、key / 主库 0600，沿用容器数据卷所有权。**备份必须保留完整目录和 key**；运行中使用 SQLite 备份或停服后复制完整卷，不能只复制主库。已有数据库缺 key 时拒绝初始化，不生成新 key 冒充可读。

保留期非 0 时每分钟和入库时清理过期记录，缩短保留期仍会删除历史及关联推送任务。0 禁用这项清理。容量按数据库 / WAL / SHM 实际占用及可用磁盘检查，空间不足停止新保存；旧策略中的 evict 也不再触发容量淘汰，新保存策略固定 stop。数据库写入失败不返回成功回执，不保存正文缺失的替代记录。管理员原文下载含敏感内容，本功能未新增原文读取审计。

## 历史重新脱敏

“一键清空历史”旁的“一键重新脱敏”使用当前**已保存**的策略和最新算法，在后台从保留的加密原文重建副本，包括当前版本已经处理成功的记录。确认后只处理点击前的历史；排除用户、名单外模型、过期与待首次处理的记录跳过。任务显示扫描、成功、部分内容未检查、无原文、仅存原文、资源暂缓、失败及跳过的数量；刷新、切换页面及进程重启保留进度，可停止。修改保存策略或升级到另一算法时暂停，核对后重新启动。

旧记录仅存脱敏副本时，无法还原过去误替换的值，会明确计入“无原文”，不对已经脱敏的文本反复替换。原保存方式为“仅存原文”的记录计入“仅存原文”，不会擅自改为保存副本。有原文的记录沿用其保存方式：双份保留原文；仅存副本的记录仍在成功且无未检查内容后移除兜底原文。图片、签名和加密上下文的检查范围提示不会因重跑消失，原文回退与外发范围规则保持；失败保留原文及异常状态。已经送达外部的数据不会自动撤回或覆盖；旧待推送副本的版本校验仍生效，需要按新副本重新安排推送。

任务复用历史兼容检查的单个低优先级隔离进程，逐条处理，默认每条间隔 1 秒；新采集与首次脱敏优先，日志查询和下载在处理间隙优先执行，不在主站对话链路中增加等待。内存或空间不足整条暂缓，超时 / 崩溃最多尝试三次，不裁剪正文、不解除 OOM 保护、不自动扩容。暂缓项可稍后重新启动一轮；这是尽力后台处理，仍会使用少量服务器 CPU / 磁盘资源，不承诺共享资源成本严格为零。无需新增服务器环境变量、手动迁移或修改主站。

脱敏引擎 v7 精确保护原生工具定义、选择和调用的名称关联；不再把这些名称学习为人名并传播到普通对话。数字规则排除明确日期、UUID 片段、多列进程信息、技术 ID / 大小 / 时间戳及非金融命令参数；凭据规则区分真实赋值与比较符、变量引用、空 Cookie 示例、工作目录；Git SSH 的固定 `git` 用户及回环 / 未指定地址保留。明确个人身份字段、实际邮箱、电话号码、可识别证件 / 银行卡、真实凭据及持久设备标识继续保护，代码正文仍会检查。原 JSON 数字拼写、请求 ID、消息顺序和签名不重写。识别依赖字段和上下文，不能仅凭字符串保证所有业务语义均正确；可用自定义规则补充本地要求。

管理员接口 `GET/POST /api/conversation-logs/history-redaction` 和 `POST /api/conversation-logs/history-redaction/:id/cancel`，写入要求管理员会话及 CSRF。启动参数仅接受 `policy_version`，以已保存策略为准；与历史兼容检查互斥，不允许从客户端注入强制单条处理参数。持久任务沿用原 SQLite，增加元数据列和单调插入边界，不回填 / 预加载历史正文。

## 日志推送

在“对话日志 → 推送策略”保存 Webhook、S3 兼容存储和发送设置。推送独立于保存开关，默认关闭；当前采集器不需要修改或重新发行，无新增主站环境变量。仅升级运营中心并保留原数据卷 / `archive.key`。关闭采集不会阻止管理员推送已有历史，关闭推送则暂停队列。

1. 配置接收目标，可同时启用两类目标。Webhook 使用 HTTPS URL 与可选 Bearer Token；S3 使用 Endpoint、Region、Bucket、对象前缀和静态 / 临时访问凭据，MinIO 等可选择 Path Style。Bucket 必须已存在。新 S3 策略默认按日期和模型汇总 JSONL，默认文件上限 10 GB、日期时区 Asia/Shanghai、跨日上传尾卷，可设置定时间隔或点击“立即上传待汇总日志”；旧策略保持逐条 JSON，可显式切换。JSONL 需要分片上传及中止残留上传的权限，详见 [JSONL 接入](conversation-jsonl-push.md)。
2. 选择“脱敏优先（不可用则原文）”或“原文”，以及“推送范围”。默认仅传输完整；也可显式选择“包含传输未确认”，本地保留 `complete=false`、原原因、上游状态和诊断，不将其改标完整。脱敏缺失、异常、未检查或规则过期时回退保留的原文，避免因此整轮跳过。原文可能含敏感信息，实际副本和回退原因在本地推送记录中保存，预览及自动入队显示预计回退，不加入新三字段数据；不绕过用户 / 模型排除或已选择的传输范围。两份均不可用仍明确报告，已经丢失的内容无法补回。发送前再次复核，变更不撤回已经送达的副本。
3. 保存后可“测试连接”，仅发送 `sub2api.conversation.test.v1` 虚构诊断 envelope；S3 按当前格式留下 `test-*.json` 或日期 / `test` 模型目录下的 `test-*.jsonl` 对象。JSONL 测试实际执行创建、上传分片和完成，不读取历史正文。
4. 勾选“自动推送新日志”后，可选“实时推送”（旧配置默认）或“推送前一天”；后者按归档日期时区的次日 00:00 起安排此前日期的记录，含迟到旧日志，只持久保存待日期引用。两者均从此次开启之后的新归档开始，关闭期间的历史不自动补发；关闭前已等待日期的记录保留，进程重启继续原进度。手动历史不受该日期限制；存量日志在“历史批量推送”按日期、模型 / 请求搜索、用户、Key、协议、完整性筛选，选择目标后预览、勾选确认并加入队列。每批最多 10,000 条日志，多目标各产生一个任务；已存在的相同任务不重复新增。实时 JSONL 仍按原封卷规则上传；隔日方式需留足一天加上传 / 重试的空间和保留时间，见 [自动推送方式](conversation-jsonl-push.md#自动推送方式)。

“本地保留”可开启“确认送达后清理本地对话日志”，默认关闭。所有已有任务和当前启用目标均确认送达、正文版本未变后，后台删除原文与脱敏副本，正在下载的正文受读取租约保护；轻量送达凭证仍在推送记录显示，日志列表、后续导出和重新脱敏不再包含已删除正文。分片成功或回执不明不会删除。SQLite 可复用空间先释放，物理文件在空闲时渐进回收，无需全量压缩或主站重启，详见 [送达后清理](conversation-jsonl-push.md#确认送达后清理本地)。

凭据与独立推送策略保存在原归档 SQLite 的 AES-GCM 加密表内，管理员 API 仅返回“已设置”。输入留空保留原凭据；清除须勾选清除选项。S3 Session Token 可单独清除，Access / Secret Key 可独立填写新值；清除全部凭据前需关闭 S3 目标（如果是唯一目标，同时关闭推送）。策略版本冲突须重新读取。目标变更后旧任务不会转发到新地址，副本更新后旧任务不会偷偷改发新版；需按新策略重新预览创建批次。

公网目标要求 HTTPS；私网 / loopback 和 HTTP 需要显式勾选“允许私有网络目标 / HTTP”。每次实际发送重新解析并检查所有 DNS 地址，固定本次连接 IP；链路本地 / 云元数据、组播和未指定地址始终禁止，不跟随 HTTP 或 S3 重定向。URL 不含鉴权、查询参数或 fragment，Webhook 鉴权放入专用 Token 字段。没有使用环境代理或 AWS 默认凭据链。

原 SQLite 队列只保存正文引用和任务状态；JSONL 额外保存加密元数据快照、稳定文件成员和已确认分片进度，不复制正文、不建明文临时文件，不在采集请求中发送外部网络请求。正式 Webhook / S3 发送与 JSONL 组装均在独立低优先级子进程执行，故障不回退主 API 同步发送；旧逐条与 JSONL 各限制一个在途任务。JSONL 默认单分片 8 MiB、限速 2 MiB/s，可配置 0.25–64 MiB/s；记录和分片间避让新采集 / 待处理。重试重新读取前缀校验整卷摘要，已确认分片不重复网络上传；远端 ID 失效时沿同 key 重建。分片逐次超时另计限速发送预算、有限退避、队列上限及租约恢复继续生效。网络故障、408、429、5xx 重试，其他 4xx / 重定向 / 禁止地址停止；可手动重试并复用原幂等标识。已汇总成员不占等待处理队列上限，不因日志条数提前切卷。保留期仍可能先删除原记录及关联任务，受影响的 JSONL 整卷取消并重新安排仍合格的成员，不上传缺行文件；到期前六小时提前封卷并显示积压风险，但不延长保留期。上传完成后默认保留原归档，仅显式启用“确认送达后清理本地对话日志”才后台删除符合条件的数据。已跳过的旧副本重处理后，可手动历史批量推送。预览与当前策略的自动扫描会分别显示跳过原因。

批次取消只取消未完成任务。配置 / 采集名单变化和正常退出会中止在途发送，但已发出的字节不能撤回；目标可能已接收而回执丢失，因此是**至少一次**投递。Webhook 接收端必须按 `Idempotency-Key` 去重，同一任务重试时该值和 `delivery_id` 保持相同。旧 S3 JSON 对象名仍为 `<prefix>/<UTC日期>/<delivery_id>.json`。新 JSONL 使用 `<prefix>/<日志日期>/<模型目录>/<模型>-<日志日期>-<UTC时间戳>-<稳定文件ID>.jsonl`；前缀留空时日期直接在桶下。旧路径开放卷先封卷、已有文件继续原 key，不改写在途上传或重发历史。同卷重试复用同一 key、顺序与内容，不追加重复行；开启版本控制的 Bucket 仍可能保留多个对象版本。关闭运营中心或进程异常后的未知送达会沿用原标识重试，不承诺恰好一次。

外部副本的访问控制、保留期、删除和加密由接收系统负责；本地淘汰或用户排除不会远程删除已送达对象。Webhook 仅以 2xx、S3 JSON 以成功 PutObject、JSONL 以成功 CompleteMultipartUpload 回执确认送达，不检查下游是否已完成入库或后续处理。目标返回正文和原始错误不会落入任务表，只保存固定错误码与 HTTP 状态。资源建议与待确认配置见 [JSONL 服务器清单](conversation-jsonl-push.md#服务器配置待确认)。

### 接收格式

新下载、Webhook POST、S3 JSON 对象和 JSONL 的每一行均输出网关请求 ID 与两侧正文：

```json
{
  "request_id": "0123456789abcdef0123456789abcdef",
  "request": "{\"model\":\"gpt-6-astra\",\"stream\":true}",
  "response": "data: {\"delta\":\"hello\"}\r\n\r\ndata: [DONE]\r\n\r\n"
}
```

`request_id` 是归档中保存的网关请求 ID（32 位小写十六进制），与运营中心详情中的请求 ID 一致，不是归档行 ID、投递 ID 或厂商正文里的 `resp_...` 等上游 ID；不改写正文中的任何同名字段。脱敏、原文与原文回退均保留相同请求 ID。一次网关请求的多个上游尝试可能共用此值，每次尝试仍单独输出，不按它合并或去重。Webhook 去重继续使用投递幂等头，JSONL 按对象 key 和行位置识别各条尝试。

采集入口本已验证并保存请求 ID，本次缺失来自此前对外精简投影。已有归档重新下载即可补带，无需重新采集或批量回写。若归档字段因异常缺失 / 无效，下载明确报 `CONVERSATION_EXPORT_REQUEST_ID`，推送报 `EXPORT_REQUEST_ID` 且不自动网络重试；不静默省略、伪造 ID、跳过该行或假报文件完整。正文与原归档不受该输出错误改变。

Request / Response 保持正文字符串，不将厂商 JSON 解析成对象，避免大整数舍入或数值拼写变化。对已知压缩响应进行完整后台解压；检查解码器已消费全部压缩输入，不能静默丢弃尾部。解压内存不足时明确失败 / 重试，不输出截短正文，也不因瞬时预算变化切换成另一份文件。原始加密归档和 `.raw` 下载仍保留压缩传输字节。

WS 有消息帧时，`request`、`response` 分别为发往上游 / 上游返回的消息字符串数组，保留各方向的相对顺序和空消息；存在非空初始请求 / 返回正文时，作为相应数组首项。帧时间、交错顺序、binary 标记等采集元数据留在运营中心内部，不混入正文。正文内已有图片 Base64、模型加密字段或签名原样保留，不递归解码、下载或尝试解密。

真正二进制或无效 UTF-8 为 `data:application/octet-stream;base64,<完整原字节的Base64>`；坏压缩、未知压缩或解压后仍为非法文本时，为 `data:application/octet-stream;content-encoding=gzip;base64,<完整原压缩字节的Base64>`（gzip 随实际编码变化）。这是特殊正文值的约定，没有额外 JSON 字段；接收方需接受该表示，不应把它当正常对话文字或递归解码正文内部的 data URL。没有假设特殊字节一定是采集故障。

副本来源、原文回退原因、用户信息、完整性 / 传输诊断、原字节摘要仍在本地归档和管理状态中保存，不写入新的对外 JSON；导出状态仍报告实际回退数量。Webhook 幂等标识保留在 `Idempotency-Key` 请求头，S3 单条 ID 保留在 key / 对象元数据中，整卷摘要和分片恢复保持。接收方不能再从新正文中读取本地元数据或自行推断完整性。

内部格式版本为 4，仅用于任务身份和选择序列化，不作为 JSON 字段外发。沿用既有小列，不回写历史正文。旧 v1 / v2 / v3 排队、失败重试、已汇总及分片中的任务保持原格式、ID、对象 key、行字节和摘要；v3 仍仅有 request / response。同日同模型遇新格式先封旧卷再建新卷，单卷不混格式。新任务和重新下载历史使用上述三字段数据；旧推送若需补带请求 ID，应重新预览安排新任务，可能再次推送旧格式曾送达的记录，接收方需按幂等头或其自身业务规则处理，不能用请求 ID 去掉合法的不同尝试。升级不重置自动游标、不自动重发历史。

管理员接口均位于 `/api/conversation-logs/push`，需要现有管理员会话，写请求还需 CSRF；采集令牌不能访问。策略 `GET/PUT /policy`，状态分页 `GET /jobs`，历史 `POST /preview` → `POST /batches`，批次 `GET /batches/:id` / `POST /batches/:id/cancel`，单任务 `POST /jobs/:id/retry`，诊断 `POST /test/:destination`。批次提交使用客户端 UUID 和预览 token，相同 UUID / 参数重复提交返回原批次；策略 / 内容版本改变须重新预览。没有新增公开正文下载端点。

## 发布与验收

大正文初次仅加载前 64K 字符的文本预览，不重复携带整段 base64；“查看完整”按钮按需展开，复制与下载始终读取完整内容。预览不改变保存正文、原始字节、SHA-256、脱敏规则或排除名单。邮箱规则按 `@` 定位并从固定位置校验域名，流式替换统一拼接，避免长文本和大量替换阻塞运营中心。

主站 dev 推送触发 Fork Dev Release，单元 / race 测试、前端构建、五平台压缩包及 SHA-256 校验、双架构镜像运行验证通过后发布。GitHub Release 为三段数值版本，兼容原生更新器；镜像为 `ghcr.io/fjiangming/sub2api:<version>`，最新成功版本更新 `dev`、`latest`。主站更新来源、版本菜单和安装脚本均指向本 fork，旧上游缓存不会复用。

本仓库 main 推送沿用 Docker images 流程，运行运营中心完整测试后构建原生 linux/amd64 和 linux/arm64 镜像，检查 SQLite、源码 revision、对话归档模块和导航资源，再发布 `ghcr.io/fjiangming/sub2api-extra:operations-center-latest`、`operations-center-main` 及 `operations-center-sha-<短SHA>`。不再维护本仓库独立 dev 分支或 dev 发布流程；主站仍保留其独立 dev 分支。

主站左上角更新仅升级主站程序。运营中心需要按原 Compose 项目单独更新，保留完整原数据卷及归档 key；沿用 `operations-center-latest` 的部署无需切换镜像通道。新版运营中心即使尚未接入采集也会显示“对话日志”入口，实际保存仍需上面的连接 / token 配置和管理员启用策略。源代码发布不自动操作服务器。

本地 `npm test`、`npm run check`；`npm run preview:conversations` 启动隔离的正式页面预览（默认 `http://127.0.0.1:19907/preview`），仅虚构数据和临时 SQLite。`npm run check:conversations-ui` 通过 Playwright 检查下载原字节、会话、排除与模型配置保存 / 重载、名单外零新增、空名单 / Kimi 范围、XSS、退出清理及窄屏布局，可用 `PLAYWRIGHT_MODULE_PATH` / `PLAYWRIGHT_CHROMIUM_EXECUTABLE` 指定已有运行时。

`npm run check:conversation-push-ui` 额外用 loopback 接收器验证 Webhook / S3 签名、诊断、自动 / 历史 / 去重、失败 / 重试、凭据留空和离开 / 退出清理，覆盖 1440 / 390 / 320px 及系统深色；不会发送生产正文或连接真实存储。发布前仍需原有 CI / 原生镜像运行检查，源码和本地测试通过不等于已发布或部署。
