# 安全设计与上线闸门

## 保护目标

1. 未真实到账的订单不能获得 Sub2API 额度。
2. 同一支付宝交易和同一充值订单最多发放一次额度。
3. 支付宝私钥、动态二维码原文、完整交易号、完整自动备注、Sub2API 令牌和个人收款码不进入日志或公共静态目录。
4. 上游超时、进程崩溃和重复点击不能导致重复入账。
5. 每次自动/人工判断、异常告警和额度发放都有可追溯审计事件。

## 信任边界

| 边界 | 信任内容 | 不信任内容 |
|---|---|---|
| 用户浏览器 | 当前 Sub2API 身份令牌经 `/auth/me` 验证后的用户 ID | 用户声明已付款、截图、输入金额 |
| 支付宝官方接口 | Sub2API RSA2 验签并核对主体、订单和金额后的结果 | 浏览器跳转结果、未验签通知、个人码到账猜测 |
| 支付宝账单（人工模式） | 管理员在受信设备上看到的收款状态、付款时间、金额、完整交易号 | 用户发送的账单截图或口述 |
| 个人码生成代理 | 已认证设备在本人支付宝可见页面回读的本单金额、备注和直接 `fkx...` URL | 代理自行声称的订单归属；服务端仍校验租约、金额、备注、时间和 URL 唯一性 |
| 个人转账监听器 | 已认证设备提交的原始请求体、时间戳和 nonce | 监听器对支付宝事实的声明；仍须逐字段匹配，心跳/通知栏不能证明到账 |
| 充值中心 | 官方订单回读结果、provider instance allowlist、本地人工模式状态机与审计账本 | 客户端提交的状态、用户 ID、应付金额、二维码 URL |
| Sub2API | HTTPS/受控内网连接上的认证支付 API、官方 provider 快照和兑换履约结果 | 超时请求的“失败”假设、不完整成功响应、误配置到 EasyPay 的实例 |
| 运营中心 | `redeem_codes` 中已使用的余额兑换记录 | 充值中心本地状态本身 |

## 关键控制

### 身份与会话

- 用户身份只由 Sub2API 登录响应或 `/auth/me` 确认，客户端不能提交入账用户 ID。
- 生产环境默认关闭密码代理登录，只接受 Sub2API 自定义菜单的令牌交换；确需密码登录时必须显式开启。
- `personal_manual` 与 `personal_transfer_auto` 模式下，普通用户 Sub2API 访问令牌完成身份交换后立即丢弃。
- `sub2api_official` 模式下，普通用户短时令牌仅保存在绑定会话的进程内存中，用于用户级支付 API；不落盘、不写日志、不返回浏览器，且不具备管理员权限。
- 管理员令牌仅存在于进程内存，中心重启后管理员必须重新登录。
- 中心会话使用 256 位随机令牌、HttpOnly Cookie、Partitioned Cookie、CSRF token，并绑定 IP 与 User-Agent；令牌不暴露给前端 JavaScript 或 Web Storage。
- 生产环境强制 HTTPS 与 Secure Cookie。

### 官方支付证据

- extra 不保存支付宝 AppID、应用私钥或支付宝公钥；它们只配置在 Sub2API 官方支付宝 provider 中。
- 创建前要求 CNY、充值倍率 `1`、手续费率 `0`，并计算 Sub2API 与 extra 金额范围的交集。
- 创建后通过用户级订单接口回读，核对用户 ID、订单 ID、`out_trade_no`、`amount`、`pay_amount` 和 `provider_instance_id`；实例必须命中显式官方支付宝 allowlist。
- 动态二维码原文仅存在进程内存，且必须是支付宝 HTTPS 域名；浏览器只取得带鉴权、`no-store` 的服务端渲染 PNG。
- 支付成功以 Sub2API 验签 webhook 或 Sub2API 调用 `alipay.trade.query` 的结果为准。extra 的轮询不直接接触支付宝密钥。
- 同单轮询不重入，设置全局并发上限；错误指数退避，令牌过期或订单终态立即停止。
- Sub2API 在履约前再次校验 provider、商户元数据、商户订单号、交易号和金额，并用支付订单租约与固定兑换码保持幂等。

### 人工付款证据

- 用户提交完整支付宝交易号，但只持久化 `HMAC-SHA-256(secret, namespace || tradeNo)` 和末六位。
- `trade_hash` 有唯一索引，同一交易不能复用。
- 同额活动订单可以并存；金额仅用于筛选候选账单，不能单独证明订单归属。
- 管理员页面不显示用户提交的完整交易号；管理员必须从支付宝账单重新读取并输入。
- 管理员必须录入支付宝账单付款时间，服务端强制其位于订单创建到过期之间，防止套用历史交易。
- 管理员输入的实收金额必须与服务端订单精确分值一致。
- 不提供截图上传接口。

### 个人转账自动证据

- 自动模式固定 180 秒订单窗口，运行时不能通过环境变量放宽。
- 金额占位在 SQLite 事务内完成；优先原金额，同额冲突时只尝试 `+0.01..+0.99`，每个实际金额在原三分钟内全局独占。
- 活动占位达到 100 笔后拒绝新订单。订单取消或提前完成不会提前释放金额，避免已经扫码的付款与新订单碰撞。
- 每单生成 `S2-<16位base64url>` 随机备注（96 位熵），永不复用，不含用户 ID、邮箱、时间或可枚举序号。
- `collector` 来源为每单建立短租约；代理回传的金额、备注和生成时间必须与订单一致，只接受无查询串/片段/凭据的直接 `https://qr.alipay.com/fkx...`，并拒绝跨订单重复 URL。
- 浏览器订单 JSON 不返回完整备注、二维码 URL 或代理租约；URL 使用 AES-256-GCM 密文保存，二维码端点只在鉴权和订单状态校验后解密并服务端渲染 PNG。
- 二维码代理和到账监听器使用独立密钥。版本 2 签名覆盖 `method + "\n" + path + "\n" + timestamp + "\n" + nonce + "\n" + rawBody`；服务端限制时间漂移并按权限域持久化 nonce HMAC，防止跨接口使用和抓包重放。
- 采集器只有在支付宝账单访问、登录状态和详情字段自检均成功后才能报告 `ready=true`；心跳或最近成功轮询超时会让 `/readyz` 失败并禁止创建新订单。
- `collector` 模式还要求二维码代理独立健康；到账监听器不能代替其心跳。付款时间不得早于本单二维码生成时间。
- 已发生的付款事件仍可延迟提交，但超过 `RECHARGE_CENTER_LISTENER_MAX_EVENT_AGE_SECONDS` 后只保留证据、告警并转人工，不能自动放款。
- 自动放款要求 `ledger_detail`、随机备注、精确金额、收款标识、收入方向、成功状态、完整交易号和付款时间全部匹配。
- 支付时间按秒比较，必须位于原订单窗口；监听晚到可以恢复已过期订单，但未来时间、迟付或历史交易转人工。
- `payment_events` 只保存交易号/备注/收款标识的带密钥 HMAC及必要尾号。同一交易号唯一，冲突事件不能覆盖首次证据。
- 手机通知和账单列表摘要只能触发详情查询，不可作为 `ledger_detail` 提交。
- 未知备注、字段缺失/不一致、重复交易、取消订单付款或履约不确定都停止放款，写审计并发送脱敏告警。
- 此链路依赖非官方、可能变化的个人账单采集面。生产闸门只表示该账号和客户端版本已完成实测，不表示支付宝对接口稳定性作出承诺。

### 幂等入账

- 订单创建时生成固定 32 字符兑换码，后续重试不改变。
- 每次尝试使用 `Idempotency-Key: recharge-center-<order UUID>-<attempt>`，同一尝试不重复执行；恢复尝试换键但保持兑换码不变，以兼容 Sub2API 的既有兑换码幂等语义。
- 自动模式只使用与其他本服务凭据隔离的 Admin API Key 调用履约接口；二维码代理密钥、监听器密钥、SMTP 密码、可选 Webhook Token、账本密钥和 Admin API Key 由配置校验强制互不相同。
- Sub2API `0.2.13` 的 Admin API Key 是全局管理员能力而非充值 scope；充值中心虽只调用 `create-and-redeem`，仍必须通过受控内网、出站 ACL、主机隔离和轮换演练限制密钥泄露后的影响。
- 成功响应必须同时满足兑换码、类型、值、状态和 `used_by` 全部匹配。
- 超时、连接中断或响应无法验证时进入 `needs_attention`，不会生成第二个兑换码。
- `needs_attention` 不能拒绝或删除，只能用原身份恢复并由 Sub2API 幂等语义收敛。
- 每次入账带尝试代次；过期请求的迟到失败不能覆盖更新的恢复结果。

### 数据保护

- SQLite 使用 WAL、`synchronous=FULL`、外键和唯一约束。
- 数据目录尝试设置 `0700`，数据库尝试设置 `0600`。
- 账本保存密钥校验值；误换 `RECHARGE_CENTER_SECRET` 时拒绝启动。
- 未核销兑换码使用由独立域密钥派生的 AES-256-GCM 密文保存，并绑定订单 ID；只读账本泄露不会直接暴露可兑换码。
- 自动备注和不透明二维码 URL 分别使用独立域密钥 AES-256-GCM 保存并绑定订单 ID，查找与唯一性判断只使用 HMAC。
- 审计 IP 只保存带密钥 HMAC，不保存原 IP。
- 错误消息写日志前清除 Bearer token、查询 token 和长数字交易号。
- API、二维码和静态应用均设置禁止缓存；页面禁止搜索引擎索引。

### 独立异常通知

- 通知模块完整位于 `recharge-center`，不调用 Provider Monitor、运营中心或其他扩展服务，也不读取它们的配置、数据库或通知通道。
- 个人转账自动模式必须配置 SMTP 邮件；可选 HTTPS Webhook 只能作为第二通道，不能替代邮件。
- SMTP 使用专用账号密码，生产环境强制 SMTPS 或 STARTTLS，TLS 最低版本为 1.2 且验证服务端证书。
- Webhook 生产地址必须为 HTTPS，禁止 URL 凭据和片段，拒绝重定向，并使用至少 32 字符的独立 Bearer Token。
- 邮件和 Webhook 载荷从固定字段白名单重新构造，不透传监听事件；完整交易号、完整备注、收款账号、用户 ID、邮箱、Cookie 和支付宝凭据不会进入通知。
- 每个通道最多执行三次有限退避重试，Webhook 响应最多读取 64 KiB；永久 4xx 和 SMTP 5xx 不重复发送。
- 通知失败只写入本地审计代码 `RECHARGE_ALERT_DELIVERY_FAILED`。异常订单已在通知前停止放款，因此邮件系统故障不能导致误充值。

### Web 与容器

- CSP 只允许本站脚本、样式、连接和图片；`object-src 'none'`、`base-uri 'none'`。
- `frame-ancestors` 只允许充值中心与配置的 Sub2API 来源。
- 不启用 CORS；生产 POST 请求必须来自 `RECHARGE_CENTER_PUBLIC_URL` 的 Origin。
- JSON 请求上限 16 KiB，Nginx 建议上限 32 KiB。
- 容器只读根文件系统、删除全部 Linux capabilities、启用 `no-new-privileges`。
- 人工个人码图片只读挂载，不复制进镜像，不通过静态目录服务；官方码、模板码和 collector 返回的不透明 URL 均在服务端动态渲染且不落盘。

## 仍需运营控制的风险

| 风险 | 运营控制 |
|---|---|
| 支付来源误配置到 EasyPay | Sub2API 明确选择官方来源；extra 用官方实例 ID allowlist 回读校验 |
| 支付宝应用私钥泄露 | 私钥只进 Sub2API 密钥配置；最小权限、加密备份、换钥演练和异常订单监控 |
| webhook 延迟或丢失 | extra 有限频主动查询 + Sub2API 超时补偿任务；两条路径复用同一履约幂等逻辑 |
| 轮询放大上游故障 | 同单防重入、全局并发限制、指数退避、会话过期停止 |
| 管理员支付宝设备被控制 | 专用设备、设备锁、登录设备巡检、收款提醒 |
| 管理员与攻击者串通 | 高金额采用两人复核；当前版本是单管理员 + 支付宝账单持有证明 |
| 个人码被支付宝限制 | 降低档位和频率，及时迁移官方商家能力 |
| 支付宝页面/非公开数据结构变化 | 字段缺失立即报告 `ready=false` 并停止事件提交；服务同时检查心跳与最近成功轮询时间，适配器仍需做详情字段自检和版本验收 |
| 二维码生成页面变化或复用旧码 | 代理健康检查失败即停止接单；服务校验回读金额/备注、租约、生成时间与 URL 全局唯一性，失败即取消并告警 |
| 备注被用户修改、截断或支付宝不保留 | 无法命中即转人工，不根据相近金额或时间猜测归属 |
| 二维码代理被控制 | 其独立密钥无权上报到账；立即停代理、轮换二维码代理密钥并检查已生成订单 |
| 监听器设备或密钥被控制 | 精确收款账户/窗口/交易唯一性只能降低风险，不能恢复官方签名保证；立即停服、轮换监听密钥并全量对账 |
| Sub2API Admin API Key 泄露 | 当前 Key 具有全局管理员能力；只走受控内网，限制充值中心出站目标，禁止跨服务复用并立即在 Sub2API 重新生成 |
| 异常邮件投递失败 | 充值中心内置通道有限重试；本地审计保留失败代码，监控 `RECHARGE_ALERT_DELIVERY_FAILED` 并巡检人工处理队列 |
| 反向代理记录 query token | 使用 README 中不含 `$args`/`$request_uri` 的专用日志格式 |
| SQLite 卷或密钥丢失 | 停机一致性备份，账本与密钥分开保管并联合演练恢复 |
| 已入账交易后续退款 | 保留原记录，以带订单号的负向财务记录冲销，不删除历史 |

## 上线闸门

上线前逐项确认：

- [ ] Sub2API 已升级到本文标注的兼容版本；官方模式的支付订单、主动查询和原生兑换履约接口可用。
- [ ] 充值中心仅绑定 `127.0.0.1`，公网只通过 HTTPS 反向代理进入。
- [ ] 代理访问日志不记录查询参数，错误日志也不记录请求体或 Authorization。
- [ ] `RECHARGE_CENTER_SECRET` 已离线备份，且不是其他服务密钥的复用值。
- [ ] 官方模式 `/readyz` 显示 `paymentQr: dynamic`；人工模式二维码文件未进入 Git、容器内只读且显示 `paymentQr: true`。
- [ ] 个人自动模式真实扫码能够自动带入金额和完整随机备注，且最终交易详情原样保留备注。
- [ ] 二维码代理与到账监听器使用不同密钥；交叉调用接口均返回 401，数据库和普通日志中没有明文 `fkx...` URL。
- [ ] 浏览器/手机适配器只提交最终详情；页面字段缺失、通知栏事件和列表摘要均不会产生 `ledger_detail`。
- [ ] 停止监听心跳、报告 `ready=false` 或让最近成功轮询时间过期后，`/readyz` 均为 503 且新订单被拒绝；真实轮询恢复后才允许创建。
- [ ] 超过最大迟到窗口的事件即使声称 `paidAt` 位于订单窗口也不会自动放款。
- [ ] 错金额、错备注、错收款人、支出、处理中、窗口外付款和重复交易全部未放款并产生告警。
- [ ] 充值中心专用 SMTP 账号已实测，生产链路使用 SMTPS/STARTTLS，邮件不含完整交易号、备注、用户邮箱或收款账号。
- [ ] `RECHARGE_CENTER_AUTO_MODE_VERIFIED=true` 只在上述测试完成后设置，并记录支付宝/浏览器/手机版本。
- [ ] 官方模式只允许 `provider_key=alipay` 的实例 ID，支付宝可见来源未指向 EasyPay。
- [ ] 官方模式倍率为 `1`、手续费率为 `0`、币种为 CNY，webhook 公网 HTTPS 可达且完成验签实测。
- [ ] 管理员账号启用 TOTP；普通管理员与日常用户账号分离。
- [ ] 真实小额测试验证了动态码收款主体；自定义金额、快捷金额及上下限均正确。
- [ ] 测试订单经 webhook 和主动查询两条路径都只产生一条 `balance/used` 兑换记录。
- [ ] 运营中心同日 CNY 自动收入能看到该测试记录及正确用户。
- [ ] 人为阻断一次 webhook 和一次查询响应，验证补偿查询及履约重试不会重复入账。
- [ ] 完成账本与密钥恢复演练。

## 事故处置

发生疑似错充、重复入账、二维码替换、令牌泄露或账本损坏时：

1. 立即关闭充值入口并停止二维码代理与个人转账监听器；官方模式同时禁用受影响的支付宝 provider instance。保留数据库、数据卷和订单。
2. 导出相关时段的支付宝商家账单、Sub2API 支付审计/兑换记录、充值中心备份和运营中心记录。
3. 撤销受影响的 Sub2API 会话/API Key；分别轮换二维码代理密钥、监听密钥、SMTP 密码和 Webhook Token。若官方应用私钥可能泄露，在支付宝侧换钥并更新 Sub2API。
4. 对比订单号、兑换码尾号、用户 ID、精确金额和时间线。
5. 通过 Sub2API 正式余额调整流程修正，不直接改数据库，不删除原兑换记录。
6. 确认根因和补偿完成后，再恢复入口并加强对应控制。

不要在未保全账本与支付宝原始记录前执行清理或覆盖恢复。
